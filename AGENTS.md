# Работа в `wb-core`

Этот файл — единственная обязательная точка входа. Остальные документы читаются
только когда относятся к задаче.

## Оформление задач WBC

- В новом или ещё не оформленном основном/кураторском чате WBC первым действием
  по содержательному запросу прочитай и выполни навык `wbc-task-intake` из
  `${CODEX_HOME:-$HOME/.codex}/skills/wbc-task-intake/SKILL.md`. Это обязательный
  шаг для `WBC_new`, серверных проектов `/srv/wbc/repo` и их рабочих деревьев.
- Новая задача получает номер только из общего реестра VPS; затем переименуй
  и закрепи текущий чат и проверь результат. Локального запасного счётчика нет.
- При явной просьбе подхватить существующую задачу примени тот же навык:
  проверь номер по реестру и паспорту и оформи чат с прежним номером, без нового
  резервирования. Уже оформленные задачи не перенумеровывай. Оформление чата
  не расширяет разрешённые работы и не отменяет явные ограничения пользователя.

## Как работать

- Принятую задачу доводи до результата самостоятельно. Спрашивай пользователя
  только когда нужен его личный выбор, отсутствует необходимый доступ или
  действие необратимо и явно не входит в задачу.
- Явные границы пользователя — «только обсудить», «ничего не менять», «до PR»,
  «остановись» — обязательны.
- Главный чат / куратор отвечает за пользовательскую цель и итог: обсуждает,
  принимает существенные решения, планирует, по умолчанию делегирует техническую
  работу и принимает её по доказательствам. Сам он читает код, когда это нужно
  для существенного решения.
- Куратор выбирает полезные роли, порядок работы и достаточный контекст. Нет
  обязательных этапов или фиксированного числа агентов. Один изменяемый ресурс
  одновременно имеет одного ответственного.
- Перед выводом или изменением проверь актуальное состояние, прочитай только
  относящийся к задаче код и документацию и не смешивай чужие незавершённые
  изменения со своей работой.
- Изменения репозитория делай в отдельной ветке через PR. Не добавляй в PR
  секреты, production-выгрузки и посторонние файлы.
- В контексте WBC короткие просьбы о паспорте, например «составь паспорт»,
  «составь паспорт задачи», «создай паспорт», «подготовь паспорт», «подготовь
  паспорт для миграции» и «обнови паспорт», означают применить протокол
  [передачи этой же задачи через паспорт](docs/architecture/07_codex_execution_protocol.md#передача-задачи-через-паспорт).
  Не требуй повторно объяснять назначение: сначала проверь доступные материалы и
  спроси только о существенной неоднозначности, которую нельзя снять
  самостоятельно; необязательный неизвестный факт честно отметь как неизвестный.
  Не создавай паспорт при явной границе «только обсудим» или «пока не создавай»
  и не подменяй другой явно указанный вид паспорта паспортом задачи WBC.
- По просьбе передать или подхватить задачу используй общий указатель
  `/srv/wbc/context/INDEX.md`. Создание или обновление паспорта требует проверки
  фактического состояния, не означает фактический приём задачи в другой среде,
  не разрешает внедрение и не расширяет границы задачи.
- Проверки выбирай по изменённой области и риску. Полный набор нужен только для
  действительно сквозного или опасного изменения.
- Итог пользователю сообщай коротко: что получилось, что проверено и какой
  существенный риск или следующий шаг остался.

## Модели агентов

Модель выбирается по роли, без классификации задач по сложности:

| Роль | Модель | Уровень рассуждения |
| --- | --- | --- |
| Главный чат / куратор | `gpt-6-astra` | `high` |
| Первичный поиск | `gpt-6-luna` | `high` |
| Предварительный аудит | `gpt-6-sol` | `high` |
| Реализация и исправления | `gpt-6-sol` | `high` |
| Код-ревью | `gpt-6-sol` | `high` |

При запуске явно задавай модель и уровень рассуждения по роли, не полагайся на
наследование настроек родителя. Ясную простую реализацию куратор вправе поручить
`gpt-6-luna`. Эти правила не требуют дополнительных агентов или обязательных
этапов. Границы ролей описаны в
[протоколе выполнения](docs/architecture/07_codex_execution_protocol.md#роли-и-модели).

## Production и данные

- Сначала точно определи источник, цель и текущее состояние. Отсутствующие
  данные не равны нулю.
- Чтение production выполняй без записи. Для SQLite используй read-only режим и
  `PRAGMA query_only=ON`.
- Перед опасной записью нужны проверяемый кандидат, состояние «до», подходящий
  способ восстановления и повторная проверка цели непосредственно перед
  записью.
- Запись отправляется не более одного раза. Неоднозначный сетевой ответ означает
  только чтение результата той же операции, а не повторную отправку.
- Резервная копия нужна для изменяемых production-данных, которые нельзя
  восстановить из Git или внешнего источника. Для обычного изменения кода
  достаточно Git.
