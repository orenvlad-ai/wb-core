# Работа в `wb-core`

Это общий рабочий минимум. Остальные документы читай только по задаче.

## Общие инструкции и номера чатов

- Источник общих правил — `AGENTS.md` в `origin/main`. На этом Mac оба аккаунта
  читают его из `/Users/Shared/WBC/rules/AGENTS.md`; местные варианты не ведём.
  Общие изменения вноси через PR; после слияния обнови общую копию из `main`.
  Связанные документы читай только по задаче, из той же общей копии.
- В начале нового основного чата получи готовое название командой
  `python3 /Users/Shared/WBC/rules/docs/local_tools/wbc_chat_number.py THREAD_ID --title "краткая тема"`
  и используй её вывод дословно: `WBC 0163 краткая тема`. Между номером и темой
  только один пробел, без тире и других разделителей. Затем закрепи чат и проверь
  точное совпадение названия с выводом команды и наличие среди закреплённых.
  Повторный запрос с тем же ID возвращает прежний номер; при продолжении задачи
  используй ID исходного чата. Старые номера сохраняй, помощников не нумеруй.
  Если счётчик недоступен, сообщи об этом; номер самостоятельно не придумывай.

## Модели и помощники

Главный чат отвечает за результат; небольшую задачу выполняет сам. Делегируй
самостоятельную часть работы, когда выигрыш оправдывает передачу контекста;
мелкие однотипные поручения объединяй. Предпочтения:
`gpt-6-luna` — извлечение, сверки и механические изменения по ясным правилам;
`gpt-6.1-terra` — тексты, изображения и работа с интерфейсом;
`gpt-6.1-sol` — основная разработка и диагностика;
`gpt-6-astra` — сложные решения, существенный риск, неопределённость и тупики.
Это варианты выбора, не обязательная цепочка. Учитывай стоимость переделок.

При создании помощника явно задавай модель и достаточную глубину рассуждения,
не выбирай повышенную глубину автоматически. Для отдельной модели используй
`fork_turns="none"`: передай цель, границы, нужные источники и критерий готовности.
Полную историю наследуй только когда она нужна; тогда модель наследуется тоже.
Уточнения продолжай с тем же помощником. При смене модели передай новому
помощнику уже полученные результаты и конкретную причину эскалации.

## Самостоятельность

- Доводи порученную работу до проверенного результата. Явные границы пользователя
  обязательны; спрашивай только о необходимом личном выборе, недоступном ресурсе
  или действии за пределами разрешённой работы.
- Выбирай способ работы, глубину исследования, инструменты и помощь других
  агентов по необходимости. Обязательных ролей, этапов и моделей нет.
- Не повторяй проверки и ревью без изменения кода, условий или нового риска.
  Независимое ревью используй там, где ошибка существенно повредит данным,
  безопасности, деньгам или выпуску.
- Сообщай просто и кратко: результат, существенные ограничения и следующий шаг,
  если он нужен. Проверенный факт отличай от предположения.

## Код и проверка

- Работа ведётся локально. Перед изменением обнови `origin/main`, проверь рабочую
  папку и используй отдельную ветку через PR. Параллельные задачи и два аккаунта
  не должны изменять один рабочий каталог; чужие изменения сохраняй.
- Изучи относящиеся к задаче код и контракты. Выбирай минимальное достаточное
  исправление и проверки затронутого поведения. Общие изменения требуют проверки
  связанных областей, а не автоматического прогона всего репозитория.
- Проверь итоговый diff и пользовательский результат. Не объявляй локальную
  проверку выпуском, а успешную команду — доказательством результата.

## Данные и рабочий сервер

- Подтверждай актуальную цель и источник. Отсутствующие данные не равны нулю.
- Читай production без записи; SQLite открывай с `mode=ro` и `query_only`.
- Перед опасной записью проверь кандидата, состояние «до» и способ восстановления.
  Backup нужен для данных, которые нельзя восстановить из Git или источника.
- Одновременно записью управляет один ответственный. При неопределённом ответе
  читай результат той же операции; повторная отправка записи запрещена.
- Секреты и production-выгрузки остаются вне Git. Выпускай проверенную версию
  штатным механизмом и подтверждай фактический результат.
