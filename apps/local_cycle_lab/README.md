# Локальный стенд WBC

## Проверка источников из командной строки

Из корня репозитория, Python 3.11+ и зависимости приложения (`openpyxl`):

```sh
python3 -m apps.local_cycle_lab
python3 -m apps.local_cycle_lab --variant zero
python3 -m apps.local_cycle_lab --variant missing
python3 -m apps.local_cycle_lab.smoke
```

Каждый запуск создаёт временную базу, выполняет штатный сбор обеих дат,
derive, CAS-публикацию Ready и чтение опубликованной витрины. `verification`
сравнивает числа и признаки полноты с независимыми ожиданиями из `scenario.json`.
Ошибка проверки завершает команду ненулевым кодом. Формулы и проверки приложения
не подменяются. Входы основного сценария синтетические. Отдельная проверка сохранённого ответа WB описана ниже.

Варианты меняют только рекламу за 23 ноября. `normal`: наблюдаемые расходы 60 ₽,
100 показов, 10 кликов, 2 заказа и 800 ₽ атрибутированной выручки; DRR 7,5%.
`zero`: те же поля в ответе равны нулю, расход 0 ₽, отношения с нулевым
знаменателем остаются пустыми. `missing`: HTTP 503, значения пустые, дата не принята,
сохраняется штатный повтор. Во всех доступных вариантах полный датированный состав
рекламных кампаний не доказан: наблюдаемый ноль **не подтверждает нулевые расходы
всего кабинета**. В конечных ячейках сохраняется `partial / unknown_scope`.

Перед первым сбором стенд выполняет отдельный штатный сбор текущих показателей
на часах 23 ноября. На часах 24 ноября работает штатный rollover. Вчера:
рейтинг 4,6, цена 380 ₽, SPP и proxy 10%, ставка 140 ₽; сегодня: 4,8, 400 ₽,
20%, 150 ₽. Различающиеся числа обнаруживают перенос сегодняшнего значения назад.
Начальные данные не записываются непосредственно в таблицы принятых снимков.
Бизнес-даты и расчётные входы фиксированы; некоторые диагностические timestamps
штатных клиентов (например, ads source_observed_at) используют реальные часы
запуска. Побайтовое совпадение всех метаданных между запусками не обещается.

Finance содержит SKU 101 и SKU 999 вне витрины. Выручка карточки 101 — 400 ₽,
доставка — 4 ₽, эквайринг — 3 ₽. Хранение кабинета — **2 + 9 = 11 ₽**,
включая товар 999. Нельзя сузить исходный финотчёт до карточек витрины.
Исторический display-stock карточки — 12; текущая дата и разбивка по складам
отсутствуют. Отдельная проверка клиента FBS получает 7 единиц размера 9001.
Это разные источники, а не два подтверждения одного складского снимка.

Для сохранения базы между командами передай новый отдельный путь:

```sh
python3 -m apps.local_cycle_lab --state /tmp/wbc-local-normal
python3 -m apps.local_cycle_lab --state /tmp/wbc-local-normal
```

Каталог и начальные наблюдения создаются один раз. Папка должна иметь маркер того
же сценария и варианта. Чужая папка, другой JSON или вариант отклоняются до
открытия базы. Для другого сценария используй другую папку; автоматического сброса
нет. `--scenario /absolute/path.json` позволяет добавить связанные входы и
ожидания.

JSON-вывод содержит конечные ячейки, их presentation, принятые слоты и покрытие,
проверки, счётчики каждого источника, фаз и размер состояния. `payload_json_bytes`
считает компактный UTF-8 JSON на наблюдаемой границе; `request_body_bytes` — тело
HTTP-запроса либо сериализованный запрос Finance transport. Это не сетевой трафик:
заголовки, TLS, ZIP/CSV и браузер сюда не входят. `calls` включает прямую подачу
данных блокам; `pages` — ответы клиентов, включая терминальный ответ Finance 204.
Повторение строк при разных вызовах учитывается повторно. Setup, bootstrap,
adapter_probes и collect_and_publish показаны отдельно. Размер JSON сценария и
сумма размеров файлов базы/состояния — отдельные величины.

Приложение запускается после очистки окружения с тестовым токеном. В этом процессе
audit hook запрещает соединения, DNS, datagram-send и запуск внешних процессов;
непредусмотренные HTTP-запросы не имеют сетевого fallback. Нарушение, даже пойманное
внутри блока, приводит к ошибке всего запуска.

## Ручной интерфейс на Mac

Из корня репозитория подготовьте Python с зависимостями и запустите стенд.
Для постоянных данных укажите один и тот же абсолютный путь. При первом запуске
стенд сам создаёт каталог. Для другого варианта сценария нужен отдельный каталог.

```sh
python3 -m venv .runtime/local-cycle-env
.runtime/local-cycle-env/bin/python -m pip install openpyxl==3.1.5
.runtime/local-cycle-env/bin/python -m apps.local_cycle_lab.local serve --state "$PWD/.runtime/manual-wbc" --port 8765
```

Откройте локальную ссылку, которую напечатает launcher. Она даёт доступ к этой
сессии. Вверху страницы видны метка «ТЕСТ» и дата сценария. На вкладке «Остатки»
откройте «Склады и себестоимость» → «Склад FF» → «Документы фулфилмента».
В разделе «Новое действие» создайте накладной расход и подтвердите его. Штатная
квитанция показывает сумму и состояние операции. Кнопка «Проверить источники
и витрину» запускает сбор и проверку опубликованного Ready. Статус попытки
виден в разделе «Запуски и результаты». Пока идёт проверка, доступны уже открытый
экран и статус запуска. Новые запросы к штатным формам и к источникам снова
разрешаются после завершения. На этом этапе подключены витрина, ручной расход FF
и чтение его квитанции. Остальные разделы оболочки могут показывать сообщение,
что операция ещё не подключена.

Ctrl+C останавливает сервер. Повтор той же команды открывает те же документы
и попытки. Кнопка «Вернуть исходные данные» запрашивает подтверждение, переносит
рабочую базу и попытки в `archives/<поколение>/` и готовит исходное состояние.
Когда сервер остановлен, сброс доступен командой
`.runtime/local-cycle-env/bin/python -m apps.local_cycle_lab.local reset --state ПУТЬ --confirm ID`.
ID берётся из `lab.json`. Исходные данные будут подготовлены при запуске.
Папки интерфейса и CLI источников имеют разное устройство.

Приложение и его дочерний Python работают под профилем macOS sandbox-exec с
отдельным окружением и синтетическими доступами. Сервер слушает 127.0.0.1.
Перед запуском launcher проверяет ограничения чтения, записи, исходящих сокетов
и Mach lookup. Единственный writer удерживает блокировку до выхода приложения.
При сбросе журнал позволяет продолжить прерванный перенос в архив.

Каждая попытка `sources_ready` сохраняет в `runs/<id>/` сценарий, копию входной
SQLite, дату, область, версию кода и результат с контрольными суммами. После
обрыва открытая попытка получает статус `interrupted`. Для следующего ручного
запуска используются текущие сохранённые данные. Восстановление выбранного
этапа из снимка со всеми файловыми входами предстоит реализовать.

## Проверки интерфейса

```sh
python3 -m apps.local_cycle_lab.local_smoke
python3 -m apps.local_cycle_lab.browser_smoke --python .runtime/local-cycle-env/bin/python --output "$PWD/.runtime/lab-acceptance"
```

Первая команда проверяет хранение, блокировку и восстановление сброса и входит
в тесты CI. Для второй нужен Mac с sandbox-exec и Playwright Chromium в среде
проверяющего Python (`python3 -m pip install playwright`, затем
`python3 -m playwright install chromium`). Она открывает отдельный headless
Chromium, создаёт временную базу, проверяет ввод расхода 123,45 ₽, его квитанцию
после перезапуска, повтор подтверждения, ручной этап, остановку supervisor и
сброс. При указании `--output` сохраняет квитанцию, результаты и снимки экрана.

## Контроль расхода в полном цикле на Linux

[Подготовка Linux VM](full_history_setup.md) описывает гостевые диски, systemd, браузер
и изоляцию сети. В подготовленной VM выполните команды из корня рабочей копии на Mac.
Для каждой новой проверки выберите свободное имя каталога в `runs`.

```sh
python3 -m apps.local_cycle_lab.full_history_vm sync
python3 -m apps.local_cycle_lab.full_history_vm run apps.local_cycle_lab.full_cycle --work /var/lib/wbc-lab/runs/expense-01
```

Сценарий импортирует синтетические исторические входы, готовит складской остаток,
вводит один расход FBS 123,45 ₽ через браузер и запускает два ручных цикла на одной
базе. Каждый цикл получает свой ID. В каталоге проверки сохраняются начальный
остаток (`opening.json`), квитанция формы (`before.json`), журналы и квитанции
девяти этапов (`cycle-1.json`, `cycle-2.json`), результаты чтения себестоимости,
витрины и опубликованной истории (`after-1.json`, `after-2.json`). Файл
`comparison.json` создаётся после сверки обоих запусков.

## Повтор отдельного этапа

В подготовленной Linux VM можно отдельно повторить `warehouse` (склад, проводка и
публикация учётной стоимости) или `rolling14` (публикация 14-дневной истории).
Для первого контрольного прогона запустите VM и синхронизируйте текущую рабочую копию.
Команды выполняются на Mac из корня репозитория.

```sh
LIMA_HOME=/tmp/wbc-cycle-lab-stage4 output/stage4-vm/tool/bin/limactl start s4
python3 -m apps.local_cycle_lab.full_history_vm sync
python3 -m apps.local_cycle_lab.stage_vm capture example01
python3 -m apps.local_cycle_lab.stage_vm replay example01 stock01 --stage warehouse
python3 -m apps.local_cycle_lab.stage_vm replay example01 history01 --stage rolling14
```

`capture` вводит один расход через форму и запускает один полный цикл. Непосредственно
перед каждым из двух этапов стенд сохраняет базы SQLite со всеми подтверждёнными
транзакциями, прикреплённые файлы, закрытые резервные копии, каталог History, исходный
сценарий и квитанцию предыдущих этапов. При позднем сбое готовая контрольная точка
доступна сразу после завершения процесса. Для проверки такого случая добавьте к
`capture` параметр `--interrupt-after warehouse` или `--interrupt-after rolling14`.
Команда завершится ошибкой после фактической записи и до подтверждения этапа.

`replay` принимает имя исходного прогона, новое имя попытки и выбранный этап.
После исправления кода снова выполните `full_history_vm sync` и `replay`
с новым именем попытки. Исходная точка подключается только для чтения. На отдельной
копии стенд запускает штатный обработчик в новом рабочем процессе с его собственными
блокировками и квитанцией. Путь к базе, бизнес-дата и условия запуска сохраняются.
Для склада используются те же ответы имитатора. Для истории входом служит
сохранённая публикация Ready. Каждая попытка независима и начинает со своей точки.

Результаты лежат в гостевой VM в `/var/lib/wbc-lab/runs/stage-ИМЯ/control/`.
В `attempt.json` указаны исходный запуск, SHA-256 контрольной точки, версия исполняемого
кода и квитанция единственного этапа. В `result.json` находятся сверка себестоимости,
число проводок, показания витрины и время восстановления вместе с пересчётом.
Для успешного исходного цикла значения дополнительно сравниваются с `after-1.json`.
Проверить результат можно командой

```sh
python3 -m apps.local_cycle_lab.full_history_vm shell sudo cat /var/lib/wbc-lab/runs/stage-history01/control/result.json
```

Для хранения контрольных точек на Mac и переноса в другую подготовленную VM
используйте `save` и `load`. Архив включает входы стадий и доступный результат
полного прогона. Команда `load` требует нового имени. При переносе действуют
исходные проверки диска History, версии формул и бизнес-даты.

```sh
python3 -m apps.local_cycle_lab.stage_vm save example01 expense-checkpoints.tgz
python3 -m apps.local_cycle_lab.stage_vm load imported01 expense-checkpoints.tgz
python3 -m apps.local_cycle_lab.stage_vm replay imported01 restored01 --stage rolling14
```

## Ручной запуск, отказ источника и восстановление после обрыва

На подготовленной Linux VM команда проверяет три случая на отдельных копиях одной
закрытой базы с принятым расходом 123,45 ₽. Внешний сетевой доступ у процессов
WBC закрыт. Сначала подготовь из локального архива ответ WB и выбери новую папку
для результата. Архив состоит из строк JSON с полями `http`, `start`, `end`, `data`.

```sh
python3 -m apps.local_cycle_lab.captured_fullstats /private/input/stats.jsonl /private/input/lab-fullstats.json
python3 -m apps.local_cycle_lab.parity_vm /private/input/lab-fullstats.json /private/output/verification-run
```

Первая команда заменяет идентификаторы кампаний и карточек и названия товаров.
Числовые показатели сохраняются для сверки, поэтому оба файла остаются частными и вне Git.
Вторая команда проверяет один архивный период через штатный HTTP-клиент рекламы, разбор
исторической статистики и агрегацию. По каждой дате и карточке шесть показателей
сверяются с независимой суммой исходных строк. В полном цикле работают отдельные
синтетические источники из карты покрытия.

- Штатный ручной запуск проходит через аутентифицированные GET/POST на loopback и чтение результата по тому же запросу. Профиль выбирается штатным переходом на отдельном пользовательском экземпляре systemd внутри VM. Время и диски принадлежат VM. У таймеров тестовые сервисы, поэтому контроль проверяет ручной запуск.
- В ветке отказа рекламный источник возвращает HTTP 503 за закрытый день. Даже при сохранённом частичном ответе и успешной публикации проверка обычного сценария должна отклонить новый сбой. Для отрицательного контроля отдельно сверяются предупреждения всех девяти этапов и новый тип попытки у одного источника.
- В ветке восстановления процесс завершается перед вызовом обработчика History, после сохранения Ready. Новый процесс на той же базе читает исходный запрос как `interrupted`, проверяет точку обрыва и запускает только History под новой операцией. Утрата владельца в произвольной точке требует отдельной проверки совершённых действий. Исходная квитанция сохраняет статус обрыва. Сверяются журнал расхода, витрина и значения истории за всё окно. Ещё один полный ручной запуск проверяет однократность проводки.
- Итоговая сводка записывается в `verification.json`. Идентификатор каталога VM в поле `guest_suite` ведёт к исходным квитанциям, базе и журналу короткого повтора. Короткий тест политики предупреждений входит в CI. Для полного прогона нужны VM и частный пример ответа.

Для проверки обрыва сразу после склада укажи этап дневной проекции и новый каталог результата.

```sh
python3 -m apps.local_cycle_lab.parity_vm /private/input/lab-fullstats.json /private/output/after-warehouse --interrupt-before daily_projection
```

Процесс сохраняет входы сбора и завершается после записи статуса `running` дневной
проекции, перед вызовом её обработчика. Новый процесс проверяет версию кода, дату,
контрольную сумму файла, исходную квитанцию API, версии данных, проводки и состояние
публикации. Он выполняет четыре штатных обработчика по порядку — `daily_projection`,
`closed_ready`, `final_ready`, `rolling14`. Попытка повторить сбор, финансовую загрузку,
получение FBS или склад прерывает проверку. В сводке сохраняются перечень выполненных
стадий и отпечатки значений всей таблицы Ready, отображаемой витрины и редакции History.
Режим по умолчанию проверяет более поздний обрыв перед одной History. Оба режима
воспроизводят точно известную точку обрыва на одной версии кода и одной рабочей дате.
