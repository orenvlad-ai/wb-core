# Временная чистка данных

Ручная справка WBC для случая, когда нехватка свободного места или обязательного
резерва блокирует работу/выпуск. Собрана в задаче 0110, 26 сентября 2026 года.
Фраза **«используй временную чистку данных»** означает: открыть эту справку,
проверить текущую ситуацию и подготовить подходящую ограниченную операцию.
Она не включает автоматическую очистку и сама по себе не разрешает необратимое
удаление ещё не показанного пользователю набора файлов.

Если пользователь уже согласовал точный набор и условия удаления в текущей
задаче, повторного согласования не нужно. Исторические согласования не переносятся.

## Быстрый выбор

| Где не хватает места | Что проверить первым | Проверенный путь |
| --- | --- | --- |
| Резервный раздел `state/backups` | Идёт ли штатная складская синхронизация и ожидается ли завершение retention | Дождаться результата и прочитать receipt; при необходимости — точный план штатной warehouse retention с сохранением защищённых копий |
| Основной `/` | Размер старых архивных systemd-журналов и необходимость их истории | Ограниченный штатный vacuum архивных журналов |
| Основной `/`, старые запуски Promo | Статус/возраст запусков, отладочные файлы, защищённые Excel/архивы | Точный debug-only план поверх Promo GC |
| Основной `/`, package cache | Проверяемые повторно скачиваемые APT/pip-файлы, отсутствие установки | Точный файловый манифест, а не очистка всего cache |
| Старые временные файлы Promo с доказанными дубликатами | Есть ли нормализованный архив с теми же hashes/данными | Отдельный точный план Promo GC; разрешение только на debug не распространяется на XLSX |
| Старый финансовый резервный набор | Проверена ли новая полноценная копия и её восстановление | Native Finance rotation: новая копия → проверка → переключение → удаление прежней |
| Большие старые копии на `/` | Допустимы ли архивирование и перенос, хватает ли пикового места на целевом разделе | Архив + полное проверочное восстановление + удаление строго исходных файлов |
| Рабочие поколения `state/generations` | Какое поколение активно, какие ещё нужны для восстановления | Универсального успешного рецепта удаления здесь нет; отдельный доменный план |

Удаление на одном разделе не увеличивает доступное место на другом. Не суммировать
свободные байты разных дисков. Не считать новый подключённый диск освобождённым
местом или готовым местом восстановления.

## Общий порядок

1. **Определить точный блокер.** Host, runtime SHA, исходный release/operation ID,
   стадия отказа; раздел, UUID, mount, доступные байты, требуемый резерв и дефицит.
   Отличать физическое заполнение диска от отказа по резерву для следующей операции.
2. **Проверить текущие правила и работу владельца данных.** Прочитать актуальные
   `origin/main`, deployed-код и storage policy. Проверить активные jobs/locks,
   retention и незавершённые recovery. Если штатная работа уже освобождает место,
   не запускать параллельную очистку. Рост free без receipt не доказывает причину.
3. **Составить точный кандидат.** Пути/operation IDs, тип и владелец данных,
   размер, identities/digests, причина допустимости, защищённые объекты,
   отсутствие читателей/писателей и ожидаемый эффект именно на нужном разделе.
   Возраст или слово `backup`, `old`, `temp` в имени сами по себе недостаточны.
4. **Посчитать достаточность.** Свободное место после очистки должно покрывать
   действующий резерв и пик следующего действия: output, временные копии,
   проверочное восстановление, допустимую конкуренцию и рост. Для складской
   ротации учитывать появление следующего checkpoint. Если помогает только
   на короткое время, так и сообщить; не обещать постоянное решение.
5. **Проверить восстановление и согласование.** Для заменяемых копий доказать
   сохранность разрешённых replacement/last-good. Для невосстановимых журналов
   явно указать потерю старой диагностики. Показать пользователю конкретный
   набор/границу, эффект и сохраняемые данные; запросить только отсутствующее
   разрешение. Не создавать дополнительную полную копию без расчёта места.
6. **Один исполнитель, одна операция.** Перед записью повторить проверку цели,
   версии, плана и блокировок. Изменившийся кандидат требует нового preview и
   проверки согласованной границы. Выполнить один submit штатному владельцу
   данных. Не менять лимиты, policy, current pointers или release marker ради PASS.
7. **Прочитать результат.** Receipt/status, точный состав удалённого, отсутствие
   ошибок, сохранность non-target/защищённых объектов, фактическое свободное место
   и здоровье сервисов. Размер файлов и прирост `available_bytes` — разные
   измерения; фоновые записи, hard links и открытые удалённые файлы могут дать
   расхождение. Не называть сумму размеров гарантированным физическим выигрышем.
8. **Проверить исходную цель.** Получить свежий штатный storage status/admission
   и только затем продолжить уже разрешённую работу. Очистка и завершённый выпуск
   — разные результаты. Для выпуска нужен связанный receipt с
   `deployment_complete=true`, а не только Git merge или marker SHA.

При сетевой неопределённости не повторять удаление: читать состояние той же
операции. Resume допустим только по явно поддержанному контракту и после
разрешения неопределённости; новый operation ID не является способом повторить
старую запись.

## Диагностика без записи

На подтверждённом production-host прочитать `findmnt`/`df -B1` для `/`,
`/opt/wb-core-runtime/state/backups` и `.../generations`, runtime marker,
`storage_generation_manifest.json` и действующий policy. Проверить inode capacity.
Сначала использовать существующий storage status с проверкой его времени;
устаревший снимок не считать допуском.

Код диагностики: [root_storage_policy.py](../../apps/root_storage_policy.py),
[storage_registry.py](../../packages/application/storage_registry.py),
[policy](../../artifacts/registry_upload_http_entrypoint/root_storage_policy_v1.json).
`status` без `--output` выводит новый расчёт; `--output` записывает артефакт,
поэтому не относится к строго read-only этапу. Возврат 0 от `status` сам по себе
не доказывает отсутствие alerts: читать поля результата и штатный admission.
`status-readback` проверяет сохранённый артефакт, включая свежесть.

В проверенном policy на дату справки root normal reserve — 25 GiB,
reserve generation — 8 GiB, backup — расчёт следующей Finance replacement плюс
аварийный резерв 4 GiB. Это разные правила; backup не равен фиксированным 45 GB.
Перед применением перечитать фактическую конфигурацию, а не копировать эти числа.

SQLite открывать только через канонический StoreRegistry/manifest с `mode=ro`
и `PRAGMA query_only=ON`. Не запускать инструмент с `ensure_schema()` как
диагностику. Отсутствующий файл/доступ не считать пустой базой.

## Складские контрольные копии на резервном диске

Метод №95 и автоматические повторения №72К2:

- через [StoreRegistry](../../packages/application/storage_registry.py) разрешить
  активную `operational` БД; проверить manifest, runtime/schema и файлы;
- получить `WarehouseRecoveryRegistry.plan_retention()` из
  [warehouse_recovery_policy.py](../../packages/application/warehouse_recovery_policy.py)
  для явно заданной активной БД, проверить отсутствие побочных записей;
- использовать только допустимые registry-кандидаты, сохранив protected set,
  last-good, незавершённые/failed/quarantined/rollback-required операции;
- проверить сами сохраняемые копии по размерам/digests и статусу verified;
- при ручном apply удерживать и job lock, и warehouse write lock, повторить
  точный fingerprint/состав/размеры, затем `apply_retention()` один раз;
- сверить receipt, lifecycle/отсутствие только согласованных файлов,
  защищённые копии и новый native plan/status.

**Ловушка:** на baseline `36086bdb` CLI
[warehouse_recovery_retention.py](../../apps/warehouse_recovery_retention.py)
конструирует `runtime_dir / DB_FILENAME`, а не выбирает active split operational
через StoreRegistry. Его нельзя слепо запускать даже с названием `dry-run` или
`status`. В №63 ошибочный apply затронул schema неактивного monolith и остановился
на stale fingerprint; №95 использовал отдельно проверенную точную обвязку.
Перед будущим применением проверить, исправлен ли CLI. Историческую обвязку
с зашитыми SHA/ID/fingerprint повторно не запускать.

Минимум две T2-копии в описанных warehouse-кейсах — правило этого домена.
Оно не переносится на Finance, где иной lifecycle. Не удалять вторую защищённую
копию ради большего запаса. Если кандидатов нет, это не разрешает ручной `rm`.

## Архивные systemd-журналы на основном диске

Исторически №61 / №33К2 использовали единственный вызов
`journalctl --directory=/var/log/journal --vacuum-size=1G` после согласования.
Это пример конкретной операции, **не команда к немедленному исполнению**.

Перед новым vacuum: подтвердить раздел, `journalctl --disk-usage`, нужный период
диагностики, текущие расследования и состояние служб. Согласовать объём/период
невосстановимой потери. Native vacuum удаляет архивные журналы; не добавлять
`--rotate`, restart, truncation других логов или изменение journald-конфига.
После — native output, disk usage, `df`, прежние/новые failed units и основные
службы. Активные журналы могут оставлять usage выше заданного размера.

В №106 свежая история ошибок была нужна, поэтому журналы не выбрали для чистки.
Наличие успешного vacuum раньше не делает его лучшим вариантом всегда.

## Старые отладочные файлы Promo на основном диске

Код: [promo_campaign_archive_gc.py](../../apps/promo_campaign_archive_gc.py).
№106 использовал узкий subset поверх штатного `apply_exact_gc_plan()`:
только debug traces завершённых `success` старше 7 дней и `partial` старше
14 дней. Срок проверялся по самому свежему файлу запуска, а не имени каталога.

Generic GC умеет также удалять доказанные дубликаты XLSX. Это **другая граница**:
debug-only разрешение не допускает их включение. Для повтора нужны точный
subset/fingerprint, deployed SHA, regular-file/device/inode/mtime/size/SHA
проверки, отсутствие symlink/hardlink и активных пользователей файлов.
Сохранить `run_summary`, metadata, нормализованный архив, все Excel и неизвестные
статусы. Сверить non-target digest до/после и терминальный audit `applied`.

В №69К15 другой согласованный план обработал 10 080 временных файлов
`promo_xlsx_collector_runs`, сохранив нормализованный архив и non-target digest.
Если план включает дубликат workbook, требуется совпадение hash с сохранённым
архивом и доказательство normalized rows, а не только расширение или возраст.

Скрипт №106 с конкретными лимитами и SHA — исторический адаптер, не универсальный
план. В новом запуске подготовить и проверить свежую обвязку в разрешённой
границе; не расширять кандидат до всего каталога или всего generic GC.

## Финансовые материалы, cache и архивирование

Финансовая чистка — не удаление счетов, проводок, документов, raw-источника или
активной БД. Подтверждённый финансовый случай — замена резервного restore set.
10 080 временных файлов в №69К15 относились к Promo, а не к Finance. Подробные подтверждённые случаи и ограничения —
в [реестре прецедентов](temporary_data_cleanup_cases.md).

Native Finance rotation реализована в
[finance_storage_backup_rotation.py](../../packages/application/finance_storage_backup_rotation.py)
и [CLI](../../apps/finance_storage_backup_rotation.py). Сначала требуется место
на сосуществование incumbent и candidate. Новая копия `finance_raw` и
`operational` проходит integrity/FK/logical/checksum и isolated restore;
только затем штатное переключение current и lifecycle удаления старого набора.
Удалить last-good сначала, чтобы хватило на новую копию, запрещено.
Ротация может не давать чистой экономии: новая копия иногда больше старой.

Cache-кандидат требует проверки воспроизводимости из источника, точного
манифеста и отсутствия APT/pip writers/open references. Browser profiles,
авторизация сборщиков, неизвестные `/tmp` и весь cache целиком сюда не входят.

Архивирование больших копий требует отдельного бюджета source + archive +
restore, manifest/checksum, полного restore и проверки SQLite, проверки
неизменности исходника непосредственно перед unlink и durable intent для
разрешения прерывания. «Сжатый файл появился» не является доказательством
восстановимости. Исторические удалённые из main утилиты не восстанавливать и
не запускать автоматически ради повторения старой команды.

В №8 также удаляли два доказанно выведенных из эксплуатации дерева DCP,
сохранив холодный архив и проверив отсутствие зависимостей. Это разовый случай,
не разрешение считать любой отключённый сервис или его backup ненужным.

## Когда остановиться

Нет проверенного кандидата/сохраняемой копии; неизвестно назначение файла;
не совпали host/mount/manifest/версия/fingerprint; есть активный конфликт;
не хватает пикового бюджета; отсутствует нужное согласование необратимой потери;
есть partial/unknown результат. Зафиксировать конкретную причину. Не обходить
резерв, не форматировать неизвестный диск, не стирать evidence или бухгалтерские
данные и не выдавать отсутствие данных за ноль.

Если reserve пройден, но следующий штатный checkpoint снова его нарушит,
разовая очистка закрывает только текущий дефицит. Изменение ёмкости, политики
хранения или размера копий — отдельная задача, не скрытая часть этой процедуры.

> Размер обработанных файлов [байты], фактическое доступное место [до → после].
> [Защищённые данные] сохранены; текущий резерв/пик [проходит или причина отказа].
> Исходная операция [завершена с подтверждением / осталась конкретная стадия].

Для восстановления прерванного выпуска следовать
[актуальному Release Recovery](../architecture/11_github_release_train.md#завершение-прерванного-выпуска-после-merge).
Fingerprint retention не является fingerprint восстановления выпуска.
