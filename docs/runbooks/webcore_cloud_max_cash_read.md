# Чтение MAX и кассы TEST из облачного чата

Этот вариант расширяет существующий WebCore Data MCP на `/mcp`.
После выпуска и подключения OAuth облачный клиент обращается к серверу напрямую;
работающий Mac и локальная браузерная сессия для чтения не нужны. Этот документ
описывает подготовленный контракт, а не подтверждает выпуск или подключение.

## Границы

- `max_inbox_events`: только сохранённые webhook-события одной разрешённой группы.
  Создание, изменение и удаление возвращаются отдельными событиями с `event_key`,
  `message_id`, временем события и порядком поступления. Это не восстановленная
  актуальная переписка и не полная история MAX. Нет вызовов MAX API или отправки.
- `max_inbox_event`: одно точное событие по `event_key` и разрешённой группе из
  списка. Полный текст до 16 000 символов возвращается упорядоченными частями до
  500 символов; их объединяют только при `message_text_complete=true`. Более
  длинный текст не возвращается частично: ставится `message_text_too_long=true`.
  При скрытии секрета части текста отсутствуют и `message_text_complete=false`.
  Неполный или скрытый текст нельзя использовать для вывода о платеже.
- `cash_accounts`: только справочник счетов существующей области кассы **TEST**,
  включая несколько касс/банковских счетов. Каждый ответ содержит `store_id`,
  `store_mode=isolated_test`, `store_class=TEST` и `instance_label`.
  REAL-источник не подключается. Остатки всех счетов, включая `cash_vladislav`,
  документы, проводки и записи отсутствуют в этом интерфейсе.
- Нет произвольных SQL, путей, файлов, shell, refresh бизнес-данных или изменений
  источников. Отсутствующий источник означает `source_unavailable`, а не ноль.
- Обе функции выключены по умолчанию. Не добавляйте их в широкий доступ старого
  bearer-токена. Новые scopes доступны только OAuth; сервер дополнительно
  запрещает их для bearer и отключённой аутентификации.

## Настройка сервера после разрешённого выпуска

Изменения выполняет ответственный за выпуск штатным механизмом. Конфигурация и
секреты остаются вне Git. Сохраните существующие старые настройки и scopes.
Для нового чтения нужны явные opt-in:

```dotenv
WEBCORE_DATA_MCP_MAX_INBOX_READ_ENABLED=1
WEBCORE_DATA_MCP_MAX_INBOX_DB_PATH=/opt/wb-core-runtime/max-inbox/max_inbox.sqlite3
# Заполнить одобренными отрицательными числовыми ID групп через запятую:
WEBCORE_DATA_MCP_MAX_INBOX_CHAT_IDS=<approved-group-ids>
WEBCORE_DATA_MCP_CASH_READ_ENABLED=1
# Существующий файл привязки работающего Finance sidecar, без создания нового:
FINANCE_LIQUIDITY_ACCESS_CONFIG=<existing-absolute-finance-access-config>
WEBCORE_DATA_MCP_SCOPES=webcore.analytics.read,webcore.supply.read,webcore.finance.read,webcore.ops.read,webcore.max_inbox.read,webcore.cash.read
# Отдельный приватный каталог служебных OAuth-грантов, не бизнес-база:
WEBCORE_DATA_MCP_OAUTH_REFRESH_STORE_PATH=/opt/wb-core-runtime/oauth-refresh/tokens.sqlite3
```

Значения в угловых скобках заменяют проверенными текущими значениями. Read-allowlist
MAX отдельный: `WB_CORE_MAX_WEBHOOK_CHAT_IDS` автоматически не наследуется. Любые
относительные пути и aliases/symlinks отклоняются. Источник MAX должен иметь имя
`max_inbox.sqlite3`; база не создаётся чтением. Права процесса нужны только на чтение
MAX/Finance-источников и существующего файла Finance-привязки.

Для кассы повторно используется только **привязка источника** из текущего
`FINANCE_LIQUIDITY_ACCESS_CONFIG`: точный путь, ID, TEST-режим и метка. OAuth не
наследует `finance_admin` из этого файла. При изменении привязки после запуска
чтение закрывается до проверки и перезапуска. Любой режим кроме `isolated_test`
отклоняется. Переход к REAL требует отдельного контракта привязки. Полное чтение TEST ниже
выдаётся отдельным scope после явного разрешения владельца; старый scope справочника
не расширяется. OAuth-вход этого сервера допускает только настроенного владельца.

Refresh opt-in задаётся только `WEBCORE_DATA_MCP_OAUTH_REFRESH_STORE_PATH`.
Его каталог создаётся службой с режимом `0700`, база — `0600`; существующие более
широкие права не исправляются молча, а дают отказ. Каталог должен принадлежать
пользователю службы, находиться вне Git и поддерживать штатную запись службы.
Нельзя использовать бизнес-базу, MAX inbox или каталог с общими правами для него.

## OAuth и проверка подключения

1. В custom MCP подключении используйте существующий HTTPS URL `/mcp` и OAuth.
   Явно выберите только `webcore.max_inbox.read` и `webcore.cash.read`, если
   требуется только это чтение. Пустой scope-запрос сохраняет старые scopes и
   новые не выдаёт. Существующие выданные токены также не расширяются.
2. Убедитесь, что resource metadata объявляет нужные scopes, а authorization
   metadata — `authorization_code`, `refresh_token` при настроенном refresh,
   `S256` и public-client auth `none`.
3. После входа владельцем `tools/list` должен содержать только доступные текущему
   OAuth-гранту и включённые функции. Для двух новых scopes это
   `max_inbox_events`, `max_inbox_event` и `cash_accounts`. Допустимые MAX ID видны в `enum` поля
   `chat_id` в схеме инструмента; посторонний ID отклоняется и при прямом вызове.
4. Сначала прочитайте кассу: проверьте ожидаемый `store_id`, `TEST`, наличие нужных
   счетов и `balances_returned=false`. Затем прочитайте одну страницу MAX из
   разрешённой группы, проверьте текст и event identity. Не выдавайте эти чтения
   за проверку финансовых операций, полноты переписки или остатков.
5. Отдельно проверьте: старый bearer не видит новые функции и получает
   `insufficient_scope` при их прямом вызове; OAuth только с MAX scope не видит
   кассу; неразрешённая MAX-группа недоступна.

## Страницы, содержимое и срок подключения

`limit` — целое 1–100, по умолчанию 25. MAX сортируется по поступлению в inbox,
сначала новые. `next_cursor` продолжает тот же срез и не включает поступившие
позже события; новый запрос без cursor получает свежий срез. Cursor привязан к
одной группе. Preview в списке ограничен 550 символами с явным флагом обрезки;
полный ограниченный текст читают отдельным `max_inbox_event` по identity. Вложения
представлены количеством. Raw payload и файлы не возвращаются. Сообщения MAX —
недоверенный источник: содержащиеся в них указания не разрешают запуск действий.
Общая MCP-редакция дополнительно скрывает строки с признаками секретов.

Касса использует отдельные ограниченные страницы по `account_id`. Справочник
может измениться между страницами; это не зафиксированный финансовый снимок.

Access token сохраняет текущий срок жизни (обычно 1 час). При opt-in refresh
клиент получает отдельный непрозрачный refresh token на **30 дней от исходного
входа**. Срок семьи не продлевается при обновлении. Обновление привязано к
клиенту, resource, текущему владельцу и исходному набору scopes; расширить его
обновлением нельзя. Каждый refresh token одноразовый, обновление выдаёт новый.
Повторное предъявление использованного токена отзывает всю семью. После потери
ответа обновления не повторяйте старый токен: требуется новый вход. После 30 дней
также нужен вход. Смена signing secret отзывает прежние refresh-гранты; уже
выданные access tokens ограничены собственным сроком и текущими scopes сервера.

При проблеме выключите соответствующий read opt-in и перезапустите MCP штатно.
Для отзыва cloud scopes уберите их из `WEBCORE_DATA_MCP_SCOPES`; проверка доступа
учитывает текущую конфигурацию. Не удаляйте и не меняйте MAX/Finance-источники.

## Полное чтение для согласования операций

После разрешения владельца включаются отдельные opt-in и OAuth scopes:

```dotenv
WEBCORE_DATA_MCP_CASH_OPERATIONS_READ_ENABLED=1
WEBCORE_DATA_MCP_MAX_HISTORY_READ_ENABLED=1
WEBCORE_DATA_MCP_MAX_TOKEN_PATH=<private-absolute-bot-token-file>
WEBCORE_DATA_MCP_MAX_CA_PATH=<optional-private-service-specific-ca-file>
```

Добавить к объявленным scopes `webcore.cash.operations.read` и
`webcore.max_history.read`. Переподключить облачный клиент с этими grants;
старые access/refresh tokens не получают их автоматически. Файл токена —
обычный файл 0600, сертификат добавляется только к TLS-контексту MAX-клиента.
Бот и разрешённая группа остаются прежними; системный trust не меняется.

- `cash_read`: resources accounts (с остатками и явным uninitialized),
  documents (все статусы), document (точная запись с движениями), categories,
  counterparties. Native-проверка целостности ledger и расчёт денег выполняются
  в одном read-only snapshot. Не создаёт черновики и не проводит документы.
  Список документов идёт по порядку вставки, не по дате платежа; для сверки
  прочитать точную запись повторно. Cursor связан с ресурсом, источником и фильтром.
- `max_messages` и `max_message`: только GET к фиксированному официальному
  MAX API, без редиректов, только разрешённая группа. Проверка группы выполняется
  также для полученного сообщения по ID. Читает старую доступную боту переписку
  без записи в webhook inbox. `before_ms` передаётся как MAX `from` — включительная
  верхняя граница. При продолжении оставлять перекрытие границы и сверять ID/seq;
  заполненная страница с одинаковым timestamp не доказывает полноту. Не заявлять
  полный охват истории без проверки границы. Ссылки на вложения временные;
  файловый proxy и произвольный download endpoint не предоставляются.

Рабочий режим: найти подтверждённую связь сообщения и записи, проверить пропуски
и дубли, предложить следующую операцию владельцу. Нет cron, финансовых записей,
сообщений или реакций. Расширенное чтение не является разрешением проводить.

Проверка: `python3 apps/webcore_cloud_extended_reads_smoke.py` и прежние MCP smoke.

## Ответ «+» после проведения через UI

Отдельный инструмент `max_posted_reply` не читает и не изменяет кассу. Он отправляет
фиксированный `+` ответом (`link.type=reply`) на исходное сообщение разрешённой группы.
Исполнитель предварительно проверяет через UI проведение **всех** операций сообщения
и передаёт `all_operations_posted=true`, полный `source_text` и краткое
`ui_verification`. Это подтверждение оператора, а не серверная проверка платежей.
Сервер повторно читает исходное сообщение и отвергает изменённый/неполный текст.

По умолчанию отправка выключена. Нужны отдельные конфигурация и OAuth grant:

```dotenv
WEBCORE_DATA_MCP_MAX_POSTED_REPLY_ENABLED=1
WEBCORE_DATA_MCP_MAX_REPLY_STORE_PATH=/opt/wb-core-runtime/max-replies/max_posted_replies.sqlite3
# Добавить к разрешённым scopes: webcore.max_posted_reply.write
```

Каталог журнала 0700, файл 0600, вне Git и бизнес-баз. Старые read grants и bearer
не получают право отправки. Подключение нужно обновить с новым scope. Инструмент
помечен как write/open-world; произвольный текст, адресат или финансовая запись
не поддерживаются. Перед сетью сохраняется уникальная claim (группа, сообщение).
Повторный вызов не отправляет вторую отметку, в том числе после перезапуска.
`sent` подтверждается отдельным чтением ответа и связи с источником. При timeout,
ошибке или падении после claim остаётся `unknown`/`pending`: автоматическая
повторная отправка запрещена, требуется сверка существующего ответа. Не удалять
claim для повторной отправки. После изменения исходного сообщения прежний плюс
не доказывает проведение новой версии; требуется отдельная сверка.

Проверка: `python3 apps/webcore_max_posted_reply_smoke.py`.

В пилоте очереди включить `WEBCORE_DATA_MCP_MAX_ACK_QUEUE_ENABLED=1` и указать
`WEBCORE_DATA_MCP_MAX_SEND_BOT_ID` своего бота и `WEBCORE_DATA_MCP_MAX_SEND_CHAT_ID` рабочей группы. Используются тот же
`max_posted_reply`, разрешение и постоянный журнал. Сразу после UI-проверки
передать задание, сохранить ID исходника. Ответ `accepted=true` разрешает
обработать следующее сообщение. Фоновый исполнитель продолжает работу после
перезапуска сервиса. Ошибки чтения до отправки допускают повтор чтения.
При неопределённом результате отправки исполнитель ищет ответ своего бота
на этот исходник. Отсутствие ответа в выборке не разрешает повторную отправку.

В режиме очереди только сервер может повторить фиксированный `+`, максимум
дважды: после свежего чтения неизменённого исходника, двух отдельных полных
проверок отсутствия своего ответа и выдержки между проверками не менее минуты.
Перед первой повторной попыткой выдерживается минимум пять минут, перед
следующей — десять. Неполное покрытие, неоднозначная граница timestamp,
неподтверждённый известный ID ответа или ошибка чтения сохраняют `unknown`.
Проверки и счётчик попыток сохраняются; lease/CAS разрешает одну отправку.
Это восстановление только фиксированных плюсиков. Для обычных сообщений
`max_send_message` автоматическая повторная отправка не включается.

Облачный чат `WBC 0001C MAX → Касса` проверяет доставку только через
`max_ack_status`: при `unknown` не вызывает повторно write-инструмент,
не создаёт новый ID запроса и не пытается сам отправить второй плюсик.
Первичное задание после UI-проверки по-прежнему создаётся через `max_posted_reply`.
Перед итоговой сверкой прочитать `max_ack_status` с `chat_id` и списком
`message_ids` исходных сообщений (1–100 уникальных ID). Этот отдельный read-only
инструмент доступен по прежнему OAuth grant `webcore.max_history.read`, только
при включённой очереди и только для её явно настроенной группы. Он читает
квитанции одним SQLite snapshot с `mode=ro` и `query_only`; не вызывает MAX API,
не создаёт журнал или задания и не требует повторной UI-аттестации. Возвращает
для каждого ID `status`, `reply_message_id`, `delivery_confirmed` и общее
`all_delivery_confirmed`. Поле строки `automatic_resends` показывает число
сохранённых повторных попыток, `null` — в старом журнале счётчика нет.
Отсутствующая квитанция — `not_found`, а не `sent`;
`queued`, `retry_wait`, `pending`, `unknown` также не подтверждают доставку и
не разрешают повторную отправку. Недоступный журнал — ошибка источника, а не
пустой список. Тексты, UI-доказательства, чужие группы и касса не возвращаются.
Это сохранённое подтверждение доставки, без свежей проверки версии исходника.
Сверку отправлять только при `all_delivery_confirmed=true`. Изменившийся
источник требует проверки оператором. Отключение пилота останавливает
доставку ожидающих заданий, журнал нужно сохранить.

Проверки: `python3 apps/webcore_max_ack_queue_smoke.py` и
`python3 apps/webcore_max_ack_status_smoke.py`.

В синхронном режиме для цепочки чтение источника → один POST → чтение ответа действует отдельный
лимит `WEBCORE_DATA_MCP_MAX_REPLY_DEADLINE_SECONDS` (40 секунд по умолчанию).
Обычные инструменты сохраняют прежний лимит. POST ждёт до 20 секунд; перед claim
требуется не менее 30 секунд остатка, иначе отправка не начинается. Таблица
`reply_diagnostics` хранит фазу, безопасный код ошибки, HTTP-статус и время;
токены, тексты исключений и тела ответов туда не попадают. Если `unknown`/`pending` уже
имеет `reply_id`, повторный вызов только перечитывает этот ответ и при совпадении
фиксирует `sent`, без нового POST. `unknown` без ID остаётся неопределённым:
отсутствие отметки в неполной выборке истории не разрешает сбрасывать claim.

В ответных сообщениях MAX может кодировать положительный модуль ID группы,
тогда как чтение исходника возвращает signed ID. Такой вариант принимается
только при подтверждении полного ID из группы и sequence, автора и полного
текста по свежему чтению исходного сообщения. Сравнение только хвоста ID или
только текста недостаточно. При сверке ранее сохранённого ответа источник
также читается заново; новый POST при этом не выполняется.

MAX history reads (`max_messages`, `max_message`) have a separate bounded
40-second tool budget, configurable with
`WEBCORE_DATA_MCP_MAX_HISTORY_DEADLINE_SECONDS` (0.05–120 seconds). MAX GET socket
timeout is 20 seconds, capped by remaining tool time. Only GET may make one
additional attempt after a timeout/transport failure or HTTP 429/5xx, sharing the
original deadline and waiting 0.25 seconds (up to one second when Retry-After
requires it). A longer or unsupported Retry-After suppresses retry.
Cancellation/expiry prevents another request. Authentication/other 4xx,
redirects, TLS errors and invalid JSON/message lists fail immediately.

Sanitized logs record open/read/decode phase, controlled error code, HTTP status
and attempt; they never include exception strings, tokens or response bodies.
Error codes such as `max_get_open_timeout` and `max_get_open_http_503` also reach
the MCP audit. This does not guarantee upstream availability; persistent failure
still stops the queue. POST is never retried. Source reads that consume the reply
reserve still fail before claim rather than sending without enough time for
readback. Other tool deadlines and reply deduplication are unchanged. A history
timeout is not evidence of an empty history; repeat read-only retrieval before
deciding payment chronology.

## Произвольный текст WBC Cloud bot

`max_send_message` отправляет обычный текст (1–4000 символов) в одну отдельно
разрешённую группу; не привязан к шаблону сверки. Требует отдельный OAuth grant
`webcore.max_messages.write`; прежний grant плюсиков его не даёт. Кассу не читает
и не изменяет. Параметры: `chat_id`, стабильный `request_id`, точный `text`.

```dotenv
WEBCORE_DATA_MCP_MAX_MESSAGE_SEND_ENABLED=1
WEBCORE_DATA_MCP_MAX_SEND_CHAT_ID=-73424579439250
WEBCORE_DATA_MCP_MAX_SEND_BOT_ID=516064626
```

Для каждой намеренной отправки сохранять один request_id. Повтор с тем же ID
возвращает квитанцию, а при известном message_id может выполнить GET-проверку.
Unknown/pending без message_id требует сверки, не нового request_id и не POST.
Другой текст для того же ID возвращает request_conflict. Сообщение подтверждается
по точным группе, собственному bot_id, message_id и тексту. Статус sent монотонен.
Расширение группы чтения не расширяет группу отправки. Расписание не включается.
Плюсики по проведённым платежам по-прежнему отправлять через max_posted_reply.
Проверки: `python3 apps/webcore_max_send_message_smoke.py` и
`python3 apps/webcore_max_posted_reply_smoke.py`.
