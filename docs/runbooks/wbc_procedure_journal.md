# Журнал процедур WBC

На Linux приложение пишет структурированные события в systemd-journald с идентификатором `wbc-procedure`. Такой же транспорт работает на изолированном стенде. Включение по умолчанию. Для сравнительного прогона одной службы можно передать ей `WBC_PROCEDURE_LOG=0`. Срок хранения и ротацию задаёт конфигурация journald на конкретном узле.

## Разбор запуска

Посмотреть события выбранной службы за нужное время можно командой

```sh
journalctl -u "$unit" -t wbc-procedure --since "$since" -o cat
```

По идентификатору цикла можно получить его этапы и работу History, включая события из другого процесса.

```sh
journalctl -t wbc-procedure --since "$since" -o cat |
  jq -c --arg id "$cycle_id" 'select(.cycle_id == $id)'
```

По полю `trace` из любого из этих событий можно получить также родительский HTTP-запрос и фоновое задание. `span` и `parent` связывают вложенные вызовы. Независимый системный запуск получает собственный trace. PID в JSON относится к исполняющей процедуре. Процесс с фиксированными аргументами передаёт записи в journald, поскольку система автоматически добавляет командную строку отправителя. В JSON попадают время, идентификаторы, имена из кода, коды состояния, счётчики и SHA версии при наличии штатного маркера. Для исключения сохраняются категория и строка кода приложения, если она доступна.

## Что искать при сбое

- Для CLI видны вход и штатный код выхода. Для HTTP видны метод, имя маршрута и код ответа. Принятое фоновое задание имеет отдельный результат. `returned` означает, что вызов вернул управление.
- Для цикла записываются начало и длительность каждого этапа, предупреждения по источникам, фазы склада. Терминальное событие успешно завершённого этапа следует за записью штатной квитанции.
- В History можно сопоставить бюджет и исход обмена с дочерним процессом, код выхода, отправку SIGKILL при принудительном завершении, дату расчёта, запись промежуточного результата и последующее подтверждение при чтении. При сохранённой диагностике неудачного цикла `history_failure` содержит проверенный код причины из штатной квитанции.
- Для ручных операций на внутренних данных доступны HTTP-вызов, задание или команда, которые действительно исполнились. В общей записи HTTP 200 или коде выхода CLI может отсутствовать предметный исход, например результат сверки документа. Его подтверждают штатная квитанция и чтение данных по идентификатору операции.

Если процесс внезапно завершился, в журнале может остаться только начало этапа. Медленный или недоступный сборщик может потерять записи. При следующей успешной отправке тот же отправитель указывает количество обнаруженных пропусков в `dropped_before`. При разборе неопределённого исхода сначала прочитайте квитанцию и опубликованные данные исходной операции. Полная редакция History подтверждается чтением опубликованного CURRENT и его доказательств.
