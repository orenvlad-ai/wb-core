# Чаты и возвраты: наблюдение без отправки

Первый срез WBC 0115 хранит чаты, события, покупки и заявки в отдельном
`<runtime-dir>/buyer-support/observation.sqlite3`. Автоматические действия
отключены: нет отправки сообщений, решений по заявкам, LLM и планировщика.
Правила ответов на отзывы не изменены.

## Экран и права

Раздел «Чаты и возвраты» входит в существующую WebCore-страницу; прямая ссылка
использует `?tab=buyer-support`. Права совпадают с разделом «Отзывы».
`WB_BUYER_SUPPORT_CABINET_ID` задаёт единственный кабинет серверной проекции.
Штатный `wb-core-registry-http.service` использует `seller-portal-primary`,
совпадающий с существующим account scope реестра изменений; это не секрет.
Без настройки экран сообщает, что кабинет не настроен. Клиентский параметр
кабинета не принимается. Для нескольких кабинетов пока нет переключателя или
отдельной ACL-модели; нельзя направлять один пользовательский контекст на
чужой кабинет.

Защищённые GET:

- `/v1/sheet-vitrina-v1/feedbacks/buyer-support/list`: `q`, `filter`, `offset`,
  `limit` (1–100), `period=90d|30d|all` (90 дней по умолчанию); фильтры `all/active/archive/orphan/unlinked/ambiguous`.
- `/v1/sheet-vitrina-v1/feedbacks/buyer-support/detail`: `kind=chat|claim`, `id`.

Период списка ограничивает чаты по времени последнего сообщения (`addTimestamp`),
а не по дате создания чата. Выбранная переписка показывается целиком, включая
сообщения до начала периода и исторические ответы продавца/менеджеров.
У независимых заявок без чата нет подтверждённой часовой зоны, поэтому они
остаются видимыми при любом периоде. Чаты без сообщений доступны в режиме
всей сохранённой истории; число таких чатов возвращается в метаданных.

Ответ списка содержит `history`: состояние загрузки сообщений, число событий
и чатов, диапазон исходных времён сообщений и время сохранения последних
полученных событий (`MAX(seen_at)`, в интерфейсе «Данные сохранены»). Пустой
опрос и ошибка не заменяют эту дату; без сохранённых событий она неизвестна. Диапазон описывает доступную локальную историю, без гарантии полноты
90 дней у внешнего API. Пустая выборка при частичной/ошибочной загрузке отличается
от отсутствия обращений в загруженной истории.

Чтение открывает SQLite в `mode=ro` с `query_only=ON`, не создаёт хранилище и
не вызывает WB. Ответ содержит только явную проекцию; исходные payload и
подписи в JSON/интерфейс не попадают. Номер и коды состояния WB доступны в
подробностях, без предположений об одобрении/отказе по неизвестному коду.

## Контролируемая загрузка

Перед запуском оператор обязан сопоставить кабинет с токеном выбранной
переменной окружения и подтвердить тип токена/доступные квоты. Идентификатор
кабинета — доверенная настройка локального пространства данных, не извлечённый
из API факт. Утилита не проверяет владельца токена отдельным endpoint.
Секрет передаётся только через существующую runtime-переменную окружения;
значение никогда не указывается в аргументах или квитанции.

Пример формы вызова (подставить реальные локальные пути и кабинет):

```sh
python3 apps/wb_buyer_support_sync.py \
  --runtime-dir /path/to/runtime \
  --cabinet CABINET_ID \
  --token-env-var WB_API_TOKEN \
  --token-rate-class personal-service
```

`--token-rate-class` обязателен: `personal-service` использует паузу 3.1 секунды
между GET, `base` — 3601 секунду. Это консервативная настройка первого среза,
не автоматическое определение рабочего типа токена. Вызов выполняется один
раз и завершается. Штатный `guard_cli` проверяет maintenance barrier до
создания read model или обращения к WB и удерживает admission lease на весь
запуск. При активном барьере результат — `skipped_maintenance`, без записи
данных и внешних запросов. Нет автоматического повтора после 429/401/403, расписания
или фонового возобновления. Ошибка имеет безопасный код без тела ответа WB.
Продолжение после устранения причины — отдельный операторский вызов.

Утилита запрашивает только официальные GET seller/chats, seller/events и
claims у фиксированных российских WB-хостов. Перенаправления запрещены, чтобы
Authorization не ушёл на иной адрес. Зафиксированные разрешения API:
[общение с покупателями](https://dev.wildberries.ru/news/278),
[отдельный контракт заявок](https://dev.wildberries.ru/news/146).
Загрузка файлов/изображений ещё не подключена; экран показывает число материалов.

## Гарантии и ограничения данных

Каждая страница событий сначала полностью проверяется, затем события и
курсор сохраняются одной транзакцией. Повторные eventID дедуплицируются;
конфликт содержимого того же eventID останавливает загрузку. CAS курсора и
локальная блокировка исключают конкурирующую загрузку. Уже сохранённая
история не удаляется при следующем скане или сбое.

Активные и архивные заявки читаются отдельно через limit/offset. Страница
сохраняется целиком, повторы идентификаторов/пустая незавершённая страница
останавливают скан с ошибкой. Исчезновение из списка никогда не меняет заявку
на завершённую; архив подтверждается только полученным архивным снимком.
Полный offset-скан отражает ограниченное движущееся окно WB, не полную историю
за произвольный период. Часовая зона `dt/dt_update` и точный deadline неизвестны;
дедлайн не рассчитывается.

Покупки ограничены кабинетом. Заявка связывается только через точное `srid=rid`
из исходного goodCard чата/события. Конфликт товара или несколько подходящих
чатов сохраняют `ambiguous`. Заявка с srid без чата — `orphan`; без srid —
`unlinked`. Подтверждённая связь не удаляет исходную независимую историю заявки.

В одном чате могут быть разные покупки. Отсутствие inline goodCard у сообщения
не приписывает ему последнюю покупку. Если пока наблюдается одна покупка,
`observed_single_purchase/candidate_rid` остаётся неподтверждённым кандидатом;
при нескольких покупках сообщение имеет `ambiguous`, без покупки — `unlinked`.
Изменившиеся товарные сведения одного источника сохраняют конфликт вместо
молчаливого отбрасывания нового факта.

## Локальная проверка

`python3 apps/wb_buyer_support_smoke.py` использует только синтетические данные:
период по последнему сообщению, полный ранний контекст и история продавца,
транзакции, курсор, дедупликация, pagination, кабинет, неоднозначность, ACL,
недоступность POST, безопасные ошибки и XSS. При наличии штатного Playwright
выполняется Chromium-проверка полной страницы, прямой ссылки, перезагрузки и
ошибки чтения. Реальные данные, токены и выгрузки в Git не включаются.
