# Восстановление дневных метрик бота

Механизм исправляет подтверждённые дневные данные поиска и воронки. Он не
меняет расписание сбора, состав товаров или формулы остальных показателей.
Повторно полученный отчёт WB может отличаться от первоначального закрытого дня;
сохраняются сам ответ, период, кабинет, время получения и доказательство покрытия.
Отсутствующая строка WB не считается нулём.

## Подготовка

1. Сохранить независимый снимок опубликованной витрины и сверить его с её HTTP
   выдачей. Собирать точные закрытые дни штатным dated collector, последовательно
   и с его ограничениями. Сравнить все семь показателей SKU и соответствующие
   итоги и группы. Совпадающие дни исключить.
2. Разделить проверенные ответы на порции не более семи дней. Зафиксировать
   source digest, кабинет и датированный состав опубликованных SKU. Поиск со
   `scoped_complete` доказывает только явно запрошенный состав.
3. Проверить кандидат до записи: нативные ready-планы, точные ячейки истории,
   сохранность посторонних ячеек и способ возврата к состоянию до операции.
   Выгрузки и журналы находятся вне Git.

## Публикация одной порции

После проверенного выпуска кода использовать общий Production Apply launcher.
Для каждой фазы — собственный operation ID, preview с точными before/candidate
fingerprints, один submit и readback. Не отправлять запись повторно после
неопределённого ответа.

Для непрерывного окна обслуживания все три запроса связываются с одним точным
`maintenance_window_id`. Зарегистрированный recovery получает настоящий admission
lease и heavy lock под блокировками pause/resume, проверяет сохранённый baseline
и удерживаемое окно. Он не снимает barrier и не разрешает обычные циклы во время
восстановления. Запрос без этого поля сохраняет обычные правила допуска.

- `web_source_publication_v1`, `phase=source`: исходные таблицы и handoff,
  сохранение полных before-images и проверка материализованного ответа.
- Тот же adapter, `phase=publication`: accepted slots, closure и нативные
  ready-планы. `expected_nm_ids_by_as_of_date` фиксирует фактический состав
  каждого старого плана. `history_roster` связывает текущую edition с датированным
  составом и подписями строк. Недостающие строки добавляются только для семи
  разрешённых метрик; соседние даты в новых строках остаются пустыми.
- `web_source_history_repair_v1`: запрос связывает точную предыдущую publication,
  её request digest, текущую edition и датированные составы. Публикация истории
  разрешена только в подтверждённом окне обслуживания. Сначала журнал, затем
  копирование изменяемых объектов, полная проверка и CAS переключение CURRENT.

Завершить все три фазы порции до следующей. Соседние порции могут менять разные
столбцы одного ready-плана. Поэтому возврат нативных before-images требует
обратного порядка и точного CAS; чужие изменения не перезаписываются.

## Доказательства результата

Исторический overlay сохраняет каталоги, membership, native proofs и байты всех
нецелевых сжатых ячеек. Отдельный `source_repair` указывает наблюдавшийся источник;
это не новая отметка полного нативного пересчёта. Штатное обновление сохраняет
такое свидетельство только пока сохраняется тот же неизменяемый объект дня.
Старые свидетельства ремонта групп не переносятся на заменённые объекты.
До переключения сохраняется `SOURCE_REPAIR_PINS.json`: исходные editions и их
объекты защищены от обычной очистки по сроку. Удаление этих закреплений требует
отдельного решения о сроке хранения восстановления. Повторная проверка истории
сверяет собственные датированные объекты и источник, поэтому публикация следующей
непересекающейся порции не делает прежнее подтверждение ложным. Для более поздней
проверки нативного плана используется его `target_only` readback; строгая проверка
полного before/after сохраняется для непосредственной записи и rollback.

Сверить все восстановленные SKU, TOTAL и GROUP с сохранёнными ответами, проверить
посторонние ячейки, а также HTTP выдачу опубликованной edition. Отдельно показать
неполное покрытие и отсутствующие строки. После успешного выпуска и восстановления
возобновить то же окно обслуживания штатным exact resume; проверить восстановление
исходного трёхчасового расписания. Успешный submit сам по себе не означает, что
витрина проверена или циклы возобновлены.
