# PR Gate, выпуск и Production Apply

## Проверка PR

Для `main` требуется один context — `pr-gate`, связанный с точными base/head.
Он проверяет diff и форматы, механизм выбора тестов и затронутую область.
Общая основа, схема или опасная правка требуют более широких проверок.
Неизвестная область останавливается с причиной, а не включает весь репозиторий.
Selector и harness берутся из доверенного base; их правка действует после слияния.

## Обычный выпуск

1. Доведи Gate до PASS, пока PR в Draft. Draft проверяется, но не выпускается.
2. Для `live_runtime` при выбранном трёхчасовом профиле подготовь quiet/held
   maintenance окно по [защите цикла](../runbooks/business_data_cycle_deploy_protection.md).
3. Сделай PR готовым и один раз запусти существующий `Release Runner` вручную
   с `workflow_run_id` успешного Gate. Готовность PR сама не перезапускает тесты.

Runner из доверенного `main` повторно проверяет готовность PR, provenance Gate,
точные base/head, успешные jobs и неизменный проверенный план. При изменении
base/head прежний PASS не подходит: нужен новый Gate. Runner выполняет один
squash merge, подтверждает его родителя и фактический `main`. Автоматический
запуск после нового успешного Gate для уже готового PR также сохраняется.

`repo_only` заканчивается без production-доступа. `live_runtime` разворачивает
точный merge и проверяет версию, сервисы и health. При выбранном профиле ownership
claim выполняется до merge и удерживается до внешнего runtime readback;
45-минутный Runner не ждёт drain и не открывает явную паузу автоматически.

Receipt связывает PR, Gate run, base/head/merge, фактически выпущенную версию и
результат. Блокировка означает ошибку workflow. При неопределённом результате
сначала читают исходную operation; повторный запуск не заменяет recovery.
Поддержанные частные recovery и границы первого выпуска находятся в
[отдельном runbook](../runbooks/release_recovery.md).

## Production Apply

Выпуск кода заканчивается до отдельно разрешённой записи бизнес-данных.
Общий launcher вызывает только зарегистрированный доменный adapter и связывает
operation ID, точную цель, отпечатки состояния «до» и кандидата, submit/readback
и способ восстановления. Adapter отвечает за предметную проверку, locks и
backup/CAS. Submit выполняется один раз; неоднозначный ответ требует readback
той же операции. Исторические WBC-манифесты и универсальные пакеты проверок
в действующий контур не входят.
