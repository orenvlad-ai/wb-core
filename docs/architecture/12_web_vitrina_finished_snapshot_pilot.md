# WBC0069K16: проверочный готовый снимок витрины, этап 1

Этап 1 принят на реальных сохранённых данных 14/31. Следующий кандидат добавляет отдельную фоновую сборку и готовые текущие периоды 14/31; действующие сборщики источников, склад, финансы и операторские процедуры сохраняются.

## Ручная сборка и публикация

Источник — **полный завершённый** `web_vitrina_page_composition`, уже рассчитанный существующими `SheetVitrinaV1WebVitrinaBlock → view model → gravity adapter → page composition` на явно выбранных 14 или 31 датах. Предпочтителен существующий полный `indexed_cells_v2` (версия ответа 2); полный legacy (версия 1) при импорте переводится в тот же формат. Вызывающая сторона сначала сохраняет trusted JSON результата в локальный файл. Shell, Loading, error, неполные счётчики строк, каталог групп/дат/ячеек отклоняются до записи. Пилотный импорт:

```sh
python3 apps/web_vitrina_snapshot_pilot_smoke.py --import-artifact /path/to/finished_full_projection.json --store /path/to/explicit_pilot.sqlite3 --date-from 2026-04-07 --date-to 2026-04-20
```

Каталог и все 16 полей ячеек берутся из готового adapter result без повторения формул; существующий `indexed_cells_v2` сохраняется и передаётся без распаковки всего периода. Лимит суммарного JSON артефакта остаётся 128 MiB. Ручной импорт записывает immutable generation и переключает указатель в одной транзакции отдельной SQLite. Фоновый сборщик публикует сразу готовую пару 14/31 через отдельный файл-кандидат и атомарную замену своего хранилища. Если валидация или транзакция не завершилась, прежний указатель остаётся. Хранилище включается в HTTP-сервер **только явным** `snapshot_pilot_store=...`; нет автосоздания на GET. Пилотный GET открывает только это хранилище `mode=ro&immutable=1`/`query_only` и не вызывает business evaluator.

## Проверочный UI

`?history_mode=explicit&date_from=...&date_to=...&snapshot_pilot=1` загружает только готовые TOTAL/GROUP rows. Кнопка «Показать SKU этого снимка» отдельно получает SKU rows по тому же immutable `generation_id`; возможная новая публикация не смешивается с уже открытым поколением. В таблице показывается время сохранения именно выбранной generation, а не время повторного открытия страницы. Пока SKU не получены, поиск и сортировка по всему каталогу отключены: вывод по summary не объявляется глобальным. Проверки статуса projection в этом режиме не запускают legacy full/V3 reload. Кнопка обновления источников скрыта. Доступ к обоим GET проходит через обычную проверку Web Vitrina HTTP auth и scope.

Локальный сервер с синтетическим fixture и сравнимым обычным путём:

```sh
python3 apps/web_vitrina_snapshot_pilot_smoke.py --serve
```

Команда печатает URL 14 и 31 дней с `snapshot_pilot=1`, те же URL без него, путь временного SQLite и полные fixture JSON. Числа времени этого fixture не описывают production. `python3 apps/web_vitrina_snapshot_pilot_smoke.py` проверяет точный row/cell/column parity 14/31, HTTP, браузерное раскрытие и обычный путь, сохранение last-good при сбое, отказ от усечённых таблиц и отсутствие evaluator на пилотном GET. Отдельный **синтетический структурный** тест около 8000 строк × 31 дата проверяет размер компактного артефакта относительно 128 MiB; это не production benchmark.

## Принятые реальные проверки этапа 1

3 октября 2026 проверены сохранённые полные композиции 14/31: каталог, даты и все 16 полей ячеек совпадают с исходным результатом. Начальная таблица TOTAL/GROUP: 14 дней — 4,2–4,5 с, 31 день — 3,9–4,7 с; summary read — 0,5–0,8 с. Проверка выполнена изолированно на том же production host через SSH; это не выпуск и не benchmark HTTPS-прокси. Существующая подготовка исходного результата занимала примерно 39/64 с. Раскрытие всех SKU остаётся крупной операцией, около 14–18 с; пользователь принял ускоренную начальную загрузку.

Доказательства и реальные данные хранятся **вне Git**: `WBC_audits/0069-ротация-0054/СНИМОК_ПИЛОТ_ЭТАП1_2026-10-03/real/browser-real-final.json` и receipts исходных композиций. Замороженный `real-pilot.sqlite3` не изменяется. Новый default UI отдельно проверяется на личной копии этих артефактов, без расчёта на GET.

## Фоновый кандидат

`apps/web_vitrina_finished_snapshot_build.py` — отдельный oneshot. Новый таймер запускается в 01:55, 03:55, …, 23:55 `Asia/Tbilisi`, `Persistent=false`, без догоняющих запусков. Одновременно работает только один собственный builder. Срок окончания абсолютный — до :59 текущего слота; задержанный запуск получает меньше времени. Subprocess убивается при превышении срока. Часовой пояс бизнес-дат остаётся штатным `Asia/Yekaterinburg`, обе композиции используют один captured now и pinned read-only operational/FBS boundary.

Перед стартом проверяются live API markers, существующий warehouse lock, Finance daily lock и relevant systemd oneshots (включая `activating`). Busy или unknown пропускают слот. API marker — короткая атомарная запись при старте и удаление в finally существующего job runner, без фонового polling и без ожидания операторских задач. Эта проверка не обещает защиты от нового ручного запуска после её завершения.

Сборщик переиспользует общий текущий business evaluator и считает 14/31 **отдельно**. Готовая пара валидируется целиком; он копирует только собственную прежнюю derived DB в `.building-*`, выполняет publication/GC на кандидате, закрывает SQLite, делает fsync и atomic rename. Served DB никогда не изменяется на месте. SIGKILL сохраняет прежний читаемый файл; временный journal относится только к кандидату. При следующем singleflight запуске удаляются только собственные временные файлы. GET не создаёт SQLite sidecars и не запускает evaluator.

Хранилище: `/opt/wb-core-runtime/state/generations/web-vitrina-finished.sqlite3`, на существующем внешнем generation mount. До сборки проверяются его штатный контракт/UUID/options, свободное место с 8 GiB reserve и запасом на собственную копию/пару. SQLite ограничена 2 GiB. Retention выполняется только в кандидате: current и previous на каждый период плюс 4 часа для pinned вкладок; истёкшее поколение возвращает `snapshot_expired`. VACUUM по расписанию нет; страницы повторно используются.

HTTP runner читает `WEB_VITRINA_FINISHED_SNAPSHOT_STORE`; `WEB_VITRINA_FINISHED_SNAPSHOT_DEFAULT=1` включает текущие ready 14/31. До первой успешной atomic публикации отсутствующий store и sentinel означают обычную загрузку с сообщением о подготовке снимков. После создания store либо `.initialized` отсутствующий/пустой/повреждённый снимок даёт явную ошибку без скрытого тяжёлого fallback. Sentinel создаётся только после публикации, с file/directory fsync. Flag `DEFAULT=0` или явный `snapshot_pilot=0` оставляют проверяемый обычный путь.

Обычный URL показывает готовые 14 дней; календарь содержит явные быстрые кнопки 14/31. Другие периоды, включая прежние 30/90/180/365, используют действующий путь с индикацией. Резка 31-дневных агрегатов не применяется. При смене дня до новой сборки показываются фактические даты предыдущего полного снимка и предупреждение, включая раскрытые SKU. Авторизация, серверные пользовательские настройки метрик, фильтры и сортировка сохраняются.

## Проверка и выпуск

`python3 apps/web_vitrina_finished_snapshot_smoke.py` проверяет read-only parity 14/31, pair validation/failure, bootstrap rename-before-sentinel, storage collision/hardlink, marker failures/concurrency, абсолютный deadline, kill unpublished candidate → read-only last-good без recovery/sidecars, TTL expiry, default14 → быстрый UI preset31 → pinned SKU → обычный период → ready31, user config, missing/corrupt no fallback. Существующий pilot smoke сохраняет проверки обычного пути и auth/encoding.

Unit и timer включаются штатным hosted target/deploy barrier. Выпуск и production warmup выполняет куратор после независимого review. Приёмка требует готовых текущих 14/31, отдельного readback timer (`is-enabled`, `is-active`, `OnCalendar`), прав reader/store и обычного браузерного UI; CI и локальные времена сами по себе не подтверждают production результат.
