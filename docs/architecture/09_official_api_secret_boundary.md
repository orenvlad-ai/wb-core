# Секреты и внешние API

- Токены, пароли, ключи SSH, cookies и полные production-выгрузки не хранятся в Git.
- Локальные секреты остаются в системном или пользовательском хранилище;
  production-секреты — на сервере или в GitHub Environment.
- Клиентский интерфейс не получает секрет, если запрос может выполнить сервер.
- Логи и receipts содержат безопасные идентификаторы и хеши, а не секретные значения.
- Проверка PR выполняется без production-ключей. Ключи доступны только доверенному
  выпуску или явно запущенной production-операции.
- При ошибке авторизации не подставляй другой аккаунт, сервер или старый токен по догадке.

Каждый модуль дополнительно ограничивает нужные ему методы API, область аккаунта,
частоту запросов и допустимые записи.

## Браузерная проверка WebCore

Для браузерных проверок на Mac и сервере разработки используй одну отдельную
учётную запись **WebCore Codex** через обычную форму входа
`https://api.selleros.pro/login`. `codex1` и `codex2` — разные пользователи
операционной системы, а не разные учётные записи WebCore. Пользователь разрешил
сохранить данные этой учётной записи в личном хранилище каждой среды и выполнять
вход самостоятельно.

### Личное хранилище в каждой среде

На Mac и под каждым серверным пользователем (`codex1`, `codex2`) запись находится
в `~/.config/wbc-browser-access/credentials.json`. Это JSON с ровно тремя
полями: `origin`, `username`, `password`. `origin` равен
`https://api.selleros.pro`; имя записи хранилища или пользователя Linux не
является логином сайта. Каталог должен принадлежать текущему пользователю и
иметь права `0700`, обычный файл — тому же пользователю с правами `0600`.
Символьные ссылки недопустимы. Файл находится вне репозитория и рабочих деревьев.
Это **незашифрованный файл с паролем**; пользователь явно согласовал такой способ
хранения. Доступ к нему ограничен правами владельца, но root на сервере также
может его прочитать. Файл одной среды автоматически не доступен в другой.

Перед использованием прочитай личную инструкцию без секретов:
`~/.local/share/wbc-browser-access/README.md`. Проверка наличия, формата и прав
без вывода значений:

```bash
python3 ~/.local/share/wbc-browser-access/check_access.py
```

На Linux один обычный вход и проверка доступа к странице витрины:

```bash
/srv/wbc/tooling/wb-core-stage5/venv/bin/python ~/.local/share/wbc-browser-access/check_access.py --login
```

Проверка закрывает свой браузер. Для дальнейшей диагностики агент выполняет
обычный вход в собственном браузерном процессе. Серверный Playwright не
управляет рабочим столом или встроенным браузером Mac. На Mac при использовании
Codex Computer Use инструкция в личном README описывает чтение JSON через
`node:fs` непосредственно в память процесса: сначала проверяются владелец,
права и отсутствие символьных ссылок, затем точный `origin`. Данные передаются
только полям формы входа; в связку ключей, вывод инструмента или браузерный
профиль они не копируются.

### Общие правила

Читай запись только в память браузерного процесса и передавай значения полям
входа только после проверки точного origin `https://api.selleros.pro`.
Не выводи значения в переписку, аргументы команд, логи, снимки заполненной
формы, артефакты, Git или CI. Не сохраняй cookies, storage state или профиль
браузера для повторного входа, не извлекай cookies пользователя и не подменяй
сессию через сервер. Сессия WebCore истекает; тогда выполняй новый обычный
вход. При неопределённом результате сначала проверь состояние той же попытки
входа; не отправляй форму повторно вслепую.

После входа проверь целевую страницу и ожидаемый результат реализации.
Доступность `/login` сама по себе не считается браузерной проверкой.
Использование аккаунта не расширяет разрешённые задачей изменения рабочих
данных. Если запись отсутствует, права неверны или вход отклонён, сообщи
конкретный блокер; не перебирай другие аккаунты и старые секреты.
