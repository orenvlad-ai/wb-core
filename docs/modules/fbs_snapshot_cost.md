# Кандидат стоимости FBS по официальным снимкам

`packages/application/fbs_snapshot_cost.py` готовит отдельный дневной расчёт
себестоимости FBS. Он не подключён к рабочему учёту. Этап 5 подготовил
[проверочное отображение FF и товарного капитала](fbs_inventory_presentation.md).
Этап 4 использует
его в отдельной [общей цене SKU](shared_sku_cost.md) для проверочного расчёта
финансового и партнёрского отчётов. Все результаты имеют `candidate_only=true`.

## Источники и начальное состояние

`fbs_snapshot_cost_sources.capture_current()` читает существующую operational
SQLite в одной транзакции `mode=ro`, `query_only=ON`. Внешние запросы и сервисы
записи не запускаются. Количество поступает из полного свежего официального
снимка для всей номенклатуры и настроенных FF-складов. Нет строки или нарушен
охват — источник неполный, нулевой остаток не выдумывается.

При инициализации текущая опубликованная стоимость SKU × склад принимается
как начальная без восстановления истории. Версия должна соответствовать
точному digest текущих FF pool-строк и опубликованным FF-данным. Вместе с ней
фиксируются снимок количества, источники стоимости и точный перечень уже
учтённых документов с их отпечатками. Временной отсечки без проверки состава
недостаточно. Начальный день остаётся замороженной точкой наблюдения; первый
расчётный день следует за ним. Подготовительный кандидат не назначает дату
реального перехода.

Также один раз принимаются опубликованные FBO-остатки и уже находящийся в
документальном перемещении товар. Это вспомогательная часть кандидата для
общих расходов и перемещений FBS ↔ FBO, а не переключение рабочего FBO.
Начальный капитал в пути сохраняет остаток копеек после уже принятых частей.

После инициализации capture вызывается с `include_baseline=False`
(`--without-baseline` в CLI). Прежние pool quantity/WAC и опубликованные цены
тогда вообще не читаются. Документальные движения используются для проверки
соответствия проведённому документу; операции Lifecycle без такого документа
не являются входами расчёта.

Адаптер передаёт `cost_document`: проверенный по точным сохранённым байтам
заголовок документа, строки обоих пулов, расходы, связи и движения. Охват
расхода берётся из заголовка, даже если прежнее распределение содержало строки
только одного пула. Новые цены не читаются из старых денежных строк переносов.

## Дневной расчёт

Для каждого SKU × склад исходная база — количество и средняя последнего
закрытого дня. Открытый день каждый раз собирается заново от этой базы:

```
средняя = (исходное количество × исходная средняя
           + стоимость поступлений дня + подтверждённые расходы дня)
          / (исходное количество + количество поступлений дня)
капитал = количество из снимка данного дня × средняя
```

Пример: исходно 1000 шт. по 100 ₽, документ поступления 1000 шт. по 200 ₽.
Средняя равна 150 ₽, даже если снимок с 2000 шт. получен раньше документа.
Следующий снимок с 1900 шт. меняет капитал на 285000 ₽, но не прибавляет приход
повторно. Движения выбытия не вычитаются второй раз из официального количества.

Документальные источники:

- Приёмка из Китая: количество строки распределения и её документальная
  стоимость с расходами. Суммы сверяются с проведёнными движениями.
- Расходы: полная сумма и охват FBS/FBO/both берутся из подтверждённого
  заголовка. `fbs_document_cost.py` распределяет копейки сначала между пулами,
  затем между SKU по новой дневной базе: открытие плюс поступления дня.
  Сохраняются веса и суммы распределения. Прежние доли и прежние количества
  не участвуют. Расходы начального manifest остаются внутри принятой цены.
- Перемещения: отгрузка получает новую среднюю своего дня и сохраняет ссылку
  на документ, исходный склад и версию оценки. Приёмка следующего дня или
  позднее использует эту сохранённую цену. Повторного списания количества
  из FBS-снимка нет.
- Частичная приёмка, потеря, отмена и расхождение SKU расходуют оставшуюся часть
  отгрузки. При отмене возвращается стоимость товара; транспортные расходы
  отменённой/потерянной части в остаток не капитализируются. Поздний счёт
  распределяется по количеству исходной отгрузки и учитывает уже принятые части.
- Переносы FBS ↔ FBO используют тот же новый источник стоимости. FBO-кандидат
  после начальной фиксации меняется только по документам. Старый FBS-капитал
  не может вернуться через промежуточный FBO.

Связанные перемещения одного дня оцениваются совместно, чтобы одна дневная
стоимость использовалась с обеих сторон, включая возврат по кругу. Нет внешней
стоимостной основы для такого круга — расчёт отклоняется. Новая средняя дня
отгрузки может уточняться, пока день открыт; закрытая ссылка не меняется.

Сторно документа того же открытого дня исключает его перед расчётом. Сторно
закрытого документа требует отдельной корректировки и не переписывает историю.
Неподдерживаемый документ не применяется частично. Пропавший из следующего
полного чтения неучтённый документ сохраняется как неразрешённый факт. Нет
стоимости отгрузки, превышено её количество или расходу не соответствует
положительная расчётная база — обновление отклоняется с причиной; нулевая
оценка вместо пропуска не публикуется.

При нулевом количестве последняя известная цена сохраняется, капитал равен
нулю. Новое поступление после нулевого открытия устанавливает среднюю по
своей стоимости. Неизвестная цена положительного остатка не заменяется нулём;
неполная оценка делает итоговый капитал недоступным. Увеличение количества без
документа сохраняет известную среднюю и отмечается в диагностике.

## Даты, закрытие и сохранение

Закрытие кандидата — явная операция только для прошедшего полного дня без
неразрешённых документов. Расписание закрытия и окончательная дата старта
пока не назначены. Пропущенный дневной снимок блокирует продвижение к следующему
периоду; количество другой даты не подставляется.

Если документ пришёл на следующий день, пока предыдущий ещё открыт,
пересчитывается предыдущий день с его сохранённым снимком. После его закрытия
тот же новый capture можно применить для следующего дня. Старое документальное
наблюдение не может заменить более новое, даже при одинаковом снимке количества.

Поздний документ закрытой даты или изменение уже поглощённого документа
остаётся в диагностике и блокирует дальнейшее закрытие. Закрытые цены и
начальная база не меняются. Автоматического исторического исправления нет.

`CandidateStore` хранит отдельную SQLite с неизменяемыми ревизиями и проверкой
ожидаемого текущего отпечатка при записи. Файл существующей бизнес-базы
отклоняется до записи. `candidate_period_view(state, day)` возвращает только
точную запрошенную дату, исходный снимок, формулу, документы и качество;
отсутствующая дата не заменяется последней ценой.

CLI `apps/fbs_snapshot_cost.py` предоставляет `capture`, `initialize`,
`refresh`, `close`, `read`. Пути источника, capture и отдельной базы задаются
явно. Повтор идентичной операции не создаёт новую ревизию. Исходные capture
предназначены для доверенного внутреннего использования и не являются
самостоятельным разрешением записи в production.

Формат кандидата — `fbs_snapshot_cost_candidate_v2`. Предварительные файлы v1
не мигрируют автоматически: для новой подготовки нужен свежий capture и
отдельный файл кандидата. Начальные или закрытые цены старого файла не меняются.

## Граница дальнейшего подключения

Активных потребителей, таймеров, автоматического закрытия и переключателя
политики этот модуль не добавляет. Документы уже подключены к кандидату;
их исходные утверждённые суммы не меняются. Подключение отчётов, капитала,
расписания и окончательная начальная фиксация выполняются отдельными этапами
перехода. Публикация новой политики должна брать сохранённые значения кандидата,
включая его распределения расходов и ссылки стоимости перемещений.

Датированное чтение возвращает FBS-итог и отдельный `fbo_component` той же
версии. Общий капитал и общая цена должны использовать эту согласованную пару:
добавление старой FBO-доли расхода к новой FBS-доле повторно учло бы часть суммы.
FBO-компонент не прибавляется к показателю официального количества FBS.

Количество является доступным официальным FBS, а не подтверждённым полным
физическим FF с резервом и транзитом. Снимки не доказывают фактическую
последовательность всех движений; эта модель не гарантирует компенсацию
погрешностей прибыли после распродажи.

Проверки: `apps/fbs_snapshot_cost_smoke.py`,
`apps/fbs_snapshot_cost_sources_smoke.py`, `apps/fbs_document_cost_smoke.py`.
