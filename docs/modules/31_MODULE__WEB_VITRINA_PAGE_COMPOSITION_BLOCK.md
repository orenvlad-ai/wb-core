# 3. Target contract и смысл результата

- `GET /sheet-vitrina-v1/vitrina` теперь является реальной usable web-vitrina page:
  - canonical entrypoint for the unified `sheet_vitrina_v1` UI; the main tab strip contains only work sections `Витрина`, `Поставки`, `Отчёты`, `Отзывы`, `Реклама`, `Цены`, `Исследования`; `Настройки` is a right-side shell action next to `Выйти` and activates the embedded settings panel inside the same shell.
  - shell visibility is section-aware: runtime `allowed_sections` controls which work tabs/actions are shown and which matching `/v1/...` APIs are allowed. `settings` allows the settings surface; `settings + manage_users` is required for `Настройки -> Пользователи`. `supply_operator` legacy users map to only `Поставки`; supplier-only users do not receive the full shell.
  - `GET /sheet-vitrina-v1/operator` remains a compatibility entry and renders the same unified shell instead of the former narrow operator-only page; embedded operator-only panels are reserved for the unified tabs and internal compatibility probes
  - compact table header inside `Витрина`: visible source badge `sheet_vitrina_v1`, explanatory ready-snapshot copy, grid-library/row/column diagnostics and `Снимок/Вчера/Сегодня/TZ` technical line are not rendered. The former standalone `Таблица` title is not rendered; the header line is a two-zone layout: left zone contains only the compact dynamic object label, and the right zone is anchored to the table/header right edge near the load action with short browser-owned `обн:` timestamp, short server freshness `свеж:` timestamp, the compact icon-only load-status lamp, unlabeled in-header controls and `Загрузить` / `Загрузить и обновить`. The separate visual freshness badge `акт` / `стар` is not rendered. The dynamic object label may ellipsis/truncate with title and must not move the right-side controls/status/action when its text changes from `Итого` to a long SKU label.
  - status next to the load action is a compact lamp immediately left of `Загрузить` / `Загрузить и обновить`, visually attached to data loading. Visible text is not rendered; the accessible title/aria label carries only `Загрузка: идёт`, `Загрузка: успешно`, `Загрузка: ошибка`, `Загрузка: предупреждение` or `Загрузка: нет данных`. Loading is a simple violet pulsing dot with visible opacity/scale pulse; final states are small static green/yellow/red/neutral dots without border, halo, glyphs or other extra graphics. Its semantics remain the last load window only: `today_current` + `yesterday_closed` in `Asia/Yekaterinburg`; the UI must not expose those technical slot names in the header. Old snapshot errors elsewhere in the selected historical table range must not force visible error; errors/warnings inside that latest two-day window still surface truthfully.
  - while `Загрузить и обновить` is running, the header replaces the load status lamp with a compact pulsing loading lamp driven by the existing async job/log polling (`start/queued`, source fetch, prepare/materialize, load/update table, finish). The former long stage-based progress bar is not rendered; after completion the compact indicator disappears and the final semantic lamp stays visible.
  - compact summary strip uses `обн:` and `свеж:` without visible timezone or seconds; semantic load status is an inline lamp left of the load button, not under the button and not as a left-side period/table aggregate. The former bulky `Период`, `Строки`, grid-library and source-diagnostic cards are not separate operator blocks because period is controlled in the header and row counts remain table/internal diagnostics
  - the same top status area includes a compact Seller Portal session indicator rendered as the lowercase word `сессия` and a neutral grey separator `|`, with no leading dot/bullet, no pill/badge frame and no long state words in the header. Only the word `сессия` receives the session tone: green means the last relevant run did not hit a session-expired/login-required blocker; red means the last relevant run returned invalid/missing/wrong-supplier/session-expired/login-required evidence such as `login_redirect` or `validate_401`. The container, separator, update timestamp and neighboring text stay neutral. It is a read-only `span`, not a button/link/dropdown/launcher trigger, and clicking it must do nothing. Page open/table reread must not launch `seller-portal-session/check` or any other Seller Portal probe only for this indicator. The indicator is derived from already returned runtime/source-status/result-state for the latest bot/full refresh run; neutral means there is no last-run session signal in the payload. A manual `Проверить сессию` action may update the same UI state from its explicit probe result.
  - compact historical period control stays in the table header line; section/group controls are moved behind the adjacent `Фильтры` button into a narrow one-row rail. The old always-expanded `История` block and the old standalone filter toolbar are not rendered by default. On desktop width, selected date range renders fully without internal ellipsis while there is usable control space; section/group labels render fully after the rail is opened, with narrow-width fallback allowed only after compact padding/spacing has been exhausted.
  - default web-vitrina period is backend-owned and browser-render-only: opening `GET /sheet-vitrina-v1/vitrina` without an explicit history marker selects `date_to=current_business_date_iso(now, Asia/Yekaterinburg)`, `date_from=date_to-13 days`, `default_preset_id=two_weeks`, exactly 14 inclusive dates. Ready snapshot availability may produce truthful blank/partial cells inside that window, but it must not move the default range endpoint to the latest materialized snapshot. Browser `localStorage`, history state and table snapshot cache are not default-period inputs.
  - manual historical period/day URL state requires `history_mode=explicit`. `date_from/date_to` without this marker, invalid `history_mode`, legacy range state and old table snapshot keys are treated as default no-query mode and are cleaned from the browser URL/state without full reload. The browser may draft dates inside the calendar popover, but the authoritative default range is only `historical_access.default_date_from/default_date_to` and `historical_access.selected_date_from/selected_date_to` from page composition.
  - table controls are in the compact table header, not a separate `Фильтры и настройки` / toolbar section: the header keeps period plus a small `Фильтры` button immediately before the load-status lamp/progress/load action; the opened rail contains section/group controls and a dark-theme `SKU-метрики` picker. `SKU-метрики` defaults to `Все метрики` on every fresh page load, keeps `Все метрики` as the first service option, orders individual metric options by the current rendered SKU metric order from the table/presentation state rather than by label/backend option order, does not persist to backend or localStorage, applies only after `Показать`, resets through `Сбросить`, and narrows only `row_kind=sku` rows. The `Итого` block and non-SKU aggregate rows stay full; SKU separator rows are compact plain-text table separators without pill/capsule framing and are rendered only when a visible SKU metric row remains under them. Visible `Поиск`, `Столбцы`, `Сброс`, `Тип строк`, toolbar `Метрики`, visible `Сортировка` selector and row-count `Итог` block are not rendered. Obsolete browser state from the former toolbar metric selector is ignored safely.
  - a separate collapsible `Метрики` presentation block sits below the main table and below `Автообновления`. It renders two compact dark tables side by side: `Итого` and `SKU`, while canonical preferences are stored in the auth-protected server user-config route and `localStorage` is only cache/one-time migration input. Each table is one scope-level sortable list with columns `Метрика`, `Группа`, `Отображение`; `Группа` is informational metadata from the existing section/group labels, not a sortable container or truth model. Metric rows expose compact drag handles and can be reordered across the whole scope list, so groups no longer constrain presentation order. Each scope table also has its own transient `Выбрать` mode: checkboxes appear only in that table, selected rows can be moved as one drag-and-drop batch while preserving their relative order, and a bulk `Отображение` selector applies `Показано` / `Свернуто` / `Скрыто` to selected rows only. Scope headers/actions are sticky inside each long settings table so `Выбрать`, bulk `Отображение`, and the SKU-only `Как Итого` action remain available while scrolling; selection mode, checkbox changes and drop reorders preserve the active scope table scroll position. Selection itself is UI-only transient state and is not persisted; order/display changes are scoped by `Итого`/`SKU` so shared metric keys cannot silently mutate the other scope. `Как Итого` derives SKU order/status from current `Итого` analog metrics by canonical key relation first (`total_...` / `..._total` / exact shared keys) and by bounded metadata signature only as fallback; it changes only SKU, preserves current `Итого`, and appends unmatched SKU metrics without duplicates. A safe one-time browser migration may auto-apply that derivation only when SKU state is default/uninitialized while `Итого` is already custom. `Отображение` has exactly `Показано`, `Свернуто`, `Скрыто`: shown rows are visible immediately and marked by a violet left accent; collapsed rows stay active/readable but are hidden under the nearest previous shown metric in the same scope; hidden rows remain in settings as muted rows and are absent from the main table. The main table order follows the scope list, collapsed runs reveal through an icon-only disclosure arrow inside the `Метрика` cell, and visible text `ещё N` / `Показать ещё N` is not rendered. Reset returns scope order, display statuses and expanded disclosure state to server/view-model defaults. This block is not a metric registry, formula, ready snapshot or accepted-truth owner.
  - repeated object/technical identity columns such as `Объект`, object key/type, SKU id/group, metric key and row-level update timestamp are kept in the row/backend model for filtering, ordering, dynamic label and refresh metadata, but are not visible columns and are not offered as user-restorable column controls. The old visible `Столбцы` control is not rendered in the compact header. `Метрика` is the first visible sticky column; `Раздел` is the next visible sticky column, left-aligned and sized for current Russian section labels; date columns and required business context columns stay non-hideable by the page UI.
  - custom browser floating controls in the unified shell close on outside click and `Escape`: historical period popover, `Фильтры` rail / `SKU-метрики` picker, feedbacks date-range picker, research SKU/metric multiselects, research date-range pickers and embedded operator stock-report SKU selector. Inside clicks for checkbox multiselects/date-range selection stay inside the control; clicking section/group inside the filters rail closes only the SKU picker and keeps the rail open. The rule is browser-only UX state, not backend/data truth.
  - main table display headers are Russian and start with `Метрика`, `Раздел`, then date columns; the former visible `Обновлено` table column is not rendered because freshness is shown in the header/status area. Backend/API row update metadata stays stable for refresh bookkeeping. The row object/scope label is exposed by the dynamic label above the table, which follows the top visible rendered row (`Итого` first, then current SKU/article while vertically scrolling) and does not depend on horizontal scroll. The main table inserts presentation-only separator rows between `Итого` and the first SKU block and between SKU object blocks; those separator rows show the next SKU/object label and do not change row truth or object identity. The separator label itself is horizontally sticky inside the first visible/sticky `Метрика` column zone, stays visible during horizontal table scroll, truncates long SKU labels with title/tooltip, and the separator background/gap may still span the whole row.
  - expanded collapsed metrics render as child rows with a subtle hierarchy guide/indent inside the `Метрика` cell. The parent disclosure remains icon-only and left of the metric name; visible count text such as `ещё N` / `Показать ещё N` is not rendered.
  - main-table operator projection keeps seller-funnel source keys distinct while removing the duplicated `Просмотры` row from section `Воронка`: `openCount` / `total_openCount` remain source metrics, but are not shown in this funnel section. Visible funnel rows are ordered as `Показы в воронке`, `CTR в воронке`, `Открытия карточки в воронке`; CTR is calculated read-side as `open_card_count / view_count` (or `total_open_card_count / total_view_count` for total rows), uses percent formatting and renders blank when the denominator is blank/zero/null. Search metrics such as `views_current` / `total_views_current` remain in section `Поиск`; the TOTAL row `CTR в поиске средний` is weighted by `views_current` so low-view SKU outliers from source snapshots do not dominate the operator total.
  - `Загрузить и обновить` = canonical server-side refresh from external sources + page reread, without Google Sheet write path. The backend owns the business date in `Asia/Yekaterinburg`, refreshes the visible-table source coverage for `yesterday_closed` and `today_current` according to source policy, then materializes/rereads the web-vitrina payload. Source groups that remain stale/missing without an accepted fallback keep the semantic result warning/error instead of being presented as a silent success.
  - `Автообновления` is a compact runtime-managed web-vitrina schedule panel below the main table and uses the same compact dark/violet collapsible header pattern as `Метрики`: disclosure arrow on the left, title, and one-line operator-readable summary. ## 3.1 Minimal bundled/client path

- Chosen path:
  - repo-owned inline client island inside `packages/adapters/templates/sheet_vitrina_v1_web_vitrina.html`
  - same existing read route with optional `surface=page_composition`
- Why this path is minimal:
  - no new endpoint family
  - no Node/React/Vite/Webpack contour
  - no client router
  - no static asset publish campaign
  - no duplication of business-truth assembly in browser
- Gravity-specific logic stays isolated:
  - adapter semantics still live in `packages/application/web_vitrina_gravity_table_adapter.py`
  - page shell only consumes adapter payload and renders sticky table headers/pinned columns plus ordinary scrolling group rows above it

## 3.2 Browser-state boundary

- Browser-side state now exists only as page-local UI state for filter/search/internal ordering plus a cache/migration copy of metric presentation preferences and optional column visibility. The `SKU-метрики` rail picker is transient page-local filter state: default is `Все метрики` after reload, and custom selection is not backend/user-config/localStorage truth. Metric presentation itself (scope-local `Итого`/`SKU` order, per-metric display status `Показано`/`Свернуто`/`Скрыто`, expanded disclosure state; transient selection checkboxes are not persisted; legacy toolbar metric selection, grouped shown/hidden, block-order and anchor fields are ignored) is canonical in the auth-protected server-side user config.
- Historical access state stays query-string-owned on the same route:
  - no query = default rolling two-week preset ending backend-owned `today_current_date`
  - `as_of_date` = one-day historical mode
  - `date_from/date_to` = bounded period mode assembled server-side from materialized ready snapshots plus explicit missing-date blanks for the backend-owned current week
- Namespace is explicit: `wb-core:sheet-vitrina-v1:web-vitrina:page-state:v1`.
- `GET/POST /v1/sheet-vitrina-v1/web-vitrina/user-config` stores versioned presentation preferences under the current authenticated WebCore account. Server config wins over `localStorage`; when server config is missing, a valid v2 browser metric-presentation payload may be migrated once with revision `0`, while stale/broken browser state cannot overwrite an existing server revision.
- This state is not data/source truth: it stores only presentation preferences, never metric values, source statuses, tokens or secrets.

# 7. Что уже доказано по модулю

- `/sheet-vitrina-v1/vitrina` is no longer a placeholder shell.
- Existing stable seams are now used end-to-end in a live read-only surface.
- The chosen client path stays intentionally minimal and repo-owned.
- Web-vitrina completion is verified through the server/public web surface (`/v1/sheet-vitrina-v1/web-vitrina`, optional `surface=page_composition`, and `/sheet-vitrina-v1/vitrina`); Google Sheets / GAS / `clasp` are not active verification targets for this surface.
- Historical ready snapshots may be used as bounded, audited reconciliation input for the shared accepted temporal source layer when the read model already contains daily SKU facts that reports lack; this is done only by repo-owned dry-run/apply tooling and does not make the browser UI or Google Sheets/GAS a source of truth.
- Freshness for automatic refresh is surfaced by `Автообновления` (`last run`, `last success`, `next run`, status/error). The table header is intentionally compact: browser-owned `обн:`, server freshness `свеж:`, and load-adjacent latest-window status as an icon-only lamp with accessible `Загрузка: ...` text; raw snapshot ids/as_of/debug remain in JSON/log surfaces.
- Embedded `Поставки` / `Отчёты` / `Настройки` remain UI-only composition inside `/sheet-vitrina-v1/vitrina`; iframe sizing/scroll relay changes do not introduce browser-side business truth or server-side profile persistence.
- user-facing timestamp render is unified: raw ISO artefacts like `T` / `Z` stay machine-only and no longer leak into visible operator text.
- summary/status tone now follows semantic snapshot truth:
  - green = confirmed normal result;
  - yellow = empty/zero/unchanged/stale/not_refreshed/preserved/retrying/not_verified;
  - red = hard source/materialization failure;
  - snapshot row existence alone is never enough for green.
- source-aware temporal policy is now part of that read-side truth:
  - `stocks` stays green when only non-required `today_current` is blank/`not_available`;
  - `fin_report_daily` stays green when `yesterday_closed` is confirmed and intraday `today_current` only produced tolerated non-final current-day output;
  - `prices_snapshot`, `ads_bids`, `spp` and `spp_proxy` preserve accepted-current rollover/latest-confirmed filled values, but closed-day preservation is surfaced as warning/latest-confirmed instead of false fresh-green closed-day refetch; missing required current without accepted fallback remains not OK;
  - `promo_by_price` stays green when accepted/runtime-cached latest confirmed values fill the visible cells, while invalid attempts without fallback remain not OK;
  - `seller_funnel_snapshot` / `web_source_snapshot` remain strict two-slot sources and keep the summary cards degraded on broken `today_current`.
- `Загрузить и обновить` on the vitrina now reuse-ит the canonical refresh contour and no longer depends on `/load` or Google Sheet auth to refresh the web-vitrina itself. It resolves `today_current`/`yesterday_closed` in `Asia/Yekaterinburg`, runs the same source/status machinery used by group refresh, materializes the ready snapshot and rereads the page payload. Technical job completion is not enough for user-facing success: the UI and log use `semantic_status`, `semantic_tone`, group/date-slot reasons and stale/missing source details to keep warning/error visible when expected visible metric sources did not refresh.
- The web-vitrina schedule panel is runtime-managed, not a frozen view of systemd. Old/default manual rows remain `11:00` and `20:00` in `Asia/Yekaterinburg`, and add/edit/delete/disable are persisted in server runtime JSON through the auto-schedules API. The same payload now also carries `schedule_policy`: `manual` uses persisted rows and permits arbitrary local `HH:mm` values, while `interval` materializes due slots from allowed 3/4/6 hour cadence inside fixed `10:00-22:00 Asia/Yekaterinburg`, preserves matching slot lifecycle across interval id/cadence rematerialization, and never creates night/24h schedules. The browser presents this as one selector (`Ручные настройки` / `Каждые 3/4/6 часа`) with no duplicated interval chip preview, no separate action row and no block-level reload button. The repo-owned systemd timer runs an authenticated due-check every 10 minutes against `/opt/wb-core-runtime/state`, starts only the latest accumulated due slot and marks older due slots as missed; manual and automatic refresh paths stay unified and differ only by trigger metadata. A completed auto-refresh result persists WB supplies diagnostics under `last_auto_run_result.wb_supplies_auto_sync`; official WB sync errors or Seller Portal transit-cost preflight failures lower the semantic result to warning without turning the refresh technical status into error.
- `Обновить группу` on the vitrina starts date-scoped `POST /v1/sheet-vitrina-v1/web-vitrina/group-refresh` with payload `{async: true, source_group_id, as_of_date}` for one source group and one selected date. The action immediately surfaces a group-local launch state and appends a visible client action-log line; if the POST fails before a backend job is created, the page shows a group-local error and a visible log line such as `Не удалось запустить обновление группы WB API за 2026-04-24: HTTP 404 route not found`.
- Once the POST reaches the backend, the action reuses the existing refresh/status/job/log seams, creates a `refresh_group` job before source fetch, fetches/prepares only the selected group, loads only cells for the selected date into the target ready snapshot, updates row-level update timestamp metadata and group-level `last_updated_at` only for affected rows/groups, and logs stage-aware success/failure (`source_fetch`, `prepare_materialize`, `load_group_to_vitrina`) with the selected `as_of_date`.
- For `source_group_id=onec_product_capital`, group-refresh treats a fresh successful 1C payload that fully covers the active SKU universe but lacks a canonical stage bucket as structural zero stock: source status stays successful with `zero_stock_stage_buckets=...`, the selected date's bucket qty/unit-cost/capital cells materialize as `0`, present 1C buckets still materialize, and unrelated source groups plus non-selected dates are preserved. Source errors, date mismatch, unmapped stages and partial SKU coverage remain warning/error/blank without fake zeros; accepted same-date server truth is preserved only for those invalid/failing attempts.
- Refresh and group-refresh job results may include `updated_cells` entries `{row_id, metric_key, as_of_date, source_group_id, status}`. The field is result metadata for the current UI session only: it drives transient green/amber text-color highlighting and log counters without replacing the dark table background, and it is not persisted as permanent table styling. Full refresh emits metadata across all refreshed `date_columns`; group refresh remains bounded to the selected `source_group_id + as_of_date`.
- For full refresh, an explicit current business date is normalized to the previous closed-day snapshot key; this prevents invalid current-day ready snapshots with duplicate `today_current`/`yesterday_closed` columns and keeps highlight metadata on both temporal slots.
- `Загрузка данных` and `Лог` stay server-driven:
  - source-status details are lazy-loaded: initial page-open keeps a `not_loaded` state and the `Загрузить` button; no grouped source rows, no group action controls and no session controls are rendered until the first `Действия и состояния` open auto-loads details or an explicit retry/read-only details request succeeds
  - if the explicit details request asks for a ready snapshot that is not materialized, the loading table returns `source_status_state=missing_snapshot` with an actionable Russian message to run `Загрузить и обновить`; it must not render fake group shells or generic `upload summary unavailable` as the primary operator message
  - if the explicit details request returns empty/incomplete payload, the UI shows an explicit empty/error message and retry button instead of normal-looking group shells with `Источники группы пока не представлены...`
  - loading table is derived from the last relevant refresh/group-refresh job log and persisted source fallback; if exact job association is unavailable, page shows truthful non-OK status rather than unrelated stale run
  - after details load succeeds, absence of transient in-memory refresh-log must not hide source-group headers/actions when persisted source summary and backend capabilities are available; before the first open/load, controls stay intentionally unloaded
  - loading table rows are nested under stable source-group headers while preserving source truth and canonical source labels; coverage must include all visible main-table metrics, with residual calculated/formula metrics assigned to `Прочие источники`
  - loading table uses server/business `Сегодня: <YYYY-MM-DD>` and `Вчера: <YYYY-MM-DD>` dates, short OK/not-OK cells, reason columns, Russian metric labels from the existing metric registry and secondary technical endpoint text
  - loading table OK/not-OK reduction is source-aware: latest confirmed/runtime-cache/accepted fallback with filled visible cells is OK, non-required source slots are OK/non-degrading, and red is reserved for required source failures without accepted fallback or required visible value
  - log preview and `Скачать лог` reuse the existing in-memory job/log contour and render below the loading table
  - former `Обновление данных` is not an active page-composition activity block; persisted `STATUS` rows remain the underlying read-side truth for status contracts and fallback source outcomes
  - warning/error reasons are strictly summarized on the backend: raw STATUS/job note, JSON blobs, traceback text, request ids and similar technical payload stay only in the existing log/download surface
  - for bot-backed families an invalidated seller session is surfaced as short human reason (`сессия seller portal больше не действует; требуется повторный вход`) instead of generic `Template request ... was not captured`
- Historical period UX is intentionally thin:
  - the collapsed control shows `DD.MM.YYYY - DD.MM.YYYY` plus a calendar icon above the table
  - first open / hard refresh without explicit query uses the backend-owned rolling two-week preset `D-13..D`, ending on `today_current_date` in `Asia/Yekaterinburg`
  - `today_current_date` stays visible/selectable even when no ready snapshot for that date exists; the table shows blank/partial values and semantic warning rather than hiding the date
  - period reads may combine persisted ready snapshots saved under older registry bundle versions with the current visible registry row set by stable row key; existing historical metric values remain readable after schema extension, while new rows such as `spp_proxy` stay blank on dates whose older snapshot did not contain that row
  - this schema-evolution read is not a backfill: it does not copy new metric values into older dates, does not trigger upstream fetches and does not widen group-refresh writes beyond the current selected ready snapshot
  - opened state is a compact one-month picker, not the former expanded `История` section: header has previous/next month arrows, the calendar renders only one month, and technical mode/default/query-state explanations are not user-facing
- Table control UX is intentionally thin:
  - the former expanded `Фильтры и настройки` card is not rendered as a separate section
  - only period and the `Фильтры` trigger live in the compact header next to the right-side load action; section/group live inside the opened filters rail, and `SKU-метрики` is a page-local picker that filters only SKU rows after `Показать`; visible `Поиск`, `Столбцы`, `Сброс`, `Тип строк`, toolbar `Метрики` and visible sort controls are not rendered, and obsolete stored state is ignored safely; internal stable row ordering remains browser-local without a visible sort selector
  - the collapsible `Метрики` presentation block is browser-local state over the already received metric rows: it renders two compact scope tables (`Итого`, `SKU`) with row drag-and-drop across the whole scope list, informational `Группа` metadata, and a display selector `Показано` / `Свернуто` / `Скрыто`. Each scope table has an independent transient `Выбрать` mode, bulk display selector and selected-row DnD batch move; bulk selection is not written to storage, while resulting order/status changes are saved in the same namespaced presentation state. Display state is scoped by table, not just by metric key, because some metric keys may appear in both `Итого` and `SKU`. SKU can be explicitly synced with current `Итого` through `Как Итого`, and safe auto-sync is limited to default/uninitialized SKU state. The table applies that scope order plus display status without changing metric registry, formulas, ready snapshots or accepted truth; collapsed metrics attach to the nearest previous shown metric and reveal through an icon-only disclosure arrow in the `Метрика` cell, while hidden metrics stay available in settings but are absent from the main table.
  - controls stay browser-local and only filter/reorder the already received page payload; they do not trigger source refresh, data writes or new truth semantics
  - presets (`Неделя`, `2 недели`, `Месяц`, `Квартал`, `Год`), manual `date_from/date_to` fields and `Сбросить`/`Сохранить` live below that one-month calendar in the same small popover
  - `Сохранить` rewrites query string and re-reads server payload through the existing `date_from/date_to` ready-snapshot window path
  - `Сбросить` removes `as_of_date/date_from/date_to` and returns to the same rolling two-week default
  - source-status lazy load uses `source_status_snapshot_as_of_date` from the server contract and reads that ready snapshot/status across registry bundle versions when needed, so a period ending in `today_current` does not accidentally use the current-day column as the ready-snapshot key and older historical snapshots do not turn the page-composition surface into a non-JSON upstream failure
- period read status can still aggregate source semantics for the selected ready-snapshot window in the backend payload, but the operator-facing compact header pill next to `Загрузить` is the latest two-day load window (`today_current` + `yesterday_closed`) and must not be driven red by old errors outside that window or expose the slot names as visible header text.
- The page composition layer knows only page/layout/render state and does not become a second truth owner.
- User-facing `ЕБД` / `единая база данных` means the shared server-side accepted truth/runtime layer behind web-vitrina and reports; the browser page, Google Sheets/GAS and localStorage are not data-truth owners.
