# Наблюдение за заказами FBS без влияния на учёт

`apps/wb_fbs_shadow.py … poll` собирает заказы и статусы в отдельный файл
`<runtime-dir>/fbs_observer/observations.sqlite3`. Рабочие остатки, резервы,
себестоимость, товарный капитал, финансовый и партнёрский отчёты этот файл
не читают. Наблюдатель не вызывает применение Lifecycle и не создаёт очереди
пересчётов. Старые учётные данные остаются на месте.

Изоляция нужна также для идентификаторов заказов: их добавление в рабочую
базу само по себе могло бы поменять выбор канала и себестоимости в отчётах.
Отключить только физические списания недостаточно.

## Сбор

- Расписание существующего сервиса: один раз в час, на 38-й минуте.
  Расписание официальных снимков остатков FBS не меняется.
- В начале копируются только идентификаторы уже известных незавершённых
  заказов из рабочей базы, открытой в `mode=ro` с `query_only=ON`.
  Состояния учёта, прошлые переходы, цены и старый cursor не копируются.
  Предельный объём начального импорта — 50 000 заказов; превышение даёт ошибку.
- Первое окно поиска новых заказов — последние 30 дней. Затем поиск идёт
  от предыдущей успешно завершённой границы с перекрытием в два часа.
  За цикл загружается не более десяти страниц по 1 000 заказов; незавершённое
  окно продолжается со своего сохранённого cursor в следующем цикле.
  Ошибка до записи страницы сохраняет входной cursor этой страницы.
- Известные незавершённые заказы обновляются независимо от возраста.
  Завершённые заказы продолжают проверяться, пока дата создания входит
  в последние 30 дней. Более позднее изменение старого завершённого заказа
  этим режимом не гарантируется.
- Отдельная проверка статусов ограничена 50 пакетами по 1 000 ID.
  Первыми идут незавершённые заказы, внутри каждой группы — давно не
  проверявшиеся. Статус, только что полученный вместе со страницей заказов,
  повторно не запрашивается. Пропущенный API-ответ сохраняет
  последнее известное состояние; он не означает завершение заказа.
- Повторы исходных наблюдений и переходов не создают дубликатов.
  Повторно увиденный неизменный статус обновляет время последней проверки.
  Одновременные циклы исключены отдельной блокировкой наблюдателя.

Это периодические наблюдения, а не полная история событий. Между часовыми
опросами возможны невидимые промежуточные переходы; API не сообщает точное
время каждого перехода. Сбор не восстанавливает пропущенную историю и сам
по себе не является контрольной моделью себестоимости.

## Нагрузка и диагностика

Сервис использует общий ограничитель запросов семейства `wb_fbs_orders`.
Он не берёт складскую блокировку и не пишет в рабочую SQLite. systemd
разрешает запись только в каталог наблюдателя и каталог API-ограничителя;
остальная файловая система доступна только для чтения. Память ограничена
256 МБ, приоритет CPU и диска снижен, цикл ограничен четырьмя минутами.

Команда `apps/wb_fbs_shadow.py --runtime-dir <state> observer-status` читает
результат последнего цикла без записи. В `observer_runs` сохраняются:
длительность, CPU, пиковая память, число API-запросов и повторов, ожидание
API-лимита, число изменённых строк базы наблюдателя (без DDL), объём файла,
новые наблюдения/переходы, пропуски статусов, незавершённый cursor и остаток
очереди проверки статусов. Возраст результата более двух часов — `stale`.
Журнал systemd дополнительно показывает остановку по timeout/лимиту памяти.

`bounded_partial` означает неполное окно, остаток проверки статусов, пропуски
или неизвестную схему статуса. `failed` завершает команду ненулевым кодом.
Исходные API-ошибки не копируются в диагностическую запись: сохраняется тип
ошибки, чтобы не записать токен или содержимое ответа с персональными данными.

## Включение и откат

Выпуск кода сам не включает таймер. Перед первым включением создаются
каталоги `<state>/fbs_observer` и `<state>/official_api_rate_budgets`,
проверяются версия сервиса и ограничения записи. Затем существующая команда
`business_data_maintenance.py … set-process --process-key fbs_shadow
--desired on --expected-revision <revision>` меняет только соответствующее
намерение владельца и таймер. Нужны свежая revision и чтение результата.
Разовый проверочный запуск использует тот же systemd-сервис и те же ограничения.

Для остановки используется та же команда с `--desired off` и свежей revision.
Уже собранная база сохраняется. После запуска наблюдателя откат к старой
версии poller допускается только с остановленным таймером: прежняя версия
писала в рабочую базу и применяла Lifecycle.

Приёмка: повторные наблюдения не дублируются; старые незавершённые заказы
получают новые статусы; ошибка API не теряет страницу; рабочие данные и
классификация финансовой операции одинаковы до и после тестового цикла.
На сервере отдельно проверяются установленная версия, активное часовое
расписание, результат цикла, нагрузка и отсутствие изменений учётного Lifecycle.
