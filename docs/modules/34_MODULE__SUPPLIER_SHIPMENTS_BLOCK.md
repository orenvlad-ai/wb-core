# 1. Contract

- Operator surface: in `Поставки`, inner tab `Расчёты` keeps the existing factory/WB supply calculators; inner tab `Реестр поставок` renders the read-only comparison matrix; inner tab `Счёт CNY` renders the server-side CNY account ledger; inner tab `От поставщика` embeds the supplier registry without an extra operator card/title wrapper.
- Supplier-only surface: authenticated role `supplier` on `GET /sheet-vitrina-v1/supplier` receives a dedicated production-focused template and explicit role-derived capabilities (`can_create_order`, `can_edit_composition`, no delete/documents/internal-costs/price-check). The internal role route continues to render the full existing template; `embedded=operator` is presentation context only and never an authorization boundary.
- Supplier list/detail/parse/create/update responses use a separate server-side allowlisted projection before HTTP serialization. It contains shipment and factual dates, target facility id/name, derived status/deadline, invoice/contract text metadata, supplier invoice currency/totals, safe product/extra line fields, `nm_id`, nomenclature name, match status and bounded validation messages. It never contains CNY ledger/payment/bank fields, approximate/exact landed costs, expenses completeness, internal purchase/reference prices, price conformity, financial rows/documents, document IDs, filenames, hashes, storage/runtime paths or download URLs. `admin`, `operator` and `supply_operator` retain the full internal read model.
- Supplier JSON writes are fail-closed through one strict root/metadata/line allowlist. Unknown or sensitive fields, including `target_facility_id`, `approx_yuan_rate`, financial summaries, document IDs/paths and reference purchase/price-conformity fields, return validation error before the application mutation. Line identity, barcode ownership, matching projection and internal price-conformity snapshots are rebound from trusted upload/persisted evidence, so supplier composition edits cannot mass-assign server-owned values.
- Supplier-safe registry has exactly eleven visible columns: planned date, deadline, actual shipment, actual FF acceptance, invoice number/date, target fulfillment, product quantity, matching, derived order status and the real Open action. Loading/empty/error rows use `colspan=11`; there are no hidden legacy cells, blank headers, supplier/cost/amount/upload/document columns or download actions.
- Supplier deadline is derived only from server-owned business today and planned/factual dates: `10+` calendar days is green; `1–9` and today are yellow; a past planned date is red with trilingual overdue text; an occurred factual shipment/acceptance is success `已出货 / Shipped / Отгружено`; missing/invalid planned date is neutral `—`. Russian `день/дня/дней` observes the `11–14` exception. The value is never persisted as independent business truth.
- Standalone supplier-facing labels in the order registry/card use `中文 / English / Русский` business wording. The main title is `订单登记表 / Order registry / Реестр заказов`; duplicated registry headings and the old subtitle are not rendered. In framed operator view the same template is configured as Russian-only: a single compact toolbar contains `Добавить заказ`, the multi-select `Фильтры` menu and `Столбцы`; `Выйти` and `Открыть отдельно` are not rendered in the embedded toolbar. Standalone logout/open and supplier-auth behavior remain unchanged, and the standalone-open link still points to `GET /sheet-vitrina-v1/supplier` without introducing an API route.
- Registry list UI separates `loading`, `loaded_empty`, `loaded_with_rows` and `error`: the initial DOM and in-flight list fetch show a compact loading state, while the empty text is rendered only after the list API has returned an empty shipment list. Standalone supplier empty text remains `暂无订单 / No orders yet / Заказов пока нет.`; operator embedded empty/loading/error text is Russian-only.
- Supplier registry table headers remain sticky and use a subtly stronger dark/violet surface plus visible lower border so header cells do not blend into order rows; horizontal scroll and row action semantics are unchanged.
- Internal/operator `Реестр заказов` and the saved order's `Документы` table each have their own compact `Столбцы` chooser. The registry chooser controls visibility and ordering, provides accessible up/down controls plus keyboard/drag reorder, and persists one browser-local `{visible, order}` preference; `Сбросить` restores the server-defined default. `Оплата поставщику` and `Распределение расходов` are visible by default. Registry headers use short labels such as `План. отгрузка`, `Факт. отгрузка`, `Приёмка ФФ`, `Кол-во`, `Сумма`, `Оплачено`, `Себест.` and `Расходы`, while full meanings remain in `title` and accessible names. Registry, document, product-composition and expense tables use bounded content-oriented widths, moderate padding, one-line cells, ellipsis/title disclosure for long values and compact collapsed allocation/parser diagnostics; no browser preference is financial truth. Successful product matching is a focusable accessible green check. Invoice and contract actions are distinguishable without hover as `INV ↓` and `Дог. ↓`, retaining `title`, `aria-label`, focus and permission/disabled semantics. The fixed supplier-only projection and its DOM remain unchanged and cannot share the operator keys.
- Visible order card/form UI does not render editable `Supplier` or `Customer`. Supplier metadata is fixed server-side to `HanShang Technology`; the registry shows this fixed value in `供应商 / Supplier / Поставщик` with fallback for legacy rows. Customer is kept backward-compatible in stored/API payloads but is not required by create/save and is not shown.
- Visible order product rows do not render `our_sku`/`SKU` fields. Matching still may keep legacy `internal_sku` in storage for backward compatibility, but the supplier/order UI shows source-owned `Barcode` plus server-owned `平台ID / nmId / nmId` and `我方品名 / Our item name / Номенклатура` as read-only identity fields.
- Registry matching column is `匹配 / Matching / Матчинг` in standalone supplier UI and `Матчинг` in operator embedded UI; compact registry values are `OK` when every product line is matched and `Check`/`Проверить` otherwise depending on UI mode.
- Settings surface: `Настройки` is a right-side common WebCore shell action next to `Выйти`, not a main tab. Direct `GET /sheet-vitrina-v1/settings` remains backward-compatible by rendering the same shell with active settings content; the embedded body uses two groups, `Справочники` and `Пользователи`. `Справочники` contains `Номенклатура`, `Группы SKU`, `Договоры` and `Инвойсы` without reload; `Номенклатура` is the default dictionary subsection and any browser-local tab/column state is UI preference only, not runtime truth. `Пользователи` requires `settings + manage_users` and is not part of supplier shipment truth.
- Runtime truth is server-owned:
  - original XLSX files live under `<runtime_dir>/supplier_invoices/files/<shipment_id>/<safe_filename>`;
  - staged uploads live under `<runtime_dir>/supplier_invoices/uploads/<upload_id>/<safe_filename>`;
  - settings-uploaded trade document files live under `<runtime_dir>/trade_documents/files/<document_type>/<document_id>/<safe_filename>`;
  - SQLite stores upload metadata, shipment headers, editable line details, persisted price conformity fields, nomenclature rows, trade document rows and invoice-contract links.
- Archived WebCore Data MCP compatibility exposes this contour only for legacy auth-gated read-only calls: `get_supplier_shipments_registry`, `get_supplier_shipment_full_details`, `list_supply_artifacts`, `get_supply_artifact` and the allowlisted business-table tools. It is not a normal acquisition path. Compatibility artifact reads use opaque refs resolved from server-owned runtime DB rows, never accept filesystem paths, never expose absolute server paths and do not upload/delete/reparse/replay documents.
- `shipment_date` remains the persisted/API legacy field for backward compatibility but is semantically the planned shipment date. It is rendered as `计划出货日期 / Planned shipment date / Плановая дата отгрузки`, is the only required manual date after parse, and is validated server-side even though the UI disables save until it is present. Read responses may also expose `planned_shipment_date` as a non-persisted alias equal to `shipment_date`.
- Supplier shipment headers persist nullable `target_facility_id` plus nullable resolved display `target_facility_name`. A standalone authenticated `supplier` creates and saves an order without choosing a facility: supplier-safe writes reject `target_facility_id`, the card renders a read-only `Назначается оператором` value, and storage keeps both target fields `NULL` until assignment. Internal `admin`/`operator`/`supply_operator` create still requires one explicit active facility and rejects missing, unknown or inactive ids. Those internal roles may assign an active facility to an existing unassigned order before FF acceptance; exact id/name readback is authoritative, while supplier list/detail remain readable and show the assigned name without exposing a selector or active-facility options. No default facility or backfill exists. Facility-specific planning excludes unassigned orders from inbound coverage until assignment, and downstream receipt/allocation paths that require a facility remain fail closed. A completed receipt cannot be retargeted through ordinary header edit.
- The own-FBS replenishment calculator uses `official_fbs_stock_snapshot_v1`: the latest complete official FBS generation from the warehouse registry, with current active mapping, dense catalog identity, current business date and the existing 30-minute freshness limit. A newer partial attempt does not replace a still-fresh complete generation. Missing, stale or incomplete stock blocks calculation; only a proven dense omission under the official complete-catalog policy is zero. The shared quantity reader has no lifecycle or cost dependency. Official declared stock is used directly without lifecycle reserve subtraction and is not described as certified physical inventory. Status, persisted result/evidence and Excel bind the selected warehouse, generation/digest and capture time. New results leave legacy physical/reserved fields null; historical saved results/exports remain unchanged and the UI identifies their old source.
- National `orderCount` demand, demand windows/estimation, horizon, inbound scopes and batch rounding are unchanged. The existing Moscow-only national-demand restriction remains; WB FBO stock remains excluded. This source switch does not modify lifecycle, physical warehouse accounting or source collection.
- The independent own-FBS fulfillment-order calculator has an explicit inbound scope. `selected_facility` is the safe default and includes only active supplier orders assigned to the chosen facility. `all_active` is an operator-selected planning view that removes only the facility assignment filter and counts each eligible unassigned or other-facility order once. Both scopes still require server-derived `production`/`in_transit`, an authoritative matched nmId and positive quantity; neither changes shipment targets, lifecycle rows, receipts or regional allocation truth. The calculation result/evidence/export always discloses the selected scope and warns that all-active volume is common production/in-transit stock, not simultaneous regional coverage.
- Supplier shipment headers expose nullable factual dates `actual_shipment_date` (`实际出货日期 / Actual shipment date / Фактическая дата отгрузки`) and `actual_ff_acceptance_date` (`实际入仓日期 / Actual ФФ acceptance date / Фактическая дата приёмки на ФФ`). One server-owned resolver uses repository business-time semantics and derives: no occurred facts = `production` / `На производстве`; `actual_shipment_date <= business_today` without occurred acceptance = `in_transit` / `В пути с DD.MM.YYYY`; occurred acceptance = `accepted_ff` / `Принято на ФФ с DD.MM.YYYY`. All create/update/list/detail/MCP/downstream read models consume this resolver. Legacy invalid/future/inconsistent rows stay readable with `order_status_warnings`; impossible evidence is not silently treated as an occurred boundary.
- A single exact audited legacy terminal signal, `legacy_ff_accepted_without_date`, represents a historically accepted shipment whose factual acceptance date is unknowable. It has lower precedence than a real `actual_ff_acceptance_date`, renders `Принято на ФФ · дата неизвестна`, leaves both factual fields `NULL`, and excludes the shipment from factory/WIP projections. It creates no FF receipt, FF cost layer, stock quantity or capital. Ordinary create/update payloads cannot change the signal; only the guarded reconciliation runner can activate or reverse it, with an exact shipment/invoice identity, reason, provenance, actor, evidence/request/apply fingerprints and an immutable row in `sheet_vitrina_v1_supplier_shipment_historical_status_events`.
- Application/API validation requires strict ISO `YYYY-MM-DD`, rejects either factual date after canonical business today, and rejects acceptance earlier than shipment when both exist. Planned `shipment_date` may be future. Saving acceptance still uses the existing guarded SKU-level FF cost/stock materialization; changing an already materialized acceptance remains blocked and is outside the shipment-date correction flow.
- Supplier shipment headers additionally expose nullable optional `approx_yuan_rate` (`预估人民币汇率 / Estimated CNY rate / Примерный курс юаня, ₽/¥`). Create/update accept decimal numbers only when present, require `> 0`, store blank as `NULL`, and list/detail/read-model responses return blank legacy rows as `null` plus unavailable derived fields. Status-only PATCH, rematch, price-check and contract-link operations preserve the stored rate.
- Supplier shipment list/detail responses expose advisory derived fields `approx_invoice_cost_rub = invoice_amount_total * approx_yuan_rate` when rate and positive invoice total are available, and `approx_landed_cost_per_unit_rub = ((invoice_amount_total * approx_yuan_rate) + factual_supply_expenses_rub) / product_qty_total` only when rate, positive invoice total, positive product quantity and at least one persisted factual expense line are available. UI table column `预估成本 / Est. cost / Ориент. себестоимость, ₽/шт` renders `—` when calculation is unavailable and never renders missing data as `0`.

# 1.1 Trade Documents Registry

- `Настройки -> Договоры` renders only active `contract` documents. The table omits a type column and shows number, date, supplier, linked invoice count, source, file, updated time and actions. - `Настройки -> Инвойсы` renders only active `invoice` documents. The table omits a type column and shows number, date, supplier, `Сумма invoice`, linked contract state, source, file, updated time and actions. Unlinked invoices show `Не привязан`; the link/change selector is built only from active contracts. Linked invoices expose an idempotent operator-only unlink action that removes only the invoice->contract row.
- Supported files are `.pdf`, `.jpg`, `.jpeg`, `.png`, `.xlsx`. PDF/JPG/PNG are stored as files; contract metadata extraction is best-effort and bounded.
- Contract uploads attempt to fill `number` and `document_date` automatically. XLSX files are read through `openpyxl`; PDF files first use `pdftotext`/embedded text when available and then bounded first-page OCR if runtime tools are installed. Runtime OCR dependencies are `poppler-utils`, `tesseract-ocr`, `tesseract-ocr-eng`, `tesseract-ocr-chi-sim` and optionally `tesseract-ocr-rus`. JPG/PNG files use the same Tesseract language selection over the original image. Missing OCR tools remain non-fatal and produce parser warnings.
- OCR for image-only PDFs is first-page only. It renders bounded strategies through `pdftoppm` (page-size tolerant low DPI first, then grayscale/top-crop/higher-DPI fallbacks) and tries Tesseract `psm` values `6`, `11`, `4`, `3` with the available subset of `eng+chi_sim+rus`. The parser stops when both number and date are found; it does not OCR all contract pages.
- Contract number follows the MVP rule: the first non-empty document line is authoritative input, with labels such as `Contract No`, `Contract No.`, `Contract Number`, `No.`, `№`, `Контракт №`, `Договор №`, `合同编号` and `合同号` stripped when present. If OCR produces a bilingual heading such as `KOHTPAKT Nb ... CONTRACT J ...`, the parser extracts the repeated number candidate instead of storing the whole heading. If the first line is only a generic heading (`Contract`, `Договор`, `合同`), the parser searches the nearest top header lines for the actual number instead of storing the generic heading. Contract date is searched only in a bounded header fragment and normalized to `YYYY-MM-DD` for formats such as `YYYY-MM-DD`, `YYYY.MM.DD`, `YYYY/MM/DD`, `DD.MM.YYYY`, `MM/DD/YYYY`, `2026年5月13日`, `May 13, 2026`, `13 May 2026` and Russian month names.
- Contract parser metadata stores safe diagnostics under `parsed_metadata_json.diagnostics`: OCR availability, engine, selected languages, strategy used, attempt count, whether OCR text was non-empty, and whether number/date were found. It does not store or expose full OCR text beyond the existing first non-empty line metadata used for bounded debugging.
- Manual `number`/`document_date` values on upload remain authoritative. If parser values are different, the manual values are stored on the document row while parsed values and warnings remain in `parsed_metadata_json`/`warnings_json`. Upload API responses expose `parsed_number`, `parsed_document_date`, `parser_warnings` and `parser_errors`.
- New and updated trade documents never persist an empty supplier when no manual or parsed supplier is available: they use canonical `DEFAULT_SUPPLIER_NAME = HanShang Technology`. Manual supplier input wins over parsed/default values, and parsed supplier wins over default when available.
- `apps/sheet_vitrina_v1_trade_documents_backfill.py --runtime-dir <runtime_dir> --apply` backfills existing active documents idempotently: empty `supplier_name` gets the canonical default supplier, contract rows with empty `number` or `document_date` are reparsed from their stored runtime file, and non-empty/manual values are preserved. Repeated runs do not rewrite already filled rows.
- XLSX invoice uploads through settings are parsed with the existing supplier invoice parser when applicable. Parsed metadata may fill invoice no/date, contract no/date, supplier, currency, totals, warnings and errors. Settings invoice upload creates only a document record; it does not create a supplier shipment/order card.
- Settings upload deduplicates active settings documents by `document_type + file_sha256` and returns the existing document instead of creating another row for the same file.
- Supplier shipment create from the existing invoice parser flow creates or finds an `invoice` document record, writes `invoice_document_id` to `sheet_vitrina_v1_supplier_shipments`, and keeps the existing `GET .../{shipment_id}/invoice` download backward-compatible.
- Legacy shipments with `source_file_path` and no `invoice_document_id` are backfilled idempotently into `invoice` document records. The record references the existing runtime invoice file path; physical legacy invoice files are not moved or deleted by the backfill.
- `sheet_vitrina_v1_invoice_contract_links` allows one primary contract per invoice and many invoices per contract. Exact active contract candidates are found by contract number and date. If supplier shipment creation/backfill finds exactly one active contract candidate, it auto-links the invoice to that contract; zero or multiple candidates are returned as non-destructive candidate/status data.

# 1.2 Supplier Order Documents

- Supplier order PDF documents are scoped to one saved supplier shipment/order (`supplier_order_id` = shipment id). Runtime truth is server-owned:
  - PDF originals live under `<runtime_dir>/supplier_financial_documents/files/<supplier_order_id>/<document_id>/<safe_filename>`;
  - SQLite table `sheet_vitrina_v1_supplier_financial_documents` stores document metadata, parser/rate status and raw/normalized parse JSON;
  - SQLite table `sheet_vitrina_v1_supplier_financial_expense_lines` stores normalized expense lines by document/order.
- Canonical order-document checklist still exposes Invoice, contract, logistics/customs and informational evidence, but supplier payment and fee readiness are dynamic server projections rather than global required literals. Posted canonical CNY documents produce one row per actual `Оплата поставщику`; zero or partial payment produces exactly one future missing payment row. Every actual payment has exactly one logical fee block with zero or more fee lines, and a partial order additionally has exactly one anonymous `Комиссии к следующей оплате` placeholder. At 100% both future placeholders disappear, but every actual fee block must still be complete. A compact green fee row shows payment number/date/amount, fee-line count and total; missing evidence is red, and weak/ambiguous linkage is yellow with details. Internal `bank_transfer_application`/VTB/MT103 parsing remains historical compatibility and may feed the canonical ledger, but never creates a separate required red payment row. Browser/localStorage is not payment or fee truth.
- Supported ordinary supplier-order financial document types are `logistics_quote`, `logistics_invoice`, `customs_declaration`, `bank_control_statement`, non-CNY `bank_transfer_application`, `bank_fee_statement` and `packing_list`. Financial PDFs are parsed through the text-layer parser; packing lists are accepted as `.xls`/`.xlsx` and parsed as workbook documents. CNY conversion purchase and supplier CNY payment PDFs are routed to the canonical CNY account ledger instead of being duplicated as ordinary financial documents. Factory invoices/payments, any parallel SKU allocator and WB mutations remain out of this module scope; line allocation is owned only by the canonical warehouse cost proof.
- Financial document upload accepts `.pdf`, `.xls` and `.xlsx`. PDF documents first attempt text-layer extraction; runtime prefers `pdftotext` when available, then `pypdf`. OCR is not an MVP dependency for this parser and missing text/OCR returns controlled `parse_error`/warnings instead of silent failure. Packing-list workbooks use `openpyxl` for `.xlsx` and `xlrd` for `.xls`; missing workbook parser dependencies are controlled parser errors, not raw UI exceptions. The ordinary upload preview projects every result emitted by that same canonical parser as a stable selectable result: classification, type/category, key document fields, amount/currency, confidence, reasons and warnings. Results are selected by default when importable; the operator may deselect individual lines and confirm persists only the selected expense lines under one parent source document. Stable result IDs are rebound to the staged SHA and reparsed result set, selection evidence (including unselected IDs) stays on the parent, repeat confirmation is idempotent, and weak/ambiguous/ignored evidence remains visible before confirmation. The UI replaces raw English parser warnings with a short Russian status while retaining technical text in collapsed details.
- For customs declarations, if the primary `pdftotext` extraction recognizes the document but misses gross weight or customs value, parsing retries against the same stored PDF through `pypdf` and accepts the fallback only when those critical fields are recovered. The same bounded fallback applies to VTB/MT103-like transfer applications when primary extraction recognizes the document but misses critical transfer fields.
- Customs parsing preserves all aggregate fields and additionally emits `goods_items[]` only from explicit item headers and labeled position evidence: DT position number, original name, numeric quantity, unit, barcode, customs code and source model when present. Missing item fields remain empty with warnings; aggregate weight/amount or a neighbouring number is never substituted for position quantity/name. Existing stored customs PDFs may be reparsed read-only during accounting-package assembly when their saved payload predates this item projection.
- Parser is deterministic/rule-based and returns normalized fields, expense lines, parser version (`supplier_financial_document_parser_v8`), classification reasons/warnings and confidence/status. Classification uses whole-document structural headers, account/period sections and bank identity before incidental phrases in payment purpose: `Счёт на оплату` inside a proven VTB statement cannot reclassify it as a logistics invoice. Unsupported or insufficient structure returns `needs_review`. It detects Transitplus logistics quotes, logistics invoices like World-Logistik invoices 103/113, aggregate customs declarations (`ДТ`) with customs fee/duty/VAT totals, customs value and aggregate gross/net item weights, bank control statements headed `ВЕДОМОСТЬ БАНКОВСКОГО КОНТРОЛЯ ПО КОНТРАКТУ`, VTB/MT103-like `ЗАЯВЛЕНИЕ на перевод` applications and VTB account statements. Transitplus quote parsing is table-layout aware for both `pypdf` and production `pdftotext -layout` shapes: when service labels are separated from the `Общая стоимость` column, or rows are extracted as `1 Стоимость доставки 14360` without `USD`, the parser maps known service labels/trailing amounts plus numbered cost-column rows and a total-sum sanity check to `delivery_cost`, `customs_payments_and_fees`, `ecological_fee`, `brokerage_services`, `company_commission` and `insurance`. The quote cargo-value parser is anchored to the `Оценочная стоимость груза` label and accepts USD aliases such as `USD`, `долл.`, `долл`, `долларов` and `долл. США`; CNY/yuan value is populated only when the same cargo-value line explicitly contains a yuan/CNY value. A total-validated numbered block wins over percent-like label values such as `Страховая ставка, % 1,0%`.
- `bank_control_statement` normalized parse stores УНК, statement date, resident, non-resident/vendor, contract number/date, contract currency/code/amount or raw non-numeric amount marker, full Section II `payment_operations[]` rows (`row_index`, operation date, payment direction, operation type code, payment currency/code/amount, contract currency/code/amount and expected repatriation date when present), legacy first payment operation date/amount fields for compatibility, total payment-operation amount and calculated balance when present. Missing fields add parser warnings and set review status instead of failing storage.
- `bank_transfer_application` normalized parse stores transfer application number/date, normalized execution status/time when present, debit account as available, currency, transfer amount, amount in words, ordering customer, payer INN/country/address when present, beneficiary/customer, beneficiary account/address/country, beneficiary bank, SWIFT/BIC, bank address/country/clearing code when present, payment details, parsed contract reference/number/date, charges mode such as `OUR`, sender-to-receiver info and regulatory reporting when present. The VTB parser is layout-tolerant for `pypdf` and production `pdftotext -layout`: it extracts values from MT103/SWIFT tags (`50`, `56`, `57`, `59`, `70`, `72`, `77B`), right-column label/value rows, spaced account numbers, tag `32` amounts, and global `CONTRACT <number> DD <date>` fallback when tag `70` returns only a label. Missing critical fields add parser warnings and set review status instead of failing storage.

Order identity is built from shipment invoice/metadata/linked contract fields; document identity is built from normalized parse fields. Contract number+date is a strong match, contract number alone is probable when no date conflict exists, amount/currency and vendor are supporting only, and explicit contract number/date conflict yields `order_match_status=mismatch`. For `bank_control_statement`, the ВБК itself is matched to the order by contract, then a concrete Section II payment operation is matched to the order invoice by amount/currency with operation date/type/direction as supporting evidence; `contract_amount` is not treated as the invoice payment amount. Missing or ambiguous payment-operation match keeps the upload stored but returns `needs_review` with explicit warnings. Poor parse evidence yields `needs_review`; uploads are not hard-blocked. Match fields are exposed as `order_match_status`, `order_match_reasons`, `order_match_warnings`, `matched_contract_number`, `matched_contract_date`, `payment_operation_match_status`, `payment_operation_match_reasons`, `payment_operation_match_warnings` and `matched_payment_operation` in the document payload/normalized parse.

Zero and partial are yellow; exact 100% is green. # 1.4 CNY Account Ledger

- `Поставки -> Счёт CNY` is the server-owned management ledger for CNY currency account costing. It is not бухгалтерский налоговый валютный учёт, does not calculate FX revaluation, and does not write `cost_price`, 1C, WB/web-vitrina metrics or Google Sheets/GAS.
- Canonical currency documents live once in `sheet_vitrina_v1_cny_documents`. Supported document types are `cny_conversion_purchase`, `supplier_cny_payment`, `bank_fee`, `opening_balance` and `adjustment`. A document may carry nullable `source_order_id`/`context_order_id`; this only records upload/context provenance and does not mean a whole conversion belongs to that supplier order.
- Canonical ledger rows live in `sheet_vitrina_v1_cny_ledger_operations`. Supported operation types are `opening_balance`, `conversion_in`, `supplier_payment_out`, `conversion_fee`, `transfer_fee` and `adjustment`. Money and rates are calculated with Decimal-compatible storage strings, not float arithmetic.
- Conversion purchase increases CNY balance and RUB value balance by the actual RUB debit; conversion fees in RUB, when parsed/provided, are included in purchased-CNY RUB value. Average account rate after conversion is `balance_rub_value / balance_cny`.
- Supplier CNY payment decreases CNY balance at average account rate before payment. The order payment component is `paid_cny * average_rate_before`; the order effective CNY rate is weighted across all linked supplier-payment operations as `sum(payment_currency_rub_cost) / sum(paid_cny)`. The legacy `approx_yuan_rate` remains manual/advisory and is never overwritten by ledger replay.
- Supplier transfer/bank fees are separate order cost components. RUB fees imported from RUB-account statements add directly to order exact bank fees and do not touch the CNY ledger. CNY fees imported from CNY-account statements create canonical `bank_fee` documents and `transfer_fee` operations, consume CNY at average account rate, update `cny_bank_fee_rub`, and remain a separate fee component rather than being mixed into the effective CNY payment rate.
- Replay is deterministic and server-side after create/update/import of currency documents, after CNY document upload from an order, and after explicit `POST /v1/sheet-vitrina-v1/supply/cny-account/replay`. Replay sorts exact bank execution/accepted datetimes between exact operations. Date-only rows use deterministic same-day financial slots: `opening_balance`, `conversion_in`, `conversion_fee` and `transfer_fee`/`bank_fee` are treated as start-of-day operations in that priority, while date-only `supplier_payment_out` and `adjustment` are treated as end-of-day operations; document created time/id/type are only tie-breakers inside the same slot. This lets same-day conversion CNY be available for same-day supplier payment without a manual sequence field, including when the payment has an execution time but the conversion document has only a date. Such date-only rows are still marked `needs_review` / `date_only_deterministic_sequence` whenever other operations share the date, but they are counted unless they are explicitly `blocked`.
- The CNY write boundary is explicit: parse/validation precedes one canonical document save; deterministic ledger replacement and replay-state save are then confirmed by a fresh operation/state readback. Only after that proof may own-product-capital and warehouse projection preparation run. All affected shipments and canonical mapped product-line `internal_nm_id` values are resolved first, expense certifications are reset in one atomic batch, one idempotent coalesced targeted request is enqueued for the exact source revision and the projection outbox is drained once. There is no nested per-shipment rebuild or drain.
- A certification-only projection resolves SKU closure from both own-capital events and canonical mapped supplier shipment product lines, so a shipment with mapped SKU but no payment/capital event is still exact. A truly line-less shipment can close only as an explicit proven terminal no-op. Missing shipment identity, an unmapped product line or any other unexplained empty closure remains a fail-closed data-quality blocker.
- Full success and proven no-op return `200`. If canonical CNY state and ledger readback are durable but later derived replay is recoverably pending/error, the write returns `202` contract `sheet_vitrina_v1_cny_write_pending_v1` with `operation_applied=true`, `readback_confirmed=true`, `pending_phase`, `retryable`, a Russian operator message and `durable_retry_identity`. `4xx/5xx` never claims that an already readback-confirmed CNY write was not saved. Same-file retry reuses the natural key, ledger operation, capital layer and queue identity.
- Historical backfill is supported by replaying all currency documents from the beginning of the stored period and updating existing supplier orders that already have linked `supplier_cny_payment` documents. If there is no positive CNY balance before a historical payment, replay blocks with `missing_opening_balance`; it does not borrow `approx_yuan_rate` and does not fabricate a historical course.
- Order rows/detail expose ledger-derived read-only fields: `cny_ledger_effective_rate` (`Курс CNY по счёту` / effective management ledger rate), `cny_payment_currency_rub_cost`, `cny_paid_amount`, `cny_bank_fee_rub`, `cny_calculation_status`, `cny_calculation_error` and `cny_calculated_at`.

No consumer can retain a legacy value when the detail proof is blocked, and green presentation requires `exact_cost_status=certified`, including financial readiness plus a matching active source/calculation fingerprint. They are absent recursively from supplier-role responses.
- Blocked/diagnostic statuses include `missing_opening_balance`, `insufficient_balance`, `payment_not_linked`, `parse_error`, `ambiguous_allocation`, `document_date_missing` and `no_supplier_payment`. These statuses are visible in CNY account status/ledger and supplier order CNY fields; blocked rows do not emit fake RUB costs.
- The VTB conversion purchase parser extracts `document_number`, date, RUB debit account, CNY credit account, RUB amount, CNY amount, bank rate, bank/branch, accepted/execution datetime and status text from tolerant Russian text-layer PDF parsing. The VTB bank-statement parser extracts account/period/balances, payment rows, conversion rows and fee rows, including operation number from Russian payment purpose text, CNY/RUB turnovers, contract/invoice/ref evidence and fee categories (`transfer_fee`, `currency_control_fee`, `currency_control_vat`, `other_bank_fee`). Raw user PDFs are runtime files only and are not committed; tests use sanitized text fixtures.
- Current bounded allocation model is one supplier CNY payment document -> one supplier order through `source_order_id`. The document/operation schema keeps payment operations independent from conversion provenance and does not block future split allocation rows, but UI for one payment covering multiple orders is not implemented in this checkpoint.

# 2. Parser

- Parser version is `supplier_invoice_parser_v2`. It uses `openpyxl`, searches every worksheet for the invoice table, and recognizes flexible base headers including `NO.`, `MODELS / （型号）`, `NAME & SPECIFICATION / （品名规格）`, `QTY (PCS) / （数量）`, `U.PRICE / （单价）` and `AMOUNT / （总价）`.
- Barcode-column detection is layered and independent of an absolute column: normalized semantic aliases (`Barcode`, `Bar code`, factory typo `Braocde`, `条形码`, `條形碼`, `ШК`, `Штрихкод`, `Штрих-код`) win first; otherwise a barcode-like column between `NAME & SPECIFICATION` and `QTY` is accepted from confirmed relative structure; the current D position is used only when the complete `A=NO., B=MODELS, C=NAME & SPECIFICATION, E=QTY, F=U.PRICE, G=AMOUNT` shape and the D value profile both confirm it. Multiple confirmed candidates fail with an explicit ambiguous-column error, and numeric QTY/price/amount columns are excluded from candidates.
- Parsed diagnostics expose only safe structural evidence: worksheet, header row, method `header_alias` / `relative_structure` / `positional_d`, column number/letter, normalized header and bounded value-profile counts. They never expose invoice contacts, bank details or barcode values.
- Barcode extraction is lossless and stored as a string. Spaces/NBSP and one leading Excel apostrophe are removed; text-cell leading zeroes and exact safe integer numeric cells are preserved without float/scientific-notation output. Non-digit text, non-integral or negative numbers, numeric values above Excel's exact-integer boundary and scientific-notation text are rejected instead of rounded or guessed. Thirteen digits are strong current-template evidence, not a global identity rule or checksum requirement.
- Financial-document parser aggregates customs declaration item weights from goods blocks (`35 Вес брутто`, `38 Вес нетто`) when the text layer exposes per-item rows. For current GTD `10131010/100626/5187132`, expected parser aggregates are `customs_gross_weight_kg ~= 9784.60`, `customs_net_weight_kg ~= 8806.18`, `total_goods_count = 28` and `total_places = 465`.
- `RMB`/`CNY`/`¥` invoice currency is normalized to `RMB`; declared invoice totals may be read from post-table `Total`/`总值` rows when the value is not available in pre-table metadata.
- Contract metadata is extracted from ordinary cells, merged-cell values and bounded workbook drawing XML text. Supported labels include `Contract No`, `Contract No.`, `Contract Number`, `Contract Date`, `Date of Contract`, `合同号`, `合同编号`, `合同日期`, `下单日期`; date formats such as `2026.5.13`, `2026-05-13`, `13.05.2026` and `5/13/2026` normalize to `YYYY-MM-DD`.
- The document-registry contract parser is separate from invoice table parsing: it reads only bounded header text, stores `parser_version=contract_metadata_parser_v2`, and returns non-fatal warnings/errors instead of blocking contract file storage when metadata cannot be extracted.
- Merged-cell/fill-down blocks are handled for product type markers:
  - `高清膜` / `smk` -> `clear`
  - `防窥膜` / `(Anti-Spy)` -> `anti_spy`
  - `磨砂膜` / `(Matte)` -> `matte`
- Compatible model aliases such as `iPhone 15 / 16` stay as one invoice row. Parser-derived classification is exposed only as `source_product_type` / `source_match_key` evidence and never occupies the authoritative `product_type` / `match_key`; parser does not split quantity into separate SKU rows.
- Extras such as OPP packets, labels and cards are stored as `line_type=extra`, not product SKU rows. Product-row comments may mention OPP/labels/cards as packaging instructions without turning the product line into an extra.
- Every product row carries `barcode`; extras may leave it empty. Missing or losslessly unreadable product barcodes remain explicit unmatched evidence, and an invoice without a confirmable barcode column is rejected.

# 4.1 Canonical per-line cost proof

Operator shipment detail exposes `supplier_cost_breakdown` and the product-table column `Себестоимость, ₽/шт.`. This is a read projection of the same Decimal allocation helper used by the six-warehouse functional replay; it is not a second formula. Every invoice line retains quantity, unit/value CNY, RUB capital, unit cost and document components. Supplier payments and bank fees allocate by invoice value; logistics and customs 1010 by quantity; customs 2010/5010 by invoice value. Each component carries stable source identity, number/date/status, allocation method and optional actual CNY/RUB rate evidence. Remainder assignment is deterministic, and document, line and shipment conservation controls are part of the payload.

Изменение `invoice_no`, `invoice_date` или invoice currency — cost-driving source change: certification снимается и targeted replay ставится немедленно, потому что все три поля входят в canonical supplier fingerprint, а invoice date участвует в effective-date provenance. Queue revision нормализует как nested, так и flat shipment detail, поэтому metadata-only изменение не может повторно использовать уже завершённую revision. Этапный статус реестра берётся из flow provenance выбранной поставки, а не из агрегатного SKU balance: provisional соседняя партия не понижает доказанно certified поставку и наоборот.

A shipment is fail-closed as one accounting unit: any product row without a stable line ID/exact nmID mapping, positive quantity or positive invoice value becomes an explicit blocker. Valid sibling rows may remain visible for diagnosis, but no line capital/unit cost or certified supplier flow is published from a partial invoice.

Unavailable cost is `null`/`—` plus explicit blockers, never a synthetic zero. When the canonical proof has an exact number but `financial_readiness` is pending, the number stays visible and yellow; it becomes green only when financial readiness is true and the current source/calculation fingerprints equal the fingerprints persisted in the active immutable warehouse version. Fingerprints are frozen per shipment in version-scoped `sheet_vitrina_v1_warehouse_supplier_cost_states`, so certification remains provable after a shipment reaches FF and its cost evidence becomes nested in the append-only ledger. If a legacy active version predates this projection, the guarded supplier-certification replay may append a version-scoped correction with exact `supersedes` provenance only when every frozen target per-SKU quantity/capital plus contributing payment, CNY-fee and China→FF document identity match the current canonical proof and every contributing mutable source row has a server-owned revision timestamp strictly earlier than the immutable version; equal whole-second timestamps fail closed as ambiguous. A deterministic CNY ledger replay preserves `updated_at` for byte-semantic unchanged operations, so a no-op/global replay does not manufacture target drift. Global source-group watermarks remain diagnostics rather than gates because unrelated informational documents and WB/FF/history projections may advance without changing that supplier flow; the complete current supplier-source manifest is still pinned and transactionally rechecked before apply. Changed target allocation/revision or unprovable supplier sources fail closed so stale WAC/capital cannot become green. It never writes into the immutable base row and an append-only rollback tombstone restores the prior effective state. Every cost-affecting supplier/CNY/financial mutation keeps the existing targeted shipment/SKU replay and resets compatibility completeness where applicable; opening the card never starts a global rebuild. Raw JSON is nested behind the secondary technical disclosure; the primary disclosure is Russian document arithmetic.

The unpaginated shipment collection reads all compact cost summaries in one coherent SQLite snapshot and returns only aggregate fields needed by the registry. It does not run or serialize a full line/document proof per list row; the full `supplier_cost_breakdown` graph is detail-only. Legacy approximate columns are calculated from the same batch-captured headers/documents, while every exact-looking aggregate is overwritten by the canonical proof gate, including explicit unavailable blockers.

Rematch invalidation compares accounting identity/value fields rather than the complete rendered line dictionary. A changed nmID, stable product/match key, invoice identity, quantity or value still clears certification, queues targeted replay and is rejected after an append-only FF receipt. A label or other diagnostic/presentation refresh may update the rendered nomenclature after receipt without changing capital, certification or the frozen ledger identity.

A posted supplier payment must have a positive factual `rub_value_delta`; a counted transfer fee must likewise have a positive RUB valuation. Missing/zero RUB valuation is an explicit canonical blocker and cannot certify an expense-only or zero cost. `declared_invoice_total`, calculated invoice total and `match_status` are fingerprinted; `checksum_error` blocks publication and any change clears certification and queues targeted replay. When any canonical blocker exists, legacy header-level `exact_*` aggregates are cleared as well, so the header and per-line proof cannot disagree.

Refreshing the proof after a financial-document action merges only the returned canonical proof fields into the live card draft. The browser re-reads all header, date, CNY-rate, metadata and line inputs after the request; unsaved operator edits are never replaced by older persisted values. If unsaved quantity/price/amount or cost-driving metadata differs from the server source, both line and aggregate cost proofs are suppressed until save rather than attached to the wrong draft.

# 18. Own invested-capital producer contract

Supplier shipment product lines are an authoritative allocation boundary for module 45. Create/update is atomic: every product row must resolve deterministically to an authoritative nmID and contain positive quantity, unit price and line amount. Any unmatched/ambiguous/invalid row rejects the whole file; no pseudo-SKU, partial save or discretionary money allocation is allowed.

The first posted CNY supplier payment activates the full physical invoice composition; every posted payment and related bank fee allocates capital across all product lines by invoice value. Paid-equivalent quantity remains diagnostic audit only. Actual shipment and FF acceptance dates create persisted stage boundaries; upload time and planned dates do not. Expense lines enter landed cost only when both parent document and line have eligible `parsed`/`confirmed` state; informational/needs-review/failed/duplicate/unmatched/excluded documents do not. Direct-RUB bank-fee rows use their own operation date, while CNY fees remain owned by the CNY ledger. The parent `Комиссии банка` UI row shows the sum of eligible child expenses rather than `—`; expanded detail exposes source, RUB/CNY amount and CNY-ledger operation/rate provenance. Every allocation carries document/line provenance plus deterministic dedupe. A cost-affecting source change/archive resets compatibility `expenses_complete` and queues targeted replay; setting that legacy flag true never bypasses payment/document/allocation readiness or fingerprint certification. Details are in modules 45 and 48.

# 19. Confirmation, archive and supplier-document correction contract

- Header-only shipment changes omit `lines`. Compatibility payloads that repeat every persisted line unchanged are also treated as header-only; legacy lines without a source-owned barcode remain field-for-field unchanged. A real legacy composition edit remains blocked by the barcode-identity guard.
- `actual_shipment_date` changes still require `factual-dates/preview` followed by `factual-dates/confirm`. `actual_ff_acceptance_date` is no longer a routine editable field: it is the read-only result of the Stage 7A `Принять на FF` document. Legacy preview and new-order HTTP save reject an FF-acceptance change. The guided XLSX preview pins one facility, exact SKU identity, actual quantity, FBS/FBO allocation, discrepancies and expenses; final confirmation remains fail-closed until both writer epoch and exact opening are active.
- The owner gate for that XLSX pins the immutable receipt business effect (request/source/workbook, epoch/date, document and movement identities, per-SKU FBS/FBO quantity/capital normalization and expenses), not a continually moving whole-warehouse balance. Current pool/aggregate/dependent digests remain preview evidence. Final confirm may rebase only those before-images after exact INTEGER quantity and centralized canonical-kopek global parity passes while the shared warehouse writer lock excludes functional publication and FBS suffix drain through T1 plus commit. Raw sub-kopeck differences with identical canonical totals remain diagnostic/auditable. The collector stays active; a held drain resumes its unchanged append-only sequence exactly once after the short window.
- Stage 7C may pin a clean in-transit shipment as `excluded_pending_receipt`: empty factual acceptance, no aggregate receipt source key, no supplier FF cost layer and exact integral shipment/line parity are all required. It contributes no opening quantity/capital and no historical FBS debit. After cutover only guided `Принять на FF` may accept it, exactly once; the transaction owns factual date, legacy receipt identity, exact aggregate and facility/pool quantity/capital/expenses, discrepancy evidence and subsequent accepted-quantity cost materialization. Any partial or concurrent acceptance fails closed.
- Supplier financial/CNY uploads are parse-and-stage first. Preview creates no active document, expense line, ledger operation, completeness reset or replay request. Generic preview exposes all stable parser-result IDs and confirm binds each token to its selected result IDs; only those selected lines are saved under the single parent document, with unselected/weak evidence retained in parent parse metadata. Confirm requires the exact staged SHA, unchanged parser result set and current target revision, then performs server readback before returning one of `created`, `already_present`, `restored` or `relinked`. Multi-file confirmation validates the complete selected token set before committing and returns one exact result per file; repeat confirm is idempotent.
- The account UI distinguishes saved/success, saved/pending and genuine failure. A `202` is yellow, clears the file input and immediately reloads the CNY read model. A lost/ambiguous upload response is reconciled by exact file SHA plus its ledger-operation readback; confirmed application is never rendered as red, and retrying the same file remains idempotent.
- The operator UI completes that readback before opening the bank-fee selector. A durable preview with `active_saved=false` is verified by its durable-preview readback and is intentionally absent from the active-document list; preview/cancel therefore remains side-effect free and cannot produce a false client-side readback error.
- A bank statement separates supplier payment, logical commission and atomic bank rows. The exact payment anchor plus fee currency is the operator's logical selection boundary: all VK, SWIFT and other tariff debits matched to that payment form one atomic group even when categories, bank document numbers, references or operation dates differ. The group retains every atomic category/reference/date and semantic identity for audit. Rows without a payment anchor fall back to reference/category grouping and otherwise remain atomic. Durable previews pin `logical_grouping_version`; a deploy that changes this contract deletes only the stale inactive sidecar and regenerates it from the same content-addressed source, while stale confirm fails before writes. VAT is derived from purpose semantics (`Включая НДС`, separate `НДС за ВК`, `НДС не облагается`), never from currency or row count. Confirmation accepts only explicitly selected logical groups; admissible new groups start selected, atomic rows are disclosed inside their group, and already-imported/conflict/weak/ignored rows remain in separate collapsed non-selectable blocks. Target revision drift rejects confirm before writes and repeat confirm is a no-op.
- Same SHA in another shipment is `conflict_other_shipment`, never generic success. Explicit relink moves the one existing CNY document, rebuilds its one ledger/capital chain, resets certification for old and new shipments and queues one combined targeted request. Parsed payment evidence never silently replaces the shipment from the request route.
- Every operator-owned active financial or CNY row has an exclusion action. System rows render a disabled action with a reason. Exclusion is audited archive, not physical deletion: active projection, needs-review and active expense/CNY/capital participation disappear; source file and audit remain. Linked derived CNY rows direct the operator to their source financial document.
- Active and archived projections are separate. `excluded` never maps to `needs_review`, and archived expense lines are absent from active source manifests, summaries, allocation controls and downstream capital layers. Exact SHA restore reuses the archived document; a semantic match with another SHA requires an explicit warning, confirmation and reason.
- Exact cost presentation uses canonical `exact_cost_status`: `certified` is green only after shared financial readiness and fingerprint certification, `provisional`/`pending` is yellow with its precise reason, and `unavailable` suppresses the number and shows blockers. `expenses_complete` alone never makes cost green, while packing list and bank-control statement cannot keep it yellow. Stage cost shows only a fingerprint-valid current active functional version; queued/running replay is `Ожидает пересчёта`, errors show the blocker, stale numbers are hidden, and a shipment that left the stage shows neutral `Не применяется`.

`apps/supplier_26gn390_recovery.py` remains the bounded legacy invoice-136 recovery. `apps/supplier_26gn527_bank_statement_recovery.py` is read-only legacy diagnosis; its independent apply is disabled because it required another full-DB backup and separate replay. The canonical coupled 26GN527/warehouse recovery is `apps/warehouse_cost_unified_recovery.py`: query-only dry-run by default, explicit exact-fingerprint apply, one shared writer lock, exact shipment/supply/statement/box identities, durable pre-write plan journal and per-step checkpoints, resumable idempotent steps, target-scoped undo manifests, post-apply no-op readback and zero Finance-raw/full-DB-copy I/O. When supplier documents and own-capital events are already confirmed and only durable cost queues remain, `apps/warehouse_cost_queue_replay.py` pins one or more exact invoice/shipment/document/expense/capital/queue revisions, rejects overlapping non-target SKU queues, publishes one bounded functional version plus target-scoped economics, and proves complete queues, unchanged target quantities and non-target digests before returning a repeated no-op.

# 20. Content-addressed bank statements and assignment boundary

- A physical bank PDF is stored once at `supplier_financial_sources/sha256/<prefix>/<sha256>/source.pdf`; deterministic parser output is cached beside it. The versioned deploy migration `supplier_financial_source_migration_v1` validates every source byte, links equal SHA sources to one inode, updates document paths atomically, keeps a private rollback manifest and supports exact idempotent readback/rollback.
- Generic upload confirmation rows live in `supplier_confirmation_runtime.sqlite3`; bank-specific selection previews are private fsynced JSON sidecars. Neither is active accounting evidence in the main runtime DB. Save failure removes the owned staging artifact. Expired previews are cleaned by the repo-owned bounded lifecycle, and an unreferenced source is removed only when no active document or other durable preview needs it.
- Legacy financial files that have no document reference are handled only by the deploy-time `supplier_financial_orphan_lifecycle_v1`: after 24 hours they leave the active files tree for a private hash-verified quarantine, then remain recoverable for 30 days before evidence-backed deletion. - A logical commission group owns one or more semantic atomic operation IDs. Parser work, source-file creation and group selection happen before that transaction. Derived ledger/warehouse replay happens afterward; a busy replay is an explicit resumable `202 pending`, never a second business commit or raw `500`.
- The VTB regression fixture proves that one source SHA may already own payment operations №7/№11 in `26GN527` while `26GN582` is offered only the distinct payment №9 commission group: 951.08 RUB currency-control fee plus 12,574.81 RUB SWIFT fee, total 13,525.89 RUB. # 21. Unified recovery-policy boundary

Supplier confirmation remains one short atomic source transaction with durable
preview/readback. Its dependent warehouse/cost closure is a central T1
operation: exact supplier-cost queues, factual correction, affected
functional rows and economics before images are journaled under
`warehouse_recovery_policy_v1`. A semantic repeat is T0 and creates no recovery
row or bytes. Commission regression is covered by the exact multi-invoice
queue replay and cannot open Finance raw or call the full-store backup API.

Historical `supplier_26gn390_recovery` and
`supplier_cny_payment_10_recovery` apply entrypoints are diagnostic-only and
fail closed. Any earlier paragraph describing a fresh coherent backup for
these bounded paths is historical and superseded by module 51.

## Business-date factual projection

`actual_shipment_date` and `actual_ff_acceptance_date` are functional business
boundaries. A correction recorded or published later reprojects the affected
supplier flow beginning with the earliest old/new factual date; technical
`created_at`, `effective_at` and `published_at` are audit fields only. The
source row, exact source revision, targeted queue completion, immutable
functional version and `warehouse_business_projection_v1` current switch are
one transaction. A failed candidate leaves the shipment row and both
last-good projections unchanged.

For each exact date the replay removes only the stable supplier flow from
production/China→FF and places the same quantity/capital in its business-date
stage. Same-SKU flows from other shipments and every non-target SKU remain
byte-semantic invariant. Apply waits for terminal job readback and signals an
open Vitrina to reread table data automatically.
