# 1. Contract

- Operator surface: in `Поставки`, inner tab `Расчёты` keeps the existing factory/WB supply calculators; inner tab `Реестр поставок` renders the read-only comparison matrix; inner tab `Счёт CNY` renders the server-side CNY account ledger; inner tab `От поставщика` embeds the supplier registry without an extra operator card/title wrapper.
- Supplier-only surface: authenticated role `supplier` on `GET /sheet-vitrina-v1/supplier` receives a dedicated production-focused template and explicit role-derived capabilities (`can_create_order`, `can_edit_composition`, no delete/documents/internal-costs/price-check). The internal role route continues to render the full existing template; `embedded=operator` is presentation context only and never an authorization boundary.
- Supplier list/detail/parse/create/update responses use a separate server-side allowlisted projection before HTTP serialization. It contains shipment and factual dates, derived status/deadline, invoice/contract text metadata, supplier invoice currency/totals, safe product/extra line fields, `nm_id`, nomenclature name, match status and bounded validation messages. It never contains CNY ledger/payment/bank fields, approximate/exact landed costs, expenses completeness, internal purchase/reference prices, price conformity, financial rows/documents, document IDs, filenames, hashes, storage/runtime paths or download URLs. `admin`, `operator` and `supply_operator` retain the full internal read model.
- Supplier JSON writes are fail-closed through one strict root/metadata/line allowlist. Unknown or sensitive fields, including `approx_yuan_rate`, financial summaries, document IDs/paths and reference purchase/price-conformity fields, return validation error before the application mutation. Line identity, barcode ownership, matching projection and internal price-conformity snapshots are rebound from trusted upload/persisted evidence, so supplier composition edits cannot mass-assign server-owned values.
- Supplier registry has exactly ten visible columns: planned date, deadline, actual shipment, actual FF acceptance, invoice number/date, product quantity, matching, derived order status and the real Open action. Loading/empty/error rows use `colspan=10`; there are no hidden legacy cells, blank headers, supplier/cost/amount/upload/document columns or download actions.
- Supplier deadline is derived only from server-owned business today and planned/factual dates: `10+` calendar days is green; `1–9` and today are yellow; a past planned date is red with trilingual overdue text; an occurred factual shipment/acceptance is success `已出货 / Shipped / Отгружено`; missing/invalid planned date is neutral `—`. Russian `день/дня/дней` observes the `11–14` exception. The value is never persisted as independent business truth.
- Standalone supplier-facing labels in the order registry/card use `中文 / English / Русский` business wording. The main title is `订单登记表 / Order registry / Реестр заказов`; duplicated registry headings and the old subtitle are not rendered. In framed operator view the same template is configured as Russian-only: title `Реестр заказов`, title row actions `Добавить заказ`, `Выйти`, then `Открыть отдельно`; the standalone-open link points to the existing `GET /sheet-vitrina-v1/supplier` UI route and does not introduce a new API route.
- Registry list UI separates `loading`, `loaded_empty`, `loaded_with_rows` and `error`: the initial DOM and in-flight list fetch show a compact loading state, while the empty text is rendered only after the list API has returned an empty shipment list. Standalone supplier empty text remains `暂无订单 / No orders yet / Заказов пока нет.`; operator embedded empty/loading/error text is Russian-only.
- Supplier registry table headers remain sticky and use a subtly stronger dark/violet surface plus visible lower border so header cells do not blend into order rows; horizontal scroll and row action semantics are unchanged.
- Visible order card/form UI does not render editable `Supplier` or `Customer`. Supplier metadata is fixed server-side to `HanShang Technology`; the registry shows this fixed value in `供应商 / Supplier / Поставщик` with fallback for legacy rows. Customer is kept backward-compatible in stored/API payloads but is not required by create/save and is not shown.
- Visible order product rows do not render `our_sku`/`SKU` fields. Matching still may keep legacy `internal_sku` in storage for backward compatibility, but the supplier/order UI shows source-owned `Barcode` plus server-owned `平台ID / nmId / nmId` and `我方品名 / Our item name / Номенклатура` as read-only identity fields.
- Registry matching column is `匹配 / Matching / Матчинг` in standalone supplier UI and `Матчинг` in operator embedded UI; compact registry values are `OK` when every product line is matched and `Check`/`Проверить` otherwise depending on UI mode.
- Settings surface: `Настройки` is a right-side common WebCore shell action next to `Выйти`, not a main tab. Direct `GET /sheet-vitrina-v1/settings` remains backward-compatible by rendering the same shell with active settings content; the embedded body uses two groups, `Справочники` and `Пользователи`. `Справочники` contains `Номенклатура`, `Группы SKU`, `Договоры` and `Инвойсы` without reload; `Номенклатура` is the default dictionary subsection and any browser-local tab/column state is UI preference only, not runtime truth. `Пользователи` requires `settings + manage_users` and is not part of supplier shipment truth.
- Runtime truth is server-owned:
  - original XLSX files live under `<runtime_dir>/supplier_invoices/files/<shipment_id>/<safe_filename>`;
  - staged uploads live under `<runtime_dir>/supplier_invoices/uploads/<upload_id>/<safe_filename>`;
  - settings-uploaded trade document files live under `<runtime_dir>/trade_documents/files/<document_type>/<document_id>/<safe_filename>`;
  - SQLite stores upload metadata, shipment headers, editable line details, persisted price conformity fields, nomenclature rows, trade document rows and invoice-contract links.
- WebCore Data MCP exposes this contour only as auth-gated read-only business data: `get_supplier_shipments_registry`, `get_supplier_shipment_full_details`, `list_supply_artifacts`, `get_supply_artifact` and the allowlisted business-table tools. MCP artifact reads use opaque refs resolved from server-owned runtime DB rows, never accept filesystem paths, never expose absolute server paths and do not upload/delete/reparse/replay documents.
- `shipment_date` remains the persisted/API legacy field for backward compatibility but is semantically the planned shipment date. It is rendered as `计划出货日期 / Planned shipment date / Плановая дата отгрузки`, is the only required manual date after parse, and is validated server-side even though the UI disables save until it is present. Read responses may also expose `planned_shipment_date` as a non-persisted alias equal to `shipment_date`.
- Supplier shipment headers expose nullable factual dates `actual_shipment_date` (`实际出货日期 / Actual shipment date / Фактическая дата отгрузки`) and `actual_ff_acceptance_date` (`实际入仓日期 / Actual ФФ acceptance date / Фактическая дата приёмки на ФФ`). One server-owned resolver uses repository business-time semantics and derives: no occurred facts = `production` / `На производстве`; `actual_shipment_date <= business_today` without occurred acceptance = `in_transit` / `В пути с DD.MM.YYYY`; occurred acceptance = `accepted_ff` / `Принято на ФФ с DD.MM.YYYY`. All create/update/list/detail/MCP/downstream read models consume this resolver. Legacy invalid/future/inconsistent rows stay readable with `order_status_warnings`; impossible evidence is not silently treated as an occurred boundary.
- A single exact audited legacy terminal signal, `legacy_ff_accepted_without_date`, represents a historically accepted shipment whose factual acceptance date is unknowable. It has lower precedence than a real `actual_ff_acceptance_date`, renders `Принято на ФФ · дата неизвестна`, leaves both factual fields `NULL`, and excludes the shipment from factory/WIP projections. It creates no FF receipt, FF cost layer, stock quantity or capital. Ordinary create/update payloads cannot change the signal; only the guarded reconciliation runner can activate or reverse it, with an exact shipment/invoice identity, reason, provenance, actor, evidence/request/apply fingerprints and an immutable row in `sheet_vitrina_v1_supplier_shipment_historical_status_events`.
- Application/API validation requires strict ISO `YYYY-MM-DD`, rejects either factual date after canonical business today, and rejects acceptance earlier than shipment when both exist. Planned `shipment_date` may be future. Saving acceptance still uses the existing guarded SKU-level FF cost/stock materialization; changing an already materialized acceptance remains blocked and is outside the shipment-date correction flow.
- Supplier shipment headers additionally expose nullable optional `approx_yuan_rate` (`预估人民币汇率 / Estimated CNY rate / Примерный курс юаня, ₽/¥`). Create/update accept decimal numbers only when present, require `> 0`, store blank as `NULL`, and list/detail/read-model responses return blank legacy rows as `null` plus unavailable derived fields. Status-only PATCH, rematch, price-check and contract-link operations preserve the stored rate.
- Supplier shipment list/detail responses expose advisory derived fields `approx_invoice_cost_rub = invoice_amount_total * approx_yuan_rate` when rate and positive invoice total are available, and `approx_landed_cost_per_unit_rub = ((invoice_amount_total * approx_yuan_rate) + factual_supply_expenses_rub) / product_qty_total` only when rate, positive invoice total, positive product quantity and at least one persisted factual expense line are available. UI table column `预估成本 / Est. cost / Ориент. себестоимость, ₽/шт` renders `—` when calculation is unavailable and never renders missing data as `0`.
- Shipment headers may persist `order_status` only as a backward-compatible derived cache. It is not independent business truth. A status-only PATCH is idempotent only when the requested value equals the current derived value and rejects every divergent/unknown value; the UI renders badges and no status selector.
- Factory-order supplier-registry inbound uses `order_status` server-side: only `production` and `in_transit` shipments can become `Товары в пути от фабрики`; `accepted_ff` shipments are excluded because their goods are already accepted on FF and must enter calculation through FF stock, not as factory inbound.
- When `actual_ff_acceptance_date` is saved, `packages/application/our_wb_costs.py` materializes versioned SKU-level FF source cost evidence and `packages/application/ff_stock_ledger.py` creates an idempotent ledger receipt by fully matched product-line quantity. The receipt source key is `supplier_shipment_acceptance:<shipment_id>`; repeat cannot duplicate quantity. `packages/application/canonical_cost_engine.py` consumes these sources into recognized/paid components and FF WAC. Late cost evidence creates a new component/layer version and downstream replay from factual effective date; it never changes the receipt quantity or uses upload time as business date.

## Unified cost/physical boundary (2026-07-01)

Supplier registry is the only physical source for `На производстве` and `Производство → ФФ`. Full matched line quantity remains physical even when payment is partial or cost evidence is missing. CNY payments are allocated proportionally across every matched product line and create paid-equivalent quantity; no random SKU selection or unmatched buffer is allowed. `accepted_ff` removes the shipment from registry transit and hands quantity to the idempotent FF ledger receipt. Supplier tables/documents are source truth and are never mutated by the canonical backfill.
- In the supplier registry table, `Currency / Валюта`, compact `Документы`, derived `Статус заказа` and `Действия` remain separate columns. Status is a read-only neutral/info/success badge with the factual date in `DD.MM.YYYY`; no role receives a manual selector. A compact multi-status filter is UI preference only: default selected statuses are `На производстве` + `В пути`, `Все` returns every loaded row, and `Принято на ФФ` can be included explicitly without mutating server truth.
- Changing an existing `actual_shipment_date` through ordinary Save creates one row in `sheet_vitrina_v1_supplier_shipment_factual_corrections`. It pins shipment, old/new value, actor, timestamp, source/reason `operator_factual_date_correction`, stable request/apply fingerprints, persisted phase/progress/report/backup/error and one-active-job uniqueness. UI phases are `Сохраняем изменение`, `Пересчитываем зависимые данные`, `Проверяем результат`; controls and duplicate saves are blocked, page reload reads the same persisted job, and success rereads detail/list/matrix. A combined factual-date correction plus unrelated card edits is rejected explicitly rather than silently dropping either change.
- Correction builds and verifies a coherent disposable candidate before activation. Apply uses `BEGIN IMMEDIATE`, optimistic target/non-target/pre-cutover digests, derived cache update, bounded canonical table replacement only when materialized, a `0600` SQLite online backup, integrity/idempotency verification and in-place restore without inode replacement on post-commit failure. Legacy `own_capital` dispatch evidence is preserved audit-only and reported, so `movement identity already exists with different factual evidence` cannot partially commit or leak to the operator. `apps/supplier_shipment_factual_date_correction.py` is dry-run by default; apply requires the exact current fingerprint, explicit backup directory and optional exact invoice/document constraints.
- The same runner can prepare one combined reconciliation candidate for an already-correct factual field and one historical terminal status change. When old and new factual values are equal it records source/reason `historical_factual_date_adoption` and `factual_date_already_correct_before_apply=true`; it never claims that the guarded apply first changed the date. The candidate fingerprints both target headers, rebuilds once, proves unchanged non-target/FF evidence, and is zero-change on the second run. Reversal is another exact fingerprinted action referencing the prior event; schema deployment alone does not activate any exception or correct production business rows.
- Orders can be deleted by operator role only. Delete controls use UI-level confirmation: the first click opens an inline confirmation with cancel, and backend DELETE is called only by the explicit confirm action. While confirmation is open, row clicks do not open the order card. Confirmed delete removes the DB order/lines, archives the invoice document link when present, and makes shipment-scoped invoice download unavailable without deleting the physical runtime invoice file.
- Saved order cards expose `关闭 / Close / Закрыть` in standalone supplier UI and `Закрыть` in operator embedded UI; the visible `重新匹配 / Re-match / Пересопоставить` action is not rendered in the supplier/order card. The rematch API remains available for internal compatibility and always resolves current product lines by their persisted source-owned barcode. Legacy product lines without barcode are left unchanged and return an explicit skipped diagnostic; type/model/alias compatibility fallback is forbidden.
- Internal saved order cards keep the existing inner tab switcher: `Состав поставки` owns dates/metadata, product lines, extras and totals, while `Документы` owns invoice/contract controls and the full server-built checklist/financial tooling. The supplier template does not generate this tab or any invoice/contract/package/download controls in DOM; it keeps only production dates, supplier invoice metadata/totals, editable product/extra composition and Save/Close.

# 1.1 Trade Documents Registry

- `Настройки -> Договоры` renders only active `contract` documents. The table omits a type column and shows number, date, supplier, linked invoice count, source, file, updated time and actions. Operator inline edit is limited to `number`, `document_date` and `supplier_name`; it never mutates file metadata, archive status or invoice links, and blank supplier edits fall back to canonical default supplier on the backend.
- `Настройки -> Инвойсы` renders only active `invoice` documents. The table omits a type column and shows number, date, supplier, `Сумма invoice`, linked contract state, source, file, updated time and actions. Unlinked invoices show `Не привязан`; the link/change selector is built only from active contracts. Linked invoices expose an idempotent operator-only unlink action that removes only the invoice->contract row.
- Supported files are `.pdf`, `.jpg`, `.jpeg`, `.png`, `.xlsx`. PDF/JPG/PNG are stored as files; contract metadata extraction is best-effort and bounded.
- Contract uploads attempt to fill `number` and `document_date` automatically. XLSX files are read through `openpyxl`; PDF files first use `pdftotext`/embedded text when available and then bounded first-page OCR if runtime tools are installed. Runtime OCR dependencies are `poppler-utils`, `tesseract-ocr`, `tesseract-ocr-eng`, `tesseract-ocr-chi-sim` and optionally `tesseract-ocr-rus`. JPG/PNG files use the same Tesseract language selection over the original image. Missing OCR tools remain non-fatal and produce parser warnings.
- OCR for image-only PDFs is first-page only. It renders bounded strategies through `pdftoppm` (page-size tolerant low DPI first, then grayscale/top-crop/higher-DPI fallbacks) and tries Tesseract `psm` values `6`, `11`, `4`, `3` with the available subset of `eng+chi_sim+rus`. The parser stops when both number and date are found; it does not OCR all contract pages.
- Contract number follows the MVP rule: the first non-empty document line is authoritative input, with labels such as `Contract No`, `Contract No.`, `Contract Number`, `No.`, `№`, `Контракт №`, `Договор №`, `合同编号` and `合同号` stripped when present. If OCR produces a bilingual heading such as `KOHTPAKT Nb ... CONTRACT J ...`, the parser extracts the repeated number candidate instead of storing the whole heading. If the first line is only a generic heading (`Contract`, `Договор`, `合同`), the parser searches the nearest top header lines for the actual number instead of storing the generic heading. Contract date is searched only in a bounded header fragment and normalized to `YYYY-MM-DD` for formats such as `YYYY-MM-DD`, `YYYY.MM.DD`, `YYYY/MM/DD`, `DD.MM.YYYY`, `MM/DD/YYYY`, `2026年5月13日`, `May 13, 2026`, `13 May 2026` and Russian month names.
- Contract parser metadata stores safe diagnostics under `parsed_metadata_json.diagnostics`: OCR availability, engine, selected languages, strategy used, attempt count, whether OCR text was non-empty, and whether number/date were found. It does not store or expose full OCR text beyond the existing first non-empty line metadata used for bounded debugging.
- Manual `number`/`document_date` values on upload remain authoritative. If parser values are different, the manual values are stored on the document row while parsed values and warnings remain in `parsed_metadata_json`/`warnings_json`. Upload API responses expose `parsed_number`, `parsed_document_date`, `parser_warnings` and `parser_errors`.
- New and updated trade documents never persist an empty supplier when no manual or parsed supplier is available: they use canonical `DEFAULT_SUPPLIER_NAME = HanShang Technology`. Manual supplier input wins over parsed/default values, and parsed supplier wins over default when available.
- `apps/sheet_vitrina_v1_trade_documents_backfill.py --runtime-dir <runtime_dir> --apply` backfills existing active documents idempotently: empty `supplier_name` gets the canonical default supplier, contract rows with empty `number` or `document_date` are reparsed from their stored runtime file, and non-empty/manual values are preserved. Repeated runs do not rewrite already filled rows.
- XLSX invoice uploads through settings are parsed with the existing supplier invoice parser when applicable. Parsed metadata may fill invoice no/date, contract no/date, supplier, currency, totals, warnings and errors. Settings invoice upload creates only a document record; it does not create a supplier shipment/order card.
- Settings upload deduplicates active settings documents by `document_type + file_sha256` and returns the existing document instead of creating another row for the same file.
- Supplier shipment create from the existing invoice parser flow creates or finds an `invoice` document record, writes `invoice_document_id` to `sheet_vitrina_v1_supplier_shipments`, and keeps the existing `GET .../{shipment_id}/invoice` download backward-compatible.
- Legacy shipments with `source_file_path` and no `invoice_document_id` are backfilled idempotently into `invoice` document records. The record references the existing runtime invoice file path; physical legacy invoice files are not moved or deleted by the backfill.
- `sheet_vitrina_v1_invoice_contract_links` allows one primary contract per invoice and many invoices per contract. Exact active contract candidates are found by contract number and date. If supplier shipment creation/backfill finds exactly one active contract candidate, it auto-links the invoice to that contract; zero or multiple candidates are returned as non-destructive candidate/status data.
- Invoice download, linked contract no/date/download and operator-only contract select/upload controls are rendered in the saved order card tab `Документы`, not in `Состав поставки`. Supplier standalone view can see/download linked invoice/contract documents but cannot link/upload/archive.
- Contract archive is rejected while active invoice links point to that contract. Invoice archive removes the invoice-contract link. File rows are archived in DB; physical files are not removed by document archive.

# 1.2 Supplier Order Documents

- Supplier order PDF documents are scoped to one saved supplier shipment/order (`supplier_order_id` = shipment id). Runtime truth is server-owned:
  - PDF originals live under `<runtime_dir>/supplier_financial_documents/files/<supplier_order_id>/<document_id>/<safe_filename>`;
  - SQLite table `sheet_vitrina_v1_supplier_financial_documents` stores document metadata, parser/rate status and raw/normalized parse JSON;
  - SQLite table `sheet_vitrina_v1_supplier_financial_expense_lines` stores normalized expense lines by document/order.
- Canonical required order-document checklist types are `invoice`, `contract`, `logistics_quote`, `logistics_invoice`, `customs_declaration`, `bank_control_statement`, `bank_transfer_application`, `bank_fee_statement` (`Комиссии банка`) and `packing_list` (`Packing list / Упаковочный лист`). The checklist is built by the server from existing trade-document links, supplier financial/order documents and deterministic required types; missing required rows are returned with status `Не загружен`, not inferred from browser-local state. Checklist/status chips use red for `Не загружен`, yellow for `Проверить` and green for `Загружен`/confirmed rows.
- Supported ordinary supplier-order financial document types are `logistics_quote`, `logistics_invoice`, `customs_declaration`, `bank_control_statement`, non-CNY `bank_transfer_application`, `bank_fee_statement` and `packing_list`. Financial PDFs are parsed through the text-layer parser; packing lists are accepted as `.xls`/`.xlsx` and parsed as workbook documents. CNY conversion purchase and supplier CNY payment PDFs are routed to the canonical CNY account ledger instead of being duplicated as ordinary financial documents. Factory invoices, factory payments, SKU cost allocation and WB mutations remain out of this module scope.
- Financial document upload accepts `.pdf`, `.xls` and `.xlsx`. PDF documents first attempt text-layer extraction; runtime prefers `pdftotext` when available, then `pypdf`. OCR is not an MVP dependency for this parser and missing text/OCR returns controlled `parse_error`/warnings instead of silent failure. Packing-list workbooks use `openpyxl` for `.xlsx` and `xlrd` for `.xls`; missing workbook parser dependencies are controlled parser errors, not raw UI exceptions.
- For customs declarations, if the primary `pdftotext` extraction recognizes the document but misses gross weight or customs value, parsing retries against the same stored PDF through `pypdf` and accepts the fallback only when those critical fields are recovered. The same bounded fallback applies to VTB/MT103-like transfer applications when primary extraction recognizes the document but misses critical transfer fields.
- Parser is deterministic/rule-based and returns normalized fields, expense lines, parser version (`supplier_financial_document_parser_v6`), warnings and confidence/status. It detects Transitplus logistics quotes, logistics invoices like World-Logistik invoices 103/113, aggregate customs declarations (`ДТ`) with customs fee/duty/VAT totals, customs value and aggregate gross/net item weights, bank control statements headed `ВЕДОМОСТЬ БАНКОВСКОГО КОНТРОЛЯ ПО КОНТРАКТУ`, and VTB/MT103-like `ЗАЯВЛЕНИЕ на перевод` applications. Transitplus quote parsing is table-layout aware for both `pypdf` and production `pdftotext -layout` shapes: when service labels are separated from the `Общая стоимость` column, or rows are extracted as `1 Стоимость доставки 14360` without `USD`, the parser maps known service labels/trailing amounts plus numbered cost-column rows and a total-sum sanity check to `delivery_cost`, `customs_payments_and_fees`, `ecological_fee`, `brokerage_services`, `company_commission` and `insurance`. The quote cargo-value parser is anchored to the `Оценочная стоимость груза` label and accepts USD aliases such as `USD`, `долл.`, `долл`, `долларов` and `долл. США`; CNY/yuan value is populated only when the same cargo-value line explicitly contains a yuan/CNY value. A total-validated numbered block wins over percent-like label values such as `Страховая ставка, % 1,0%`.
- `bank_control_statement` normalized parse stores УНК, statement date, resident, non-resident/vendor, contract number/date, contract currency/code/amount or raw non-numeric amount marker, full Section II `payment_operations[]` rows (`row_index`, operation date, payment direction, operation type code, payment currency/code/amount, contract currency/code/amount and expected repatriation date when present), legacy first payment operation date/amount fields for compatibility, total payment-operation amount and calculated balance when present. Missing fields add parser warnings and set review status instead of failing storage.
- `bank_transfer_application` normalized parse stores transfer application number/date, normalized execution status/time when present, debit account as available, currency, transfer amount, amount in words, ordering customer, payer INN/country/address when present, beneficiary/customer, beneficiary account/address/country, beneficiary bank, SWIFT/BIC, bank address/country/clearing code when present, payment details, parsed contract reference/number/date, charges mode such as `OUR`, sender-to-receiver info and regulatory reporting when present. The VTB parser is layout-tolerant for `pypdf` and production `pdftotext -layout`: it extracts values from MT103/SWIFT tags (`50`, `56`, `57`, `59`, `70`, `72`, `77B`), right-column label/value rows, spaced account numbers, tag `32` amounts, and global `CONTRACT <number> DD <date>` fallback when tag `70` returns only a label. Missing critical fields add parser warnings and set review status instead of failing storage.
- Bank order documents (`bank_control_statement`, `bank_transfer_application`) are verified against the current supplier order on upload/read. Order identity is built from shipment invoice/metadata/linked contract fields; document identity is built from normalized parse fields. Contract number+date is a strong match, contract number alone is probable when no date conflict exists, amount/currency and vendor are supporting only, and explicit contract number/date conflict yields `order_match_status=mismatch`. For `bank_control_statement`, the ВБК itself is matched to the order by contract, then a concrete Section II payment operation is matched to the order invoice by amount/currency with operation date/type/direction as supporting evidence; `contract_amount` is not treated as the invoice payment amount. Missing or ambiguous payment-operation match keeps the upload stored but returns `needs_review` with explicit warnings. Poor parse evidence yields `needs_review`; uploads are not hard-blocked. Match fields are exposed as `order_match_status`, `order_match_reasons`, `order_match_warnings`, `matched_contract_number`, `matched_contract_date`, `payment_operation_match_status`, `payment_operation_match_reasons`, `payment_operation_match_warnings` and `matched_payment_operation` in the document payload/normalized parse.
- Expense lines store category/stage/description/amount/currency/amount_rub/VAT and inclusion flags. Logistics quote lines keep customs payments separate from logistics quote components, and possible/not-included export-document costs are marked reviewable rather than included in totals.
- Transitplus quotes require non-empty positive `delivery_cost` and `customs_payments_and_fees` when the quote total is positive. If those required amounts are missing or zero, the financial document status is `needs_review`; the UI shows a warning and quote-vs-invoice rate calculations are not produced from a partial USD base.
- Server-side USD/RUB CBR rate provider is a seam. Runtime may request official CBR XML by document date and, if an exact date is unavailable, stores the last official effective date before the requested date. Tests and local smokes use `StaticUsdRateProvider`. Rate failure does not reject upload; document rows persist with `rate_pending`/`fx_rate_missing`.
- CBR is a benchmark only. For quote-vs-invoice comparison the summary uses:
  - `implied_rate = invoice_amount_rub / linked_quote_usd_component`;
  - `spread_pct = implied_rate / cbr_usd_rate_on_invoice_date`;
  - `estimated_bank_rate_on_quote_date = cbr_usd_rate_on_quote_date * spread_pct`;
  - `quote_rub_equivalent = linked_quote_usd_component * estimated_bank_rate_on_quote_date`.
  UI labels this as `расчётный курс по правилу КП` / `оценочный банковский курс`, not as a VTB truth.
- Quote-vs-invoice rate inference is guarded by a CBR sanity band. If `implied_rate` or `estimated_bank_rate_on_quote_date` is radically outside the CBR-relative/normal RUB-USD range, the summary returns `rate_sanity_status=rejected`, keeps diagnostic rejected-rate fields, surfaces a `needs_review` warning and hides RUB-derived quote metrics (`КП всего ₽`, quote ₽/шт and quote ₽/кг) instead of falling back to CBR or showing копеечные values. In the shipment registry, rejected RUB quote cells render with a short warning display (`курс не подтверждён` for `КП всего ₽`, or the existing yellow `ждём счета` state for dependent quote ₽ rows whose USD source and denominator are present) and keep the exact sanity-check reason in cell metadata/tooltip. The quote-date CBR fallback is allowed only when a shipment has a КП but no logistics invoice documents.
- MVP auto-match candidate links logistics invoices to logistics-related quote components (`delivery_cost`, `brokerage_services`, `company_commission`, `insurance`) and excludes customs payments/federal customs totals. The summary status is `needs_review` and the UI shows reviewable warnings because exact line-level evidence is intentionally not assumed. If the linked quote USD component is incomplete, zero or missing, implied rate, estimated bank rate and delta are hidden instead of showing mathematically unsafe values.
- `Документы` UI shows single- or multi-file PDF/XLS/XLSX upload (`Добавить документ`), per-file upload status, a unified order document checklist/table, recognized fields, expense lines, original file download link when stored, status/warnings, package download actions and grouped compact summary: quote totals/logistics/customs USD, invoice fact/VAT RUB, customs fee/duty/VAT/total RUB, `расчётный курс по правилу КП`, absolute/relative deviation from CBR and `Счета минус КП-логистика`; `На штуку` metrics for quote delivery+customs RUB equivalent per supplier-order unit, fact delivery+customs per supplier-order unit and `Себестоимость на единицу товара` from exact CNY-ledger/confirmed-document fields; `На кг` metrics for logistics/customs/delivery+customs by quote gross weight and by actual customs-declaration gross weight; `% от стоимости` metrics for quote logistics/customs/total vs quote estimated cargo value and fact logistics/customs without VAT/customs with VAT/delivery+customs vs customs value. Document rows with `needs_review`/`mismatch` are visually marked as review warnings, and the same verification warnings are shown in recognized fields.
- `Банковская выписка для комиссий` is an operator-only supplier-order financial document type. Upload stores the parent VTB statement PDF/runtime metadata under the order, parses the full statement, anchors fee rows only to already-linked supplier CNY payment documents for that order, and returns a preview with payment anchor evidence, matched fees, ignored rows, currency totals, confidence, reasons and warnings. The preview creates no expense lines; `POST .../financial-documents/{document_id}/confirm-import` confirms strong/probable matches idempotently. Weak/date-only matches stay `needs_review` and are not auto-imported in this bounded checkpoint.
- Confirmed bank-statement fees create order expense lines with `source=bank_fee_statement`. RUB-account fee rows add RUB amount directly as bank-fee cost. CNY-account fee rows create linked canonical `bank_fee` CNY documents/`transfer_fee` ledger operations in the existing `Поставки -> Счёт CNY` ledger and use ledger average rate for RUB equivalent; bank-provided RUB equivalent is reference-only, not the management truth.
- `packing_list` stores workbook metadata/summary and line items without committing raw user workbooks to repo. The parser extracts document number/title, total cartons, total quantity, total gross weight kg, total volume m3, carton size, model count, average qty/carton and representative item lines. Merged/blank cells are carried forward only when deterministic; unreliable values produce warnings/`needs_review` instead of crashes. The order card `Документы` summary shows `Коробок`, `Товаров, шт`, `Вес брутто, кг`, `Объём, м³`, optional carton size/model count/average qty per carton and renders unavailable values as `—`, not `0`. WebCore Data MCP exposes the same parsed packing-list business evidence through read-only supplier registry/full-details/artifact/table tools: registry rows include `packing_list_total_cartons` plus aliases `packing_list_box_count`, `packing_list_carton_count` and `packing_list_total_boxes`; full-details/artifact parsed reads include bounded `packing_list_summary` and line samples without absolute paths or raw workbook blobs.
- Quote-weight metrics use only `logistics_quote.gross_weight_kg`; customs-weight metrics use only aggregate gross weight parsed from the customs declaration. If actual customs weight is missing, the UI/API expose unavailable values instead of falling back to quote weight and surface `Нет фактического веса из ДТ` only when a customs declaration document exists but the field was not parsed.
- Quote percent metrics use `quote_estimated_cargo_value_usd`; fact percent metrics use `total_customs_value_rub` from the customs declaration. Missing or zero denominators render unavailable values and short source warnings (`Нет стоимости груза по КП`, `Нет таможенной стоимости из ДТ`) rather than `0`, `NaN` or `Infinity`.
- On read, saved customs declaration, bank control statement and VTB transfer application documents from older parser payloads are refreshed from their already-stored runtime PDF when the normalized parse lacks critical fields or the stored parser version is older than the current parser. Saved logistics quotes from older parser payloads are refreshed only when `estimated_cargo_value_usd` is missing, so already-complete quote parses are not rewritten just because the parser version changed. `excluded` documents are not refreshed, and an operator `confirmed` status is preserved. Local regression probe `apps/supplier_financial_documents_mt103_probe.py` checks the real Desktop `Пакет документов/MT103_2.pdf` when available; the PDF and raw bank text are not committed.
- Protected routes are operator-only and follow the existing supplier shipment path:
  - unified checklist/read model: `/v1/sheet-vitrina-v1/supply/supplier-shipments/{shipment_id}/documents`;
  - all-documents package download: `/v1/sheet-vitrina-v1/supply/supplier-shipments/{shipment_id}/documents/archive.zip`;
  - logistics package download: `/v1/sheet-vitrina-v1/supply/supplier-shipments/{shipment_id}/documents/logistics-package.zip`;
  - list/upload collection: `/v1/sheet-vitrina-v1/supply/supplier-shipments/{shipment_id}/financial-documents`;
  - detail/patch status/delete: `/v1/sheet-vitrina-v1/supply/supplier-shipments/{shipment_id}/financial-documents/{document_id}`;
  - confirmed statement fee import: `POST /v1/sheet-vitrina-v1/supply/supplier-shipments/{shipment_id}/financial-documents/{document_id}/confirm-import`;
  - original file download: `/v1/sheet-vitrina-v1/supply/supplier-shipments/{shipment_id}/financial-documents/{document_id}/file`.
- `archive.zip` includes all available documents bound to the order plus `manifest.json`. `logistics-package.zip` includes only `contract`, all `bank_transfer_application` documents and `bank_control_statement` documents plus `manifest.json`. If required package documents are missing, the archive is still generated with available files and explicit `missing_required_types`/warnings in the manifest; silent partial packages are not allowed. Manifest `included[]` also carries document status, order-match status and per-document warnings so logistics packages cannot hide mismatch/needs-review evidence.
- Operator delete removes exactly one financial-document record, its expense lines and the stored file only when the file path belongs to that document's runtime storage directory. If the deleted financial document owns linked CNY ledger documents, those linked CNY documents are deleted through the source financial-document delete path and the ledger is replayed. Supplier CNY payment rows are deduped by linked financial document/idempotent payment attributes so a linked financial document and its canonical CNY ledger document do not render as duplicate `Оплата поставщику CNY` rows. Missing documents return controlled JSON 404; bulk delete is not part of the contract.

# 1.3 Supplier Shipment Registry Matrix

- `Поставки -> Реестр поставок` is an operator-only read-side matrix for comparing official supplier shipments. It does not create a parallel storage layer and does not call Google Sheets/GAS.
- Protected read-only route: `GET /v1/sheet-vitrina-v1/supply/supplier-shipments/registry`. Response contract is `sheet_vitrina_v1_supplier_shipment_registry` with `columns[]` for shipments, grouped `sections[]`, row ids, labels and per-shipment cells shaped as `{value, display}` plus bounded UI metadata such as `type=expenses-completeness` or exact-cost `status`.
- Protected completeness route: `PATCH /v1/sheet-vitrina-v1/supply/supplier-shipments/{shipment_id}/expense-completeness` stores operator-owned `expenses_complete` on the canonical supplier shipment header. Default is false (`Расходы не учтены полностью`). Browser/localStorage is not a source of truth for this status.
- Protected temporary comparison route: `POST /v1/sheet-vitrina-v1/supply/supplier-shipments/registry/compare-quote` accepts multipart `file` + `shipment_id`, parses the PDF with the existing logistics quote parser, and returns `sheet_vitrina_v1_supplier_shipment_registry_quote_comparison`. The uploaded quote is not saved as a financial document, supplier shipment or runtime source of truth.
- The matrix is built from existing runtime truth: supplier shipment headers/lines, supplier financial documents, financial expense lines and `build_financial_summary(..., shipment=...)`. Missing financial documents or denominators produce `value = null` rather than `0`, `NaN` or `Infinity`; КП rows with known absence reasons use short display states such as `нет КП`, `нет в КП`, `ошибка парсинга КП`, `нет стоимости груза в КП`, `курс не подтверждён` or `ждём счета`, with the full reason in cell metadata/tooltip. Plain `—` remains for unknown or not-applicable cells.
- The matrix and supplier-order list/detail also expose `Точная себестоимость, ₽/шт` / `exact_landed_cost_per_unit_rub`. It is derived server-side from exact CNY payment RUB cost from the CNY ledger, confirmed bank fees and confirmed factual logistics/customs expenses included in cost, divided by positive product quantity. If CNY payment cost or CNY-fee ledger RUB equivalent is unavailable, or quantity is missing/zero, the value renders `—` with `exact_cost_blockers`; it never falls back to `approx_yuan_rate`.
- The matrix does not expose `Ориентировочная себестоимость на ФФ, ₽/шт`; advisory `approx_yuan_rate` calculations remain bounded to internal supplier-shipment list/detail UI and are not supplier-role or registry truth. The advisory value is not final бухгалтерская себестоимость and must not be written into `cost_price`, 1C, WB/web-vitrina metrics, factory-order calculations, nomenclature purchase prices or any shared metric truth.
- Exact-cost visual status is driven only by `expenses_complete`: green when the operator marked `Расходы учтены`, yellow while `Расходы не учтены полностью`. Blank exact cost remains uncolored.
- Shipments are sorted by invoice date, then shipment/order date or upload/created date; newer shipments are rightmost. Every column header keeps invoice/order number, date, `Сравнить` checkbox and a server-derived status badge (`На производстве`, `В пути с DD.MM.YYYY`, `Принято на ФФ с DD.MM.YYYY`). The compact badge preserves sticky header, horizontal scroll, minimum column width and narrow layout and never uses color as its only meaning.
- Row groups are: A `Паспорт поставки`, B `КП логиста`, C `Нормализованные метрики по КП`, D `Сроки`, E `Физика груза`, F `Стоимость товара`, G `Факт расходов`, H `Нормализованные метрики факта / по ДТ`, I `Документы`. Passport keeps identity/supplier/logist/route/document-status rows only; order/invoice/planned/fact dates live in `Сроки`.
- `КП логиста` is the registry block for raw quote cost/value/weight/volume fields. `Нормализованные метрики по КП` contains КП-derived % rows, pure КП USD/кг rows by quote weight (`услуги логиста`, `таможня`, `доставка+таможня`), RUB ₽/шт/₽/кг rows that require a sane quote RUB rate, plus mixed factual-expense-over-КП-base rows; row labels keep the source/base explicit. USD/шт rows are not exposed until a reliable quantity denominator from КП itself exists, because shipment/packing quantity would mix КП with factual/order evidence. Quote delivery days are also shown in `Сроки` as a timing reference.
- `Нормализованные метрики факта / по ДТ` contains factual/DT-base normalized rows. Cells that depend on factual logistics expenses carry explicit quality metadata (`status=partial`, `quality=partial_expenses`, `depends_on_expenses_complete=true`) and render yellow until the order's server-owned `expenses_complete` flag is true. Customs-only rows stay normal when customs/DT data exists, and pure КП rows do not turn yellow just because factual logistics expenses are incomplete.
- `Физика груза` uses parsed `packing_list` totals for quantity, gross weight, volume, density and units/kg. It does not fall back to КП values. Customs declaration weight and packing-list quantity over customs weight are shown only as comparison orientation when available.
- `Стоимость товара` uses invoice amount, exact CNY-ledger supplier payment RUB cost, effective CNY/RUB payment rate, customs value as comparison reference, invoice goods RUB/unit from matched payment cost over packing-list quantity or invoice quantity, and exact landed cost. It does not use customs value as the source for invoice goods RUB/unit and does not show КП-derived cargo value rows.
- `Сроки` exposes created/order date, invoice date, planned shipment date (`shipment_date`), actual shipment date, actual FF acceptance date, quote delivery plan, `Плановый срок производства`, `Фактический срок производства`, `Фактический срок доставки = actual_ff_acceptance_date - actual_shipment_date` in calendar days, and `Срок до ДТ / таможни` (`declaration_date - shipment_date`). Production duration start is `invoice_date` as the current business invoice/order date; if it is absent, the registry falls back to server `created_at` and does not use КП/ДТ/packing dates. Planned production ends at `shipment_date`; factual production ends at `actual_shipment_date`. Missing or invalid dates render as `—`; invalid date values also surface diagnostic warnings in the registry payload. Negative production/customs lead-time durations are suspicious source-date evidence, render as `—` with `quality=suspicious_negative_duration` and registry warnings, and must not be shown as ordinary negative business values. The matrix does not use customs declaration date as FF acceptance and does not expose a delivery-plan deviation row. The UI renders these groups with horizontal scroll; ordinary metric labels and section header labels both stay sticky in the left metric column while order-value columns scroll.
- Registry quote RUB/unit uses `quote_total_usd * quote_total_rate / total_units`, where `quote_total_rate` is the same quote-vs-invoice CBR spread estimate when invoices are available and passes the rate sanity guard; it falls back to the quote-date CBR rate only when КП is available and logistics invoices are absent. Fact RUB/unit uses `(logistics_invoice_total_rub + customs_total_payments_rub) / total_units`.
- The comparison UI lets an operator choose one temporary КП PDF, select exactly one shipment column, and render grouped rows with `КП`, `Поставка факт`, `Разница` and `Оценка КП`. Numeric differences are `КП - Поставка`, percent differences use the shipment value as baseline when available, and missing baselines remain `—`. For cost metrics with lower-is-better semantics the status text is explicit (`КП выгоднее`, `КП дороже`, `примерно равно`); neutral rows keep evaluation unavailable.
- Temporary quote RUB/unit in comparison is estimated, not divided by the selected shipment unit count directly. The estimator uses selected-shipment `total_units / customs_gross_weight_kg` first, falls back to selected quote gross weight when customs weight is missing, then divides quote RUB total by `quote_gross_weight_kg * selected_units_per_kg`. If the selected shipment has no usable units/kg coefficient, the quote RUB/unit cell remains unavailable and warns `Нет коэффициента шт/кг для оценки КП`.

## 1.3.1 Guarded historical reconciliation and publication

- The exact 26GN390 adoption plus the exact 26GN237 `legacy_ff_accepted_without_date` activation is planned on one coherent disposable SQLite candidate. The supplier approval fingerprint covers target/evidence/dependency/anomaly/canonical/accounting semantics, not an absolute digest of unrelated mutable runtime tables.

- The transaction collateral digest treats only `sheet_vitrina_v1_supplier_financial_documents.updated_at` as volatile non-semantic read-refresh metadata. That column is omitted from before/after row equality and row-localization fingerprints so an otherwise identical saved-document refresh cannot create an approval loop. Document identity, business fields, expense lines, amounts/currency, shipment binding, parse/file evidence, allocation and capital-event effects remain protected; any change to them still fails closed. Target financial-document evidence is independently pinned by its exact confirmation policy.
- `apps/supplier_shipment_non_target_drift_diagnostic.py` is the repository-owned read-only row localizer for comparing a coherent backup with a later runtime snapshot. It emits stable row fingerprints, changed fields, sanitized values, writer classification and target/dependency relevance; it never mutates either database.

The diagnostic is computed while the disposable candidate exists and cannot authorize or suppress the drift.

Apply requires all three exact fingerprints (supplier, publication and chain), fresh verified backups, persisted chain phase/status, supplier zero-change rebuild and publication zero-change reconciliation. # 1.4 CNY Account Ledger

- `Поставки -> Счёт CNY` is the server-owned management ledger for CNY currency account costing. It is not бухгалтерский налоговый валютный учёт, does not calculate FX revaluation, and does not write `cost_price`, 1C, WB/web-vitrina metrics or Google Sheets/GAS.
- Canonical currency documents live once in `sheet_vitrina_v1_cny_documents`. Supported document types are `cny_conversion_purchase`, `supplier_cny_payment`, `bank_fee`, `opening_balance` and `adjustment`. A document may carry nullable `source_order_id`/`context_order_id`; this only records upload/context provenance and does not mean a whole conversion belongs to that supplier order.
- Canonical ledger rows live in `sheet_vitrina_v1_cny_ledger_operations`. Supported operation types are `opening_balance`, `conversion_in`, `supplier_payment_out`, `conversion_fee`, `transfer_fee` and `adjustment`. Money and rates are calculated with Decimal-compatible storage strings, not float arithmetic.
- Conversion purchase increases CNY balance and RUB value balance by the actual RUB debit; conversion fees in RUB, when parsed/provided, are included in purchased-CNY RUB value. Average account rate after conversion is `balance_rub_value / balance_cny`.
- Supplier CNY payment decreases CNY balance at average account rate before payment. The order payment component is `paid_cny * average_rate_before`; the order effective CNY rate is weighted across all linked supplier-payment operations as `sum(payment_currency_rub_cost) / sum(paid_cny)`. The legacy `approx_yuan_rate` remains manual/advisory and is never overwritten by ledger replay.
- Supplier transfer/bank fees are separate order cost components. RUB fees imported from RUB-account statements add directly to order exact bank fees and do not touch the CNY ledger. CNY fees imported from CNY-account statements create canonical `bank_fee` documents and `transfer_fee` operations, consume CNY at average account rate, update `cny_bank_fee_rub`, and remain a separate fee component rather than being mixed into the effective CNY payment rate.
- Replay is deterministic and server-side after create/update/import of currency documents, after CNY document upload from an order, and after explicit `POST /v1/sheet-vitrina-v1/supply/cny-account/replay`. Replay sorts exact bank execution/accepted datetimes between exact operations. Date-only rows use deterministic same-day financial slots: `opening_balance`, `conversion_in`, `conversion_fee` and `transfer_fee`/`bank_fee` are treated as start-of-day operations in that priority, while date-only `supplier_payment_out` and `adjustment` are treated as end-of-day operations; document created time/id/type are only tie-breakers inside the same slot. This lets same-day conversion CNY be available for same-day supplier payment without a manual sequence field, including when the payment has an execution time but the conversion document has only a date. Such date-only rows are still marked `needs_review` / `date_only_deterministic_sequence` whenever other operations share the date, but they are counted unless they are explicitly `blocked`.
- Historical backfill is supported by replaying all currency documents from the beginning of the stored period and updating existing supplier orders that already have linked `supplier_cny_payment` documents. If there is no positive CNY balance before a historical payment, replay blocks with `missing_opening_balance`; it does not borrow `approx_yuan_rate` and does not fabricate a historical course.
- Order rows/detail expose ledger-derived read-only fields: `cny_ledger_effective_rate` (`Курс CNY по счёту` / effective management ledger rate), `cny_payment_currency_rub_cost`, `cny_paid_amount`, `cny_bank_fee_rub`, `cny_calculation_status`, `cny_calculation_error` and `cny_calculated_at`.
- Exact-cost read fields are derived only on the internal supplier shipment list/detail from the same financial summary contract: `exact_bank_fees_rub`, `exact_currency_payment_cost_rub`, `exact_landed_cost_total_rub`, `exact_landed_cost_per_unit_rub`, `exact_cost_status`, `exact_cost_blockers` and `exact_cost_warnings`. They are absent recursively from supplier-role responses.
- Blocked/diagnostic statuses include `missing_opening_balance`, `insufficient_balance`, `payment_not_linked`, `parse_error`, `ambiguous_allocation`, `document_date_missing` and `no_supplier_payment`. These statuses are visible in CNY account status/ledger and supplier order CNY fields; blocked rows do not emit fake RUB costs.
- The VTB conversion purchase parser extracts `document_number`, date, RUB debit account, CNY credit account, RUB amount, CNY amount, bank rate, bank/branch, accepted/execution datetime and status text from tolerant Russian text-layer PDF parsing. The VTB bank-statement parser extracts account/period/balances, payment rows, conversion rows and fee rows, including operation number from Russian payment purpose text, CNY/RUB turnovers, contract/invoice/ref evidence and fee categories (`transfer_fee`, `currency_control_fee`, `currency_control_vat`, `other_bank_fee`). Raw user PDFs are runtime files only and are not committed; tests use sanitized text fixtures.
- Current bounded allocation model is one supplier CNY payment document -> one supplier order through `source_order_id`. The document/operation schema keeps payment operations independent from conversion provenance and does not block future split allocation rows, but UI for one payment covering multiple orders is not implemented in this checkpoint.

# 2. Parser

- Parser version is `supplier_invoice_parser_v2`. It uses `openpyxl`, searches every worksheet for the invoice table, and recognizes flexible base headers including `NO.`, `MODELS / （型号）`, `NAME & SPECIFICATION / （品名规格）`, `QTY (PCS) / （数量）`, `U.PRICE / （单价）` and `AMOUNT / （总价）`.
- Barcode-column detection is layered and independent of an absolute column: normalized semantic aliases (`Barcode`, `Bar code`, factory typo `Braocde`, `条形码`, `條形碼`, `ШК`, `Штрихкод`, `Штрих-код`) win first; otherwise a barcode-like column between `NAME & SPECIFICATION` and `QTY` is accepted from confirmed relative structure; the current D position is used only when the complete `A=NO., B=MODELS, C=NAME & SPECIFICATION, E=QTY, F=U.PRICE, G=AMOUNT` shape and the D value profile both confirm it. Multiple confirmed candidates fail with an explicit ambiguous-column error, and numeric QTY/price/amount columns are excluded from candidates.
- Parsed diagnostics expose only safe structural evidence: worksheet, header row, method `header_alias` / `relative_structure` / `positional_d`, column number/letter, normalized header and bounded value-profile counts. They never expose invoice contacts, bank details or barcode values.
- Barcode extraction is lossless and stored as a string. Spaces/NBSP and one leading Excel apostrophe are removed; text-cell leading zeroes and exact safe integer numeric cells are preserved without float/scientific-notation output. Non-digit text, non-integral or negative numbers, numeric values above Excel's exact-integer boundary and scientific-notation text are rejected instead of rounded or guessed. Thirteen digits are strong current-template evidence, not a global identity rule or checksum requirement.
- Financial-document parser aggregates customs declaration item weights from goods blocks (`35 Вес брутто`, `38 Вес нетто`) when the text layer exposes per-item rows. For current GTD `10131010/100626/5187132`, expected parser aggregates are `customs_gross_weight_kg ~= 9784.60`, `customs_net_weight_kg ~= 8806.18`, `total_goods_count = 28` and `total_places = 465`.
- `RMB`/`CNY`/`¥` invoice currency is normalized to `RMB`; declared invoice totals may be read from post-table `Total`/`总值` rows when the value is not available in pre-table metadata.
- Contract metadata is extracted from ordinary cells, merged-cell values and bounded workbook drawing XML text. Supported labels include `Contract No`, `Contract No.`, `Contract Number`, `Contract Date`, `Date of Contract`, `合同号`, `合同编号`, `合同日期`, `下单日期`; date formats such as `2026.5.13`, `2026-05-13`, `13.05.2026` and `5/13/2026` normalize to `YYYY-MM-DD`.
- The document-registry contract parser is separate from invoice table parsing: it reads only bounded header text, stores `parser_version=contract_metadata_parser_v2`, and returns non-fatal warnings/errors instead of blocking contract file storage when metadata cannot be extracted.
- Merged-cell/fill-down blocks are handled for product type markers:
  - `高清膜` / `smk` -> `clear`
  - `防窥膜` / `(Anti-Spy)` -> `anti_spy`
  - `磨砂膜` / `(Matte)` -> `matte`
- Compatible model aliases such as `iPhone 15 / 16` stay as one invoice row. Parser-derived classification is exposed only as `source_product_type` / `source_match_key` evidence and never occupies the authoritative `product_type` / `match_key`; parser does not split quantity into separate SKU rows.
- Extras such as OPP packets, labels and cards are stored as `line_type=extra`, not product SKU rows. Product-row comments may mention OPP/labels/cards as packaging instructions without turning the product line into an extra.
- Every product row carries `barcode`; extras may leave it empty. Missing or losslessly unreadable product barcodes remain explicit unmatched evidence, and an invoice without a confirmable barcode column is rejected.

- Active duplicate `match_key` values remain rejected for dictionary hygiene. Active product rows require non-empty `nomenclature_name`; `product_type`, model, `match_key`, aliases and compatible-model fields remain descriptive/legacy fields and never resolve a new supplier invoice SKU.
- Supplier invoice identity resolution builds an index from primary `barcode` plus every value in `barcodes` across all active nomenclature rows, including active hidden rows because hidden is visibility-only. Exactly one active owner with a positive nmID produces `match_status=matched_by_barcode` and atomically projects `nomenclature_item_id`, `internal_sku`, `internal_nm_id`, `internal_name`, authoritative `product_type`/`group_key`, runtime-resolved `group_label`, and the owner's authoritative `match_key` from that same object. Zero owners or an owner without nmID is unmatched with an explicit reason; multiple active owners is ambiguous. No type/model/match_key/alias/compatibility fallback exists, and incomplete owner classification is returned as controlled authoritative-projection/group diagnostics rather than source-derived fallback.
- Source-owned line identity is rebound server-side from the staged upload on create and from the persisted line on update. Source-owned `barcode`, row/order identity, invoice model, `source_product_type` and `source_match_key` are restored from trusted evidence; client-edited barcode, owner item id, group key/label, match key, SKU, nmID, name, status/evidence or `manual_override` cannot replace them. Create, update and explicit rematch repeat the same barcode-owner projection. Before every full create/update save, all source invoice rows must still be present and every product row must resolve to exactly one active barcode owner with finite positive quantity/price/amount; any missing, unknown or ambiguous barcode rejects the transaction before storage.

New server groups and renamed labels appear without supplier UI/parser changes. - Invoice-model consistency is non-blocking diagnostics only. Canonical model keys extracted from the source model are intersected with the matched owner's `compatible_model_keys`/authoritative model evidence: a non-empty intersection is `consistent`, confidently disjoint evidence is `mismatch`/`needs review`, and insufficient evidence is `not_checkable`. This status never changes the barcode owner, `matched_by_barcode`, group, nmID or save eligibility.
- Empty or inactive nomenclature is valid at parse time; the UI/API preserves unmatched rows so an operator can correct the authoritative nomenclature and reparse/rematch. A client-entered nmID is never an identity correction path.
- `sheet_vitrina_v1_supplier_shipment_lines.barcode` is a nullable non-destructive schema addition. Parsed upload payloads, saved shipment detail and read-side line payloads return it; legacy rows read as an empty string. No production backfill is implied by this contract.

# 18. Own invested-capital producer contract

Supplier shipment product lines are an authoritative allocation boundary for module 45. Create/update is atomic: every product row must resolve deterministically to an authoritative nmID and contain positive quantity, unit price and line amount. Any unmatched/ambiguous/invalid row rejects the whole file; no pseudo-SKU, partial save or discretionary money allocation is allowed.

Posted CNY payments create partial ownership layers across all product lines by invoice value and paid-equivalent quantity. Actual shipment and FF acceptance dates create persisted stage boundaries; upload time and planned dates do not. Parsed factual logistics invoices and customs/duty/tax/VAT rows create dated legacy audit capital events at the document date; canonical landed cost admits their expense lines only after document status is `confirmed`. Confirmed direct-RUB bank-fee rows use their own operation date, while CNY fees remain owned by the CNY ledger. Every allocation is proportional to product invoice value and carries document/line provenance plus deterministic dedupe. A cost-affecting document mutation resets `expenses_complete`, while setting it true only certifies completeness and never supplies an amount/effective date. Details and methodology live in `45_MODULE__OWN_PRODUCT_CAPITAL_BLOCK.md`.
