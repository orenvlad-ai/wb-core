# Supplier reconciliation and vitrina publication chain

This deploy adds the schema-only table `sheet_vitrina_v1_supplier_publication_chain_jobs`. No supplier header, historical signal, canonical row or ready snapshot is changed by schema initialization.

The table persists the exact chain fingerprint, component supplier/publication fingerprints, actor, phase, status, timestamps, terminal report and sanitized error. It is execution audit/progress, not a second source of supplier or vitrina truth. Supplier truth remains in its header/audit rows, canonical truth remains in canonical tables, and published table truth remains in `sheet_vitrina_v1_ready_snapshots`.

`apps/supplier_shipment_publication_chain.py` first creates one disposable supplier candidate, plans ready-snapshot publication against that expected post-correction database and hashes the strict order and intermediate digests. Dry-run is production-read-only: it may apply the planned JSON only inside that disposable candidate so a second publication can prove `changed_cells=0`; the helper rejects any database outside the candidate runtime, and the resulting no-op fingerprint/output digest are part of the chain approval. Apply requires the unchanged supplier, publication and chain fingerprints plus explicit fresh backup roots. If the supplier stage fails, its transaction rolls back. If a later publication stage fails after supplier commit, the runner restores and verifies the fresh pre-supplier backup, then records terminal failure. Wildcards, force, partial canonical rebuild and reuse of a proof backup as the fresh apply backup are unsupported.

Candidate collateral mismatch remains fail-closed and now returns a bounded deterministic row-level diagnostic before the temporary database is removed. The report includes protected source rows plus canonical rows outside the target SKU closure, excludes only the documented volatile canonical timestamps, sanitizes long/raw/path/name fields and never changes production truth or acts as an exemption.

The transaction collateral contract is split without weakening it: protected source rows must remain byte-semantically equal before/after the apply transaction. A required full canonical rebuild may add or update rows outside the supplier SKU closure only through `supplier_canonical_rollforward_v1`, whose complete exact row inventory and canonical before/candidate-after digests are part of the supplier and chain fingerprints. Apply requires those exact digests; any unplanned canonical row rolls back. This is not a wildcard or partial-rebuild allowance.
